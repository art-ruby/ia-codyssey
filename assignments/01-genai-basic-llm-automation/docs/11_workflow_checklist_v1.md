# 11_workflow_checklist_v1.md

## 1. 문서 목적

이 문서는 **AI 테크 뉴스 블로그 자동화 프로젝트의 실행 흐름을 단계별 체크리스트 형태로 정리한 운영 기준 문서**이다.

목적은 다음과 같다.

- 실행 전 준비 누락을 줄인다.
- 자동 생성 결과의 품질 점검을 표준화한다.
- 수동 검수 시 확인 포인트를 빠르게 확인할 수 있게 한다.
- 게시 전 위험 요소를 마지막으로 점검한다.
- 반복 운영 시 일관된 작업 습관을 만든다.

---

## 2. 적용 범위

이 체크리스트는 아래 작업 흐름에 적용한다.

- 뉴스 입력 수집 및 정리
- 프롬프트 선택 및 실행 준비
- 모델 실행
- 결과 검토 및 수동 수정
- HTML 산출물 검수
- 게시 승인 전 점검
- 실행 로그 기록

---

## 3. 문서 활용 원칙

이 문서는 설명 문서라기보다 **실행용 확인 문서**로 사용한다.

### 활용 원칙
1. 단계가 시작되기 전에 먼저 체크한다.
2. 문제 발생 시 체크리스트 기준으로 누락 지점을 찾는다.
3. 체크 결과는 필요 시 실행 로그와 함께 남긴다.
4. 운영이 반복되면 자주 빠지는 항목을 보강한다.
5. 체크리스트는 짧고 명확해야 한다.

---

## 4. 전체 워크플로우 기준

이 프로젝트의 기본 워크플로우는 아래 순서를 따른다.

1. 입력 뉴스 수집
2. 입력 파일 정리
3. 프롬프트 버전 선택
4. 모델 실행
5. 초안 결과 검토
6. 비교표/요약/결론 점검
7. HTML 변환 또는 HTML 출력 검수
8. 수동 수정
9. 게시 가능 여부 판단
10. 실행 로그 기록 및 결과 저장

---

## 5. 실행 전 체크리스트

실행 전에 아래 항목을 확인한다.

### 5.1 입력 자료 점검
- [ ] 사용할 뉴스 기사 목록이 준비되어 있는가
- [ ] 기사 출처가 확인 가능한가
- [ ] 기사 날짜가 최근 기준에 맞는가
- [ ] 중복 기사 또는 같은 내용 반복 입력이 없는가
- [ ] 기사 수가 너무 적거나 과도하지 않은가
- [ ] 입력 기사 주제가 비교형 글 작성에 적합한가

### 5.2 입력 파일 정리
- [ ] 입력 파일명이 규칙에 맞는가
- [ ] 파일 버전이 명확한가
- [ ] 실험용 입력과 실제 운영 입력이 구분되어 있는가
- [ ] 불필요한 메모나 노이즈가 제거되었는가
- [ ] 기사별 핵심 정보가 식별 가능하게 정리되어 있는가

### 5.3 실행 목적 확인
- [ ] 이번 실행 목적이 명확한가
- [ ] 초안 생성인지, 비교 실험인지, 게시 후보 생성인지 구분되는가
- [ ] 어떤 결과물을 기대하는지 정의되어 있는가
- [ ] 모델 비교 실험이라면 조건이 동일한가

### 5.4 프롬프트 준비
- [ ] 사용할 프롬프트 버전이 확정되었는가
- [ ] 프롬프트 파일명이 규칙에 맞는가
- [ ] 시스템 지시문과 사용자 지시문 역할이 분리되어 있는가
- [ ] 출력 형식 요구가 명확한가
- [ ] 금지 표현 또는 주의사항이 포함되어 있는가
- [ ] HTML 출력 여부가 명확히 지정되어 있는가

### 5.5 모델 실행 조건
- [ ] 사용할 모델명이 기록되어 있는가
- [ ] 모델별 비교 실험이라면 동일 입력 조건이 유지되는가
- [ ] 온도, 토큰 길이 등 주요 조건이 필요한 수준으로 고정되어 있는가
- [ ] 재실행 기준이 사전에 정리되어 있는가

---

## 6. 입력 품질 체크리스트

입력 품질이 낮으면 출력 품질도 흔들리므로 별도로 확인한다.

### 6.1 좋은 입력의 조건
- [ ] 기사 간 주제 연관성이 있다
- [ ] 비교 가능한 관점이 존재한다
- [ ] 특정 기업/제품에 과도하게 치우치지 않는다
- [ ] 최소한의 사실 정보가 충분히 포함되어 있다
- [ ] 서로 완전히 다른 맥락의 기사만 섞여 있지 않다

### 6.2 나쁜 입력의 신호
- [ ] 제목만 있고 내용 정보가 빈약하다
- [ ] 기사 날짜 차이가 너무 커서 같은 흐름으로 보기 어렵다
- [ ] 출처가 불분명하다
- [ ] 광고성/홍보성 문구가 과도하다
- [ ] 비교형 글을 쓰기 어려운 단일 사건 기사만 있다

### 6.3 조치 원칙
- [ ] 입력 품질이 낮으면 실행 전에 기사 세트를 다시 구성한다
- [ ] 비교가 어려우면 비교형이 아닌 요약형으로 목적을 조정한다
- [ ] 기사 수가 많으면 핵심 기사 위주로 줄인다

---

## 7. 생성 실행 중 체크리스트

모델 실행 중 또는 직후 아래 항목을 확인한다.

### 7.1 출력 형식 확인
- [ ] 요청한 형식으로 출력되었는가
- [ ] 제목, 도입, 본문, 비교, 결론이 포함되었는가
- [ ] HTML 요청 시 HTML만 출력되었는가
- [ ] 불필요한 설명 문장이 섞이지 않았는가

### 7.2 구조 안정성 확인
- [ ] 문단 순서가 자연스러운가
- [ ] 비교표 또는 비교 섹션이 존재하는가
- [ ] 결론이 본문과 연결되는가
- [ ] 요약 박스가 있다면 핵심만 담고 있는가

### 7.3 1차 품질 확인
- [ ] 기사 기반 요약처럼 읽히는가
- [ ] 일반론 반복이 과도하지 않은가
- [ ] 특정 기업 편향이 심하지 않은가
- [ ] 과장된 제목/결론이 없는가
- [ ] 입력에 없는 사실을 단정하지 않는가

---

## 8. 초안 내용 검수 체크리스트

생성된 초안 본문을 읽으며 아래를 확인한다.

### 8.1 제목 검수
- [ ] 제목이 본문 내용을 반영하는가
- [ ] 자극적 표현이 과도하지 않은가
- [ ] 비교 관점이 드러나는가
- [ ] 뉴스 기반 글처럼 보이는가

### 8.2 도입부 검수
- [ ] 글의 주제와 범위가 분명한가
- [ ] 기사 흐름을 요약하는 역할을 하는가
- [ ] 과장된 일반론으로 시작하지 않는가
- [ ] 본문으로 자연스럽게 연결되는가

### 8.3 본문 검수
- [ ] 기사 요약과 해석이 구분되는가
- [ ] 비교 기준이 일관적인가
- [ ] 같은 내용 반복이 심하지 않은가
- [ ] 문장 길이가 과도하게 길지 않은가
- [ ] 근거 없는 미래 예측이 없는가

### 8.4 결론 검수
- [ ] 앞선 내용의 요약 역할을 하는가
- [ ] 우열 판정처럼 끝나지 않는가
- [ ] 불필요하게 단정적이지 않은가
- [ ] 다음 관찰 포인트를 적절히 제시하는가

---

## 9. 비교 품질 체크리스트

이 프로젝트는 비교형 글 품질이 중요하므로 별도 확인한다.

### 9.1 비교 축 점검
- [ ] OpenAI와 Google을 같은 기준으로 비교했는가
- [ ] 비교 항목이 기사 기반인가
- [ ] 항목 간 추상도 수준이 크게 다르지 않은가
- [ ] 우열보다 차이 설명 중심인가

### 9.2 비교 문장 점검
- [ ] “더 낫다”보다 “어떤 방향이 다르다”에 초점이 있는가
- [ ] 기사에서 드러난 포인트와 연결되는가
- [ ] 단정적 승패 표현이 없는가
- [ ] 한쪽만 길게 설명하지 않는가

### 9.3 비교표 점검
- [ ] 표의 각 행이 동일한 성격의 항목인가
- [ ] 주관적 평가 단어가 과도하지 않은가
- [ ] 각 셀이 지나치게 길지 않은가
- [ ] 표만 봐도 핵심 차이가 읽히는가

---

## 10. 사실성 및 리스크 체크리스트

환각, 왜곡, 과장 위험을 점검한다.

### 10.1 사실성 확인
- [ ] 입력 기사에 없는 구체 정보가 추가되지 않았는가
- [ ] 숫자, 출시 시점, 기능명 등이 임의로 생성되지 않았는가
- [ ] 기업 전략을 지나치게 확대 해석하지 않았는가
- [ ] 기사 1건의 내용을 전체 시장 결론처럼 일반화하지 않았는가

### 10.2 표현 리스크 확인
- [ ] “완전히 끝났다”, “압도적 승리” 같은 과장 표현이 없는가
- [ ] 근거 없는 예언형 문장이 없는가
- [ ] 특정 기업에 대한 조롱/비하 표현이 없는가
- [ ] 클릭 유도성 문구가 기준을 넘지 않는가

### 10.3 신뢰성 판단
- [ ] 읽는 사람이 “기사 기반 정리”로 느낄 수 있는가
- [ ] 문장 톤이 블로그 운영 기준과 맞는가
- [ ] 게시 시 오해를 부를 표현이 없는가

---

## 11. HTML 출력 체크리스트

HTML 산출물은 특히 구조 안정성을 확인해야 한다.

### 11.1 기본 구조 확인
- [ ] `<h1>` 또는 제목 구조가 정상적인가
- [ ] `<h2>` 소제목 구조가 일관적인가
- [ ] `<p>`, `<ul>`, `<table>` 등이 적절히 닫혀 있는가
- [ ] 중첩 구조가 깨지지 않았는가

### 11.2 불필요 요소 확인
- [ ] HTML 앞뒤에 설명 문장이 없는가
- [ ] 마크다운 문법이 섞이지 않았는가
- [ ] 코드블록 표시가 포함되지 않았는가
- [ ] 테스트용 문장이나 메모가 남아 있지 않은가

### 11.3 티스토리 사용성 확인
- [ ] 붙여넣기 후 구조가 크게 깨지지 않는가
- [ ] 표가 너무 넓지 않은가
- [ ] 리스트와 문단 간격이 과도하게 이상하지 않은가
- [ ] 요약 박스나 강조 박스가 단순 구조로 유지되는가

---

## 12. 수동 수정 체크리스트

자동 생성 후 사람이 수정할 때 아래 항목을 확인한다.

### 12.1 수정 필요 여부 판단
- [ ] 바로 게시 가능한가
- [ ] 표현만 조금 다듬으면 되는가
- [ ] 구조 수정이 필요한가
- [ ] 사실성 문제로 재생성이 더 나은가

### 12.2 수정 항목 확인
- [ ] 제목 과장 표현 완화
- [ ] 도입부 일반론 축소
- [ ] 비교 축 재정렬
- [ ] 결론 단정 표현 완화
- [ ] HTML 태그 정리
- [ ] 표 문구 길이 조정

### 12.3 수정 후 재검수
- [ ] 수정 전보다 명확해졌는가
- [ ] 새로 넣은 문장에 근거 문제가 없는가
- [ ] 전체 톤이 일관적인가
- [ ] 게시 가능한 수준으로 올라갔는가

---

## 13. 재실행 판단 체크리스트

수정이 아니라 재실행이 필요한 상황을 구분한다.

### 13.1 재실행이 필요한 경우
- [ ] 구조가 크게 무너졌다
- [ ] 비교 자체가 성립하지 않는다
- [ ] 환각 또는 사실 오류가 반복된다
- [ ] HTML 오류가 많다
- [ ] 입력 기사 기반성이 매우 약하다
- [ ] 제목과 본문 방향이 크게 어긋난다

### 13.2 재실행 전 확인
- [ ] 같은 조건으로 다시 시도할 것인가
- [ ] 프롬프트를 수정할 것인가
- [ ] 입력 기사 세트를 바꿀 것인가
- [ ] 모델을 바꿔 비교할 것인가

### 13.3 재실행 후 확인
- [ ] 이전 결과보다 개선되었는가
- [ ] 같은 실패가 반복되었는가
- [ ] 반복 실패라면 로그에 남겼는가

---

## 14. 게시 전 최종 체크리스트

최종 게시 직전에 아래 항목을 확인한다.

### 14.1 내용 최종 확인
- [ ] 제목과 본문이 일치하는가
- [ ] 핵심 비교 포인트가 분명한가
- [ ] 기사 기반 요약이라는 성격이 유지되는가
- [ ] 과장/단정 표현이 관리 가능한 수준인가

### 14.2 형식 최종 확인
- [ ] HTML 구조가 정상인가
- [ ] 표와 리스트가 깨지지 않는가
- [ ] 문단 간격이 지나치게 어색하지 않은가
- [ ] 불필요한 테스트 텍스트가 제거되었는가

### 14.3 운영 최종 확인
- [ ] 최종 파일명이 규칙에 맞는가
- [ ] 게시 후보 버전이 분명한가
- [ ] 승인 여부가 정리되었는가
- [ ] 실행 로그 작성 준비가 되었는가

---

## 15. 실행 로그 기록 체크리스트

실행 후 기록 누락을 막기 위해 확인한다.

### 15.1 최소 기록 항목
- [ ] run_id 기록
- [ ] 실행 날짜 기록
- [ ] 입력 파일명 기록
- [ ] 프롬프트 버전 기록
- [ ] 모델명 기록
- [ ] 출력 파일명 기록
- [ ] 결과 요약 기록
- [ ] 문제 여부 기록
- [ ] 수동 수정 여부 기록
- [ ] 최종 상태 기록

### 15.2 추가 기록 항목
- [ ] 재실행 여부
- [ ] 실패 원인 메모
- [ ] 개선 포인트
- [ ] 다음 액션
- [ ] 기준 문서 수정 필요 여부

---

## 16. 상태 분류 체크리스트

실행 결과 상태를 아래 중 하나로 분류한다.

### 상태 분류
- [ ] Draft Generated
- [ ] Review Needed
- [ ] Manual Edit Done
- [ ] Rerun Needed
- [ ] Approved for Posting
- [ ] Archived for Reference

### 분류 원칙
- 구조는 맞지만 다듬기 필요 → `Review Needed`
- 수정 후 게시 가능 → `Manual Edit Done` 또는 `Approved for Posting`
- 사실성/구조 문제 큼 → `Rerun Needed`
- 운영 참고용 저장 → `Archived for Reference`

## 18. 권장 운영 방식

실무에서는 체크리스트를 너무 길게 느끼지 않도록 운영 방식이 중요하다.

### 권장 방식
1. 실행 전에는 5분 안에 핵심 항목만 빠르게 점검한다.
2. 초안 검수 단계에서 내용/비교/사실성 항목을 집중 확인한다.
3. HTML은 마지막에 별도로 점검한다.
4. 문제가 생긴 체크 항목은 로그와 연결한다.
5. 자주 실패하는 항목은 별도 “핵심 체크”로 승격한다.

## 23. 체크리스트 기반 판정 규칙

체크 결과를 바탕으로 실행 결과를 어떻게 판정할지 기준을 둔다.

### 23.1 게시 가능
아래 조건을 대체로 만족하면 게시 가능으로 본다.

- 구조가 완성되어 있다
- 기사 기반성이 유지된다
- 비교 축이 명확하다
- 과장 표현이 관리 가능한 수준이다
- HTML 구조가 안정적이다
- 수동 수정이 최소 수준이다

### 23.2 수정 필요
아래와 같은 경우 수정 필요로 분류한다.

- 구조는 맞지만 표현이 거칠다
- 결론이 약간 단정적이다
- 비교표 문구가 다소 불균형하다
- 도입부가 일반론 위주다
- HTML은 정상이나 문장 다듬기가 필요하다

### 23.3 재생성 필요
아래와 같은 경우는 수정보다 재생성이 효율적이다.

- 비교 구조가 무너졌다
- 기사 기반성이 매우 약하다
- 사실 오류 또는 환각이 포함되었다
- HTML 오류가 여러 군데 있다
- 제목과 본문 방향이 크게 어긋난다

## 24. 반복 운영 시 개선 포인트 기록 방식

체크리스트는 단순 확인에서 끝나지 않고,  
운영 개선의 근거로도 활용해야 한다.

### 기록 권장 항목
- 자주 실패하는 체크 항목
- 반복적으로 수정하는 문장 유형
- 특정 모델에서 자주 발생하는 문제
- 특정 프롬프트 버전의 강점/약점
- HTML 오류 패턴
- 게시 승인률이 높은 조합

### 활용 방법
1. 실패 항목이 3회 이상 반복되면 체크리스트에 강조 표시한다.
2. 프롬프트 문제라면 프롬프트 문서 수정 후보로 넘긴다.
3. 모델 특성 문제라면 모델 비교 문서에 반영한다.
4. 품질이 좋은 조합은 “권장 실행 패턴”으로 저장한다.

## 25. 핵심 체크 항목 요약

실무에서 가장 중요한 항목만 다시 압축하면 아래 6개다.

- [ ] 입력 기사가 비교형 글에 적합한가
- [ ] 프롬프트 버전과 실행 목적이 명확한가
- [ ] 생성 결과가 기사 기반 요약처럼 읽히는가
- [ ] 비교 축이 일관적인가
- [ ] 과장/단정/환각 표현이 없는가
- [ ] HTML이 바로 사용할 수 있을 만큼 안정적인가

이 6개가 흔들리면 전체 결과 품질도 흔들릴 가능성이 높다.
