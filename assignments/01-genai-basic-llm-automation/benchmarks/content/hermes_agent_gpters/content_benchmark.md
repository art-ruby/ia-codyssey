# AI 도구 소개 글 콘텐츠 벤치마크

## 1. 벤치마크 목적

복잡한 AI 에이전트나 개발 도구를 일반 독자가 이해하고 실제 사용 여부를 판단할 수 있도록 설명하는 콘텐츠 구조를 정의한다.

이 문서는 글의 **내용 전개 방식**을 참고한다. 시각 디자인과 HTML 표현은 `../../format/naver_ninestonelee/format_benchmark.md`를 따른다.

## 2. 핵심 전개 구조

권장 순서:

1. 도구의 정체를 한 문장으로 정의
2. 기존 챗봇·에이전트와 다른 점 설명
3. 기억하기 쉬운 한 줄 비유 제시
4. 실제 실패 사례로 문제를 구체화
5. 해결 방식과 성공 이유 설명
6. 핵심 기능을 번호로 분해
7. 경쟁·유사 도구와 비교
8. 모델·환경 등 선택 조건 제시
9. 실전 활용 시나리오 제공
10. 설치, 요구사항, 비용 정리
11. FAQ로 예상 질문 해소
12. 원문과 공식 출처 명시

## 3. 도입부 작성법

도입부는 다음 세 질문에 바로 답한다.

- 무엇인가?
- 기존 도구와 무엇이 다른가?
- 독자에게 어떤 가치가 있는가?

전문 용어를 먼저 나열하지 않고, “쓸수록 작업 맥락이 누적되는 비서”처럼 기능을 생활 언어로 번역한다. 한 줄 비유는 이해를 돕는 요약일 뿐이며 기술적 사실을 대체하지 않는다.

## 4. 사례 중심 설명

추상적인 기능 설명 전에 실패 또는 문제 사례를 배치한다.

권장 사례 구조:

1. 목표: 무엇을 자동화하려 했는가
2. 구성: 어떤 역할이나 도구를 사용했는가
3. 실패: 어떤 문제가 발생했는가
4. 원인: 왜 실패했는가
5. 변경: 무엇을 바꿨는가
6. 결과: 어떤 개선이 있었는가
7. 의미: 독자가 무엇을 배워야 하는가

사례는 출처에서 확인되는 범위만 사용한다. 성과 수치가 없으면 “극적으로 개선됐다” 같은 표현을 객관적 성과로 바꾸지 않는다.

## 5. 핵심 기능 설명

기능은 `기능명 → 쉬운 정의 → 작동 방식 → 실제 가치` 순서로 설명한다.

예:

- 기능명: 지속적 메모리
- 쉬운 정의: 세션이 끝나도 작업 맥락을 유지
- 작동 방식: 사실과 절차를 구분해 축적
- 실제 가치: 반복 설명과 시행착오 감소

기능 목록은 4~6개가 적절하다. 기능 수보다 독자가 “그래서 어디에 쓰는가”를 이해하는 것이 우선이다.

## 6. 비교 콘텐츠 작성법

비교는 승패가 아니라 설계 철학과 적합한 상황을 보여준다.

필수 비교 항목:

| 항목 | 설명 |
|---|---|
| 핵심 철학 | 제품이 우선하는 가치 |
| 메모리·상태 | 맥락과 지식을 유지하는 방식 |
| 도구 확장 | 외부 서비스 연결 범위 |
| 운영 특성 | 속도, 무게, 관리 난이도 |
| 적합한 상황 | 어떤 사용자와 업무에 맞는지 |
| 한계·주의점 | 도입 전에 검토할 조건 |

“A가 더 좋다”보다 “A는 반복 학습형 업무, B는 광범위한 통합형 업무”처럼 선택 기준을 제공한다.

## 7. 실전 활용법

활용 예시는 서로 다른 독자 유형을 포함한다.

- 1인 창업자: 여러 운영 업무를 한 맥락에서 처리
- 개발자: 코딩 도구와 비코딩 자동화 도구의 역할 분리
- 팀: 정기 리서치, 모니터링, 브리핑 자동화

각 활용법에는 입력, 처리, 결과가 드러나야 한다. “10분이면 설정”처럼 시간이나 성능을 단정하는 문장은 직접 검증된 경우에만 사용한다.

## 8. 설치와 비용 정보

설치 안내는 다음 항목으로 분리한다.

- 지원 운영체제
- 런타임·컨텍스트 요구사항
- 필요한 API 키
- 공식 설치 명령
- 라이선스
- 자체 비용과 외부 API 비용

명령어는 공식 문서에서 현재 유효한지 확인한 뒤 코드 블록으로 제공한다. `curl | bash` 방식은 편리하지만 실행 전 공식 도메인과 스크립트 내용을 확인하라는 주의를 함께 표시한다.

## 9. FAQ 구성

본문에서 가장 많이 생길 질문 3~5개만 선택한다.

- 무료인가?
- 시작하려면 무엇이 필요한가?
- 기존 도구와 무엇이 다른가?
- 어떤 사람에게 적합한가?
- 도입 시 가장 큰 주의점은 무엇인가?

FAQ 답변은 본문 요약 역할을 해야 하며 새로운 주장을 추가하지 않는다.

## 10. 사실 검증 규칙

다음 항목은 게시 직전에 공식 출처에서 다시 확인한다.

- GitHub 스타 수
- 지원 운영체제와 메시징 플랫폼
- 라이선스
- 설치 명령
- 최소 컨텍스트 길이
- 권장 LLM 모델과 정확한 모델명
- 마이그레이션 명령
- VPS 비용과 설정 시간
- 경쟁 제품의 메모리·성능 특성

개인 X 게시물이나 커뮤니티 글의 사례·평가는 “작성자의 사례” 또는 “원문에서 제시한 평가”로 귀속한다.
