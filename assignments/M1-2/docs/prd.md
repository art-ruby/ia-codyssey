# AI Secretary — MVP·확장 단계 제품 요구사항 명세서

- 버전: v1.11 · Hermes 로컬 AI 경로 반영
- 작성일: 2026-10-01
- 작업 위치: `M1-2`
- 근거: [사용자 시나리오](ai-secretary/AI_SECRETARY_SCENARIO.md), [단일 파일 목업](mockup/index.html), 과제에서 제공된 별도 요구사항 문서. API 구현 참고 자료는 M1-1 작업에서 확인한 호출 방식이며, 해당 참고 코드는 현재 `main`에 포함하지 않는다.
- 문서 범위: 제품 요구사항, 화면, 데이터, 승인 규칙, 개발 순서, 인수 기준. 구현 완료를 뜻하지 않는다.
- 단계 용어: **MVP = Milestone A**(웹 자료·AI 채팅·숫자 데이터·배포·웹 자료 휴지통). **확장 단계 = Milestone B**(PC 연결 프로그램·실제 파일 정리·클라우드 사본·연동 삭제). §4의 B~D 흐름, §6.2·§7·§8.1~8.2와 PC 파일 관련 인수 기준은 확장 단계에 적용한다. §8.3의 웹 자료 휴지통은 MVP에 적용한다. 본문의 "MVP에 포함하지 않는다"는 A·B를 합친 이 문서 전체 범위 밖이라는 뜻이다.
- 해석 순서: 최신 사용자 확정사항 → 사용자 시나리오 → 최신 버전 변경사항 → 기존 PRD → 기존 목업. 충돌하면 앞선 근거를 따른다.
- 표기: **[확정 요구사항]** 사용자가 결정한 동작, **[권장 구현안]** 검증 후 조정 가능한 설계, **[초기 가설]** 실제 사용량 측정 후 조정할 수치, **[Open Decision]** 사용자 선택이 필요한 항목. 권장안과 초기 가설을 사용자 확정사항으로 취급하지 않는다.

## 1. 제품 목적과 사용자

AI Secretary는 내가 모은 AI 자료를 이해하고 다시 찾게 도우며, PC에 쌓이는 스크린샷과 다운로드 파일의 정리를 제안하는 개인 비서다. 자료마다 요약과 나에게 중요한 이유를 보여주고, 사용자가 승인한 보관·이름 변경·이동·삭제만 실행한다.

첫 사용자는 서비스 소유자 한 명이다. 모바일과 PC 웹에서 같은 자료와 검토 결과를 본다. 현재 주 프로젝트는 **AI Secretary**다. 프로젝트와 직접 관계없는 학습 자료도 보관할 수 있다.

- 관심 분야: AI Agent·Memory·협업, 자동화, 개발 도구·API, 콘텐츠 생성, 모델·서비스·가격·정책 변화.
- 활동 분야: 프로그램 개발, 업무 자동화, 콘텐츠 제작, 학습·연구, 사업 기획.
- 중요도 기준: 내 관심 분야의 학습 가치와 실제 작업에 영향을 주어 대응이 필요한 변화.
- 성공 경험: “자료를 맡기면 무엇인지와 왜 중요한지 알 수 있고, 내가 승인한 방식으로 정리되며, 나중에 근거와 함께 찾을 수 있다.”

## 2. 인터뷰로 확정한 요구사항 [확정 요구사항]

| ID | 확정 사항 |
|---|---|
| C01 | URL, 사용자가 제공한 제목·설명·본문·핵심 내용을 저장한다. MVP에서 URL 본문 자동 읽기는 필수가 아니다. |
| C02 | 실제 입력하거나 추출한 내용만 분석한다. URL만 있으면 `링크만 저장됨 / 본문 미확인`을 표시하고 원래 URL을 보존한다. |
| C03 | 자료를 받은 뒤 모아서 검토한다. 검토 화면에 요약과 나에게 중요한 이유를 함께 보여준다. |
| C04 | 중요도는 `높음 / 보통 / 낮음`과 이유로 표현한다. AI 제안을 사용자가 바꿀 수 있다. |
| C05 | PC 파일의 실제 이름 변경·이동·삭제를 첫 확장 단계(Milestone B)에 포함한다. (v1.6에서 "첫 MVP"를 조정) |
| C06 | 폴더 확인은 사용자가 버튼을 누를 때 실행한다. 상시 감시와 자동 정기 확인은 제외한다. |
| C07 | PC가 켜져 있고 연결 프로그램이 접속 중이면 모바일에서도 PC 정리를 검토하고 승인할 수 있다. |
| C08 | 이미지, PDF, Word·PowerPoint·Excel, 텍스트·코드는 내용 분석 대상으로 한다. 설치파일·압축파일은 이름·크기 등 기본 정보만 확인한다. |
| C09 | 보관 승인한 자료만 원본 사본을 클라우드에 보관한다. 보관 완료 후에는 PC가 꺼져 있어도 모바일에서 접근할 수 있다. |
| C10 | 모바일 정리 검토는 파일명·요약·판단 이유 중심이다. 정리 검토용 원본 미리보기는 필수가 아니다. |
| C11 | 적절한 기존 폴더가 없으면 새 폴더를 제안하고, 승인 후 생성하여 이동할 수 있다. |
| C12 | PC 파일 삭제는 Windows 휴지통으로 보내는 방식이다. |
| C13 | PC 파일을 휴지통으로 보내면 연결된 클라우드 사본도 삭제 처리한다. |
| C14 | 클라우드 삭제는 휴지통 이동으로 처리하고 보관함·검색에서 제외한다. 복원할 수 있으며 영구 삭제는 별도 동작이다. |
| C15 | AI 동향은 사용자가 제공한 자료 중 관심 분야·프로젝트·작업 영향에 따른 우선순위와 이유를 보여준다. |
| C16 | AI 채팅은 **보관을 승인한 자료만** 참고한다. 미승인 자료를 답변 근거에 섞지 않는다. |
| C17 | 초기 검증에는 표본 데이터 100건 이상을 사용한다. 실제 개인 자료와 표본을 구별한다. |

기존 문서의 숫자 중요도 점수와 PC 삭제 후 클라우드 사본 유지 정책은 위 확정 사항으로 대체한다. 개발 순서는 §16의 과제 제출 마일스톤을 따른다. C01~C17은 이 대화에서 사용자가 확정한 선택을 정리한 기록이며, 특히 C13은 이후 사용자가 다시 명시적으로 유지하도록 지시했다.

## 3. MVP 범위와 권장 초깃값

### 3.1 포함 범위 [확정 요구사항]

**MVP(Milestone A):** 웹 자료 접수(**URL·텍스트만**. 파일·이미지 업로드는 확장 단계), 일괄 검토, 개인 중요도, 보관함·검색, 관련 자료 제안, 자료 기반 채팅, 대화 기록, 클라우드 휴지통·복원(웹 자료), `data` 숫자 CRUD·요약, 표본 데이터와 과제 필수 API·배포.

**확장 단계(Milestone B):** 파일 분석, 수동 PC 폴더 확인, 승인에 따른 실제 파일 작업, 승인 자료의 클라우드 사본, PC·클라우드 연동 삭제. MVP에서 스크린샷 정리·Downloads 정리 메뉴는 "확장 단계 예정"과 PC 미연결 상태를 표시한다.

목업의 10개 메뉴를 활용하고 기능별로 별도 대형 시스템을 만들지 않는다.

### 3.2 후속 단계 [확정 요구사항·권장 범위]

URL 입력(C01)은 MVP, 버튼을 누르는 수동 폴더 확인(C06)은 확장 단계에 포함한다. URL 본문 자동 읽기와 상시 폴더 감시는 두 단계 모두에서 제외한 후속 단계다. 사용자 시나리오는 Telegram 전달, YouTube 자동 이해, Obsidian 정리, 외부 정보 자동 발견도 처음 단계 이후로 둔다. 나머지 확장 후보는 구현 범위를 줄이기 위한 권장안이며 사용자가 기능별로 확정한 목록이 아니다. 시나리오의 하루 장면은 확장이 끝난 모습을 포함한다.

URL 자동 본문 추출, 외부 뉴스·SNS 자동 수집, YouTube 자막 자동 수집, Telegram, Obsidian, 상시 폴더 감시, 예약 정리, 자동 삭제, 의미 기반 자료 연결 그래프, 사용자 판단을 학습하는 추천 모델, macOS·다중 PC 지원은 후속 단계다. MVP에도 새 자료와 과거 승인 자료의 가벼운 관련 후보 제안은 포함한다(§6.4).

### 3.3 초기 구성과 한도 [권장 구현안·초기 가설]

계정·PC 환경·대상 폴더·구성은 권장 구현안이고, 목록·분석 단위·사본 크기의 수치는 초기 가설이다.

| 항목 | 제안 |
|---|---|
| 계정·권한 | 소유자 한 명, 로그인 필수. 목업의 관리자 메뉴는 같은 사용자의 관리 화면이며 별도 관리자 계정은 만들지 않는다. |
| PC 환경 | Windows PC 한 대와 설치형 연결 프로그램. 로컬 디스크의 사용자가 지정한 폴더만 취급한다. |
| 대상 폴더 | 읽기 원본 폴더와 이동 가능한 보관 폴더를 PC에서 직접 등록한다. 하위 폴더 포함 여부도 등록한다. |
| 구성 | 바닐라 웹 + FastAPI + Firestore + 비공개 파일 저장소 + Windows 연결 프로그램. |
| 파일 확인 | 한 번에 목록 200개까지 표시하고 이어서 불러오기. 분석 작업은 20개 단위로 처리한다. |
| 원본 사본 | 파일당 최대 100MB. 초과 시 승인 대기 또는 보관 실패로 표시하고 사용자에게 알린다. |
| 숫자 데이터 | 과제용 주 지표는 자료의 날짜별 접수·보관 건수로 제안한다. 실제 지표는 조회 시 집계하고 `data`에는 수기·표본 기록만 둔다(§11). |

단일 HTML 파일 조건은 기존 **목업**에 적용한다. 실제 서비스는 웹·서버·PC 연결 프로그램이 필요하다.

## 4. 핵심 사용자 흐름

### A. 웹에서 자료 입력 → 검토 → 보관

1. 사용자가 URL, 제목, 설명, 본문·핵심 내용, 저장 이유를 입력한다. URL만 입력해도 접수한다.
2. 같은 URL이 이미 접수되었다면 기존 자료 열기·메모 추가·별도 저장 중 선택한다. AI 사용량과 분석 범위를 보고 사용자가 분석을 시작하면 요약, 중요도, 이유, 프로젝트와 관련 과거 자료를 제안한다. URL만 있으면 본문을 읽었다고 표시하지 않는다.
3. 받은 자료에 쌓인 항목을 한꺼번에 검토한다. 사용자는 제목·분류·중요도·이유·프로젝트를 수정하거나 나중에 보기로 남긴다.
4. 선택한 자료를 보관 승인한다. 승인 후 보관함과 채팅 검색 대상이 된다.

### B. PC 폴더 확인 → 모바일 검토 → 실제 정리

1. PC 연결 프로그램에서 폴더를 등록하고 웹 계정과 연결한다.
2. 모바일 또는 PC 웹에서 `폴더 확인`을 누른다. 연결 상태를 확인하고 대상 파일 목록과 분석 진행률을 보여준다.
3. 파일명·요약·판단 이유와 변경 제안을 확인한다. 파일·폴더의 AI 분석 제외 여부, 이름, 이동 위치, 새 폴더 이름을 고치거나 제외할 항목을 선택한다.
4. 작업용 스크린샷은 묶음 단위로 작업 종료 여부를 확인하고 일부만 선택할 수 있다. 연결된 클라우드 사본이 있는 경우 삭제 승인 화면에는 PC 파일과 사본이 각각 휴지통으로 이동하며 사본만 남길 수 없음을 표시한다. 사본이 없으면 연결 사본 없음 상태를 표시한다.
5. 승인된 파일 버전과 현재 파일이 같은지 확인한 뒤 실행한다. 항목마다 완료·실패·확인 필요 결과를 남긴다.

### C. 승인 자료의 클라우드 보관

파일 보관 승인은 원본 사본 업로드를 시작한다. 승인한 버전의 사본 업로드와 무결성 확인이 끝나야 `보관 완료`가 된다. PC가 꺼져도 보관 완료 자료의 설명과 원본 다운로드를 제공한다. 모든 형식의 브라우저 내 원본 뷰어는 필수가 아니다.

### D. PC와 클라우드의 연결 삭제

삭제를 승인하면 PC 파일을 Windows 휴지통으로 보내고, 해당 파일 버전에 연결된 클라우드 자료가 있으면 함께 휴지통으로 이동한다. 두 작업의 결과를 각각 기록한다. 중간 실패를 전체 완료로 표시하지 않으며 실패한 단계만 재처리한다. 연결된 사본이 있는 자료에서 `PC 파일만 삭제하고 AI Secretary 클라우드 사본은 유지`하는 동작은 삭제 메뉴에서 제공하지 않는다. 연결된 사본이 없는 자료는 §8.2의 상태별 규칙에 따라 PC 파일만 휴지통으로 보낼 수 있다. 장기 보존 자료는 이름 변경·이동·보관 흐름을 사용하도록 삭제 승인 화면에서 안내한다.

### E. 저장한 자료로 질문하기

질문 → 보관 승인 및 보관 완료 자료 검색 → 승인 자료만 반영한 숫자 요약과 원문 근거 구성 → AI Provider를 통한 답변 → 출처 표시 → 대화 저장 순서로 처리한다. 자료가 없거나 본문을 확인하지 못했다면 그 한계를 명확히 말한다.

## 5. 화면 명세 — 목업 10개 메뉴 기준 [확정 요구사항·권장 화면 배치]

PC에서는 왼쪽 세로 메뉴와 오른쪽 콘텐츠 전환을 유지한다. 모바일에서는 같은 메뉴를 접을 수 있게 한다. 모든 화면에 빈 상태·로딩·실패·재시도를 제공한다.

| ID / 목업 키 | 메뉴 | 제공 기능 (표시가 없으면 MVP) |
|---|---|---|

클라우드 휴지통은 지식 보관함의 탭으로 둔다. 파일 작업 내역 탭은 확장 단계에 제공한다. 숫자 데이터 CRUD는 지식 보관함의 `활동 기록` 탭에서 제공하고 지표별 요약은 오늘·채팅 화면에도 표시한다. 받은 자료는 신규 접수, 검토·승인은 MVP에서 웹 자료의 승인 요청 목록이다. 확장 단계에서 검토·승인을 파일 자료까지 포함한 통합 목록으로 넓히고, 스크린샷·Downloads는 각각 해당 자료의 전용 보기로 제공한다. 전용 보기에서 승인해도 같은 Review/Approval 객체와 검증 규칙을 사용한다. 오늘 화면은 예약 브리핑이나 밤사이 외부 수집이 이루어진 것처럼 표현하지 않는다.

AI 동향은 최종 중요도 높은 순, 같은 등급에서는 대응 필요로 분류된 자료 우선, 그다음 최신 접수 순으로 정렬한다. 판단 보류는 별도 묶음으로 표시한다. 대응 필요 이유도 실제 입력 내용에 근거해야 한다.

## 6. 자료 접수·분석 규칙 [확정 요구사항·권장 구현안]

### 6.1 웹 입력

- URL 또는 제목·설명·본문 중 하나 이상 있어야 접수한다. URL은 HTTP(S)만 허용한다.
- 입력 URL은 원문 출처로 보존한다. 표시 제목이 없으면 URL/도메인을 임시 표제로 사용하되 실제 페이지 제목이라고 주장하지 않는다. 비교용 URL 키는 호스트 대소문자, 기본 포트 등 안전한 정규화만 적용한다. 추적 쿼리 등을 임의로 제거해 다른 링크를 같은 것으로 합치지 않는다.
- URL 접수 시 같은 원문 또는 정규화 키의 기존 자료를 찾으면 접수일·상태를 보여주고 `기존 자료 열기 / 기존 자료에 메모 추가 / 새 자료로 별도 저장` 중 사용자가 선택한다. 메모 추가는 원본 내용을 덮어쓰지 않는다. URL 중복과 본문이 비슷한 자료는 다른 판단이다.
- 사용자 설명과 원문으로 제공한 본문은 별도 필드로 보관하여 근거 범위를 구분한다.
- 권장 길이: 제목 200자, 설명·메모 각각 2,000자, 본문 20,000자. 초과 입력은 조용히 잘라 저장하지 않고 안내한다.
- 입력 내용이 있으면 분석 가능 상태로 저장한다. AI 사용량·외부 전송 범위·과금 가능성을 보여주고 사용자가 해당 자료 또는 묶음의 분석을 시작하면 첫 분석을 실행한다. 실패해도 입력은 보존하며 재분석은 사용자가 선택한다. 변경 없는 자료를 반복 분석하지 않는다.
- `AI 분석 제외`를 선택한 자료는 입력 본문(확장 단계에서는 파일 내용·이미지 포함)을 AI Provider에 전송하지 않는다. 사용자가 해제하기 전에는 재분석도 하지 않는다. 채팅 검색 대상에서도 제외해 후속 질문이 원문을 Provider에 보내지 않게 한다. 로컬에서 얻은 기본 메타데이터는 유지한다. 제목·파일명 같은 메타데이터만 채팅 근거로 허용할지는 Open Decision 5에 둔다.
- `나중에 보기`와 임시 자료에는 사용자가 다시 확인할 날짜를 둘 수 있다. 날짜가 지나면 검토 목록의 정리 후보로 올리고, 자동 삭제하거나 승인한 것으로 처리하지 않는다.

### 6.2 PC 파일 형식

아래 형식별 세부 범위는 권장 구현안이다. 사용자 요구인 다섯 파일 그룹(C08: 이미지, PDF, Office, 텍스트·코드, 설치·압축)을 모두 지원하되 — 아래 표는 Office를 Word·PowerPoint·Excel 행으로 나눴다 — 읽을 수 없는 버전과 내용은 상태로 드러낸다.

| 그룹 | 초기 지원·분석 범위 | 한계 표시 |
|---|---|---|
| 스크린샷·이미지 | PNG, JPG/JPEG의 보이는 글과 화면 구성 분석 | 흐림·일부 가림·판독 실패는 불확실 표시 |
| PDF | 텍스트 추출 및 스캔 페이지 OCR | 암호화·깨짐·일부 페이지만 분석한 경우 범위 표시 |
| Word | DOCX 본문·표 | 삽입 이미지나 도형의 내용을 확인하지 않았으면 명시 |
| PowerPoint | PPTX 슬라이드 텍스트·노트 | 이미지·차트 전체를 이해했다고 가정하지 않음 |
| Excel | XLSX 시트 이름·셀·수식 문자열·저장된 계산 결과 | 수식 재계산·매크로·외부 링크 실행 없음, 계산 결과가 오래되었을 수 있음 |
| 텍스트·코드 | TXT, Markdown, 일반 텍스트 소스 코드 | 인코딩 실패·분량 제한 표시, 코드는 실행하지 않음 |
| 설치·압축 파일 | EXE, MSI, ZIP, 7Z 등의 파일명·크기·날짜·해시 | 내용 분석·실행·압축 해제 없음 |

구형 DOC/PPT/XLS는 우선 감지하여 `변환 필요`로 표시하는 방식을 권장한다. 변환기 검증 전 완전 지원으로 표시하지 않는다. 구형 형식까지 필수인지 여부는 구현 시작 시 호환성 결정 항목으로 남긴다.

[초기 가설] 분석 한도는 파일당 20MB, PDF 20쪽, 슬라이드 30장, Excel 5시트·시트당 200행·20열, 추출 텍스트 총 20,000자다. 한도는 설정으로 관리하고 분석한 페이지·시트·범위를 결과에 기록한다. 부분 분석 결과로 문서 전체를 읽었다고 말하거나 자동 삭제를 결정하지 않는다. 원본 사본 크기 한도와 분석 한도는 별개다. 예를 들어 20~100MB 파일은 사본 보관은 가능하지만 내용 분석은 `한도 초과 / 내용 미확인`으로 남을 수 있다. 이때 내용에 근거한 제목·삭제 제안을 만들지 않고 사용자가 직접 판단하게 한다.

### 6.3 분석 출력

제목 제안, 2~3문장 요약, 나에게 중요한 이유, 중요도 제안, 관련 프로젝트, 종류, 확인한 내용 범위, 불확실한 점, 권장 행동을 구조화하여 저장한다. 중요도는 높음·보통·낮음이며 정보가 부족하면 중요도를 비워 두고 `판단 보류` 상태로 표시한다.

AI 제안과 사용자 최종 값을 분리한다. 사용자가 고친 제목·중요도·프로젝트를 재분석 결과로 덮어쓰지 않는다. MVP는 수정 내용을 해당 자료와 명시적 설정에 반영하며 자동 학습 모델을 전제하지 않는다.

### 6.4 관련 과거 자료 제안 [확정 요구사항·권장 구현안]

새 자료 분석 후 기존 **보관 승인·활성** 자료에서 제목, 설명, 실제 입력·추출 본문, 프로젝트, 키워드가 겹치는 후보를 찾는다. 각 후보의 관련 근거와 출처를 보여주고 사용자가 `관련 자료로 연결` 또는 `관련 없음`을 선택한다. 연결은 자료 ID·버전과 사용자 승인 여부를 기록하며 나중에 해제할 수 있다. 근거가 약하면 후보를 내지 않는다. 정확한 URL 중복 경고와 이 관련 후보 제안은 서로 구분한다. 사용자가 수정한 중요도·프로젝트는 해당 자료의 다음 목록 정렬과 후보 비교에 반영하고, 다른 자료에 자동 학습한 선호를 전파하지 않는다.

## 7. PC 파일 정리와 승인 명세

### 7.1 수동 확인과 분류

- 연결된 PC의 등록 폴더만 확인한다. 다운로드 중·잠김·권한 부족 파일은 건너뛰고 이유를 표시한다.
- 같은 경로·버전의 반복 확인은 기존 항목을 갱신한다. 이름이나 내용이 바뀐 파일은 기존 식별 기록과 비교하고 불명확하면 연결 확인을 요청한다.
- 스크린샷은 작업용·정보성·판단 보류로 분류한다. 작업 종료 확인 전 삭제 승인을 완료할 수 없다.
- 관련 가능성이 높은 작업용 스크린샷은 묶어 `작업 종료 — 선택한 파일 정리 검토 / 아직 작업 중 / 일부만 선택`을 제시한다. 묶음 근거가 약하면 확인을 요청한다. 종료 확인은 묶음의 선택한 파일 ID·버전에 기록하고 각 파일의 실제 삭제 승인은 별도로 검증한다. 작업 중인 파일과 제외한 파일은 승인 대상에 넣지 않는다.
- 사용자가 등록 폴더 또는 개별 자료를 `AI 분석 제외`로 지정할 수 있다. 제외 대상은 PC에서 메타데이터만 확인하고 본문·이미지를 AI Provider로 보내지 않는다. 파일별 설정이 폴더 설정을 해제하려면 사용자의 명시적 변경이 필요하다.
- 다운로드는 이름 정리·프로젝트 이동·참고자료 이동·중복 가능·임시파일·판단 보류를 제안한다.
- 정확한 중복은 파일 해시로 확인한다. 내용이 비슷한 파일과 정확히 같은 파일을 구별한다. 유사하다는 이유만으로 하나를 삭제하지 않는다.
- 건수는 파일 수를 기준으로 집계한다. 한 파일에 이름 변경과 이동이 함께 있으면 행동 수와 파일 수를 구분한다.

### 7.2 이름·위치 변경

- 실제 확인한 내용과 출처를 기준으로 이름을 제안한다. 내용 미확인 파일의 제목을 지어내지 않는다.
- 확장자를 보존하고 Windows 예약 이름·금지 문자·경로 길이를 검증한다.
- 사용자가 등록한 쓰기 허용 폴더 안에서만 이동하거나 새 폴더를 만든다. 웹에서 임의의 PC 경로 권한을 추가할 수 없다.
- 기존 대상 파일을 덮어쓰지 않는다. 충돌하면 새 이름을 제안하고 다시 승인받는다.
- 접합점·심볼릭 링크 등을 통해 허용 범위 밖으로 벗어나는 경로를 거부한다.
- 폴더 전체의 재귀 이동·삭제는 MVP에 포함하지 않는다.
- 다른 볼륨으로 이동할 때는 복사 후 크기·해시 확인이 끝나야 원본을 제거한다. 검증 실패 시 원본을 유지하고 임시 복사본 상태를 기록한다.
- 이름 변경·이동의 작업 내역에는 이전 이름·경로와 완료 직후 파일 버전을 보존한다. `되돌리기`는 과거 작업을 역으로 실행하는 **새 승인 작업**이다. 현재 파일 상태·해시·버전, 이전 경로, 허용 범위, 이름 충돌을 다시 확인한다. 조건이 맞지 않으면 자동 덮어쓰기 없이 재검토한다. 삭제 복원은 §8의 휴지통 흐름을 따른다.

### 7.3 승인·재실행

승인은 사용자, 시간, 자료 ID, 파일 버전·해시, 작업 종류, 이전 경로, 새 경로, 제안 버전에 결합한다. 이름 변경·이동·보관·삭제를 각각 선택할 수 있게 하며 같은 파일의 보관과 삭제처럼 충돌하는 선택은 거부한다. AI Provider는 구조화된 제안만 만들고 서버가 경로·버전·작업 종류를 검증한다. Windows 연결 프로그램은 검증된 구조화 작업만 실행하며 AI 출력의 shell/PowerShell/파일시스템 명령 문자열을 실행하지 않는다.

실행 직전 파일 상태를 다시 확인한다. 승인 후 원본 또는 목적지가 달라지면 기존 승인을 무효화하고 재검토를 요청한다. 승인된 정리 때문에 경로만 바뀌고 내용이 같으면 자료와 클라우드 사본 연결을 유지한다.

작업 ID는 재요청해도 동일 작업으로 처리한다. 서버와 PC에 실행 기록을 남기고 통신 응답이 끊겼다고 같은 삭제·이동을 무조건 반복하지 않는다. 배치 일부가 실패하면 성공 항목은 유지하고 실패 항목만 재시도한다. 취소는 아직 시작하지 않은 작업에 적용하며 이미 끝난 작업을 되돌렸다고 표시하지 않는다.

## 8. 클라우드 원본과 휴지통

### 8.1 보관 승인과 사본

- 미승인 자료도 목록·설명·추출 결과는 서버에 저장할 수 있지만, 지속 보관하는 원본 사본은 승인 이후에만 생성한다. AI 분석 제외 자료의 본문·이미지는 Provider 전송과 임시 분석 업로드에서도 제외한다.
- 분석 API에 필요한 일시 전송과 사용자 보관함의 원본 사본을 구분한다. 폴더 분석 전 외부 AI 처리 범위를 안내한다.
- 임시 분석 파일은 작업 종료·실패 후 정리하고, 고아 임시 파일은 24시간 이내 정리를 권장한다. 외부 AI 제공자의 보존 정책은 모델 선정 시 별도 확인한다.
- 사본의 파일 버전·크기·해시를 검증한다. 승인 후 원본이 바뀌었으면 새 버전을 몰래 올리지 않고 재승인을 요청한다.
- 업로드 실패·PC 연결 끊김·한도 초과는 `사본 보관 대기/실패`로 표시한다. 재시도할 수 있으며 보관 완료로 집계하지 않는다.
- 동일한 이름이나 해시만으로 삭제 관계를 추정하지 않는다. 자료와 파일 버전의 명시적인 연결 ID를 사용한다.

### 8.2 연결 삭제의 의미

[확정 요구사항] 연결된 사본이 있는 자료의 삭제 승인 화면은 `PC 원본 → Windows 휴지통`, `연결된 AI Secretary 사본 → 클라우드 휴지통`을 함께 보여준다. 연결된 사본이 있는 경우 PC 파일만 지우고 사본을 남기는 선택은 제공하지 않는다. 사본이 없는 자료는 연결 사본 없음 상태를 표시하고 §8.2의 상태별 규칙을 따른다. 보관할 자료에는 이름 변경·이동·보관을 권한다.

[권장 구현안] 삭제 승인 시 해당 파일 버전의 사본 상태에 따라 다음과 같이 처리한다.

| 사본 상태 | 삭제 처리 |
|---|---|
| 해당 없음(보관 승인 전) | PC 파일만 Windows 휴지통으로 보낸다. 승인 화면에 `연결 사본 없음`을 표시한다. 작업용 스크린샷의 일반적인 경우다. |
| 업로드 대기·업로드 중 | 삭제 승인을 막는다. 사용자는 업로드 완료를 기다리거나 업로드를 취소한 뒤 다시 승인한다. 취소가 확정되기 전에는 PC 작업을 만들지 않는다. |
| 업로드 실패 | 남은 임시 업로드 조각을 정리하고 PC 파일만 휴지통으로 보낸다. 승인 화면에 `보관된 사본 없음 — 삭제 후 AI Secretary에 원본이 남지 않음`을 경고한다. |
| 완료 | 아래 연결 삭제 규칙(C13)을 적용한다. |

| 대상 | 삭제 승인 시 동작 |
|---|---|
| PC 원본 | Windows 휴지통으로 이동. 지원되지 않거나 실패하면 오류 처리하며 영구 삭제로 대체하지 않음. |
| 연결된 클라우드 자료 | 논리적 휴지통으로 이동하고 원본 사본은 복원 가능하게 유지. |
| 보관함·검색·채팅 | 삭제 진행 시작부터 해당 자료를 새 검색·답변 근거에서 제외. |
| 이전 대화 | 기록은 유지하고 해당 출처가 현재 삭제 상태임을 표시. 이후 AI 문맥에서 그 출처에 의존한 과거 답변도 제외. |
| 별도로 보관한 다른 자료 | 이름·내용이 같아도 이번 삭제와 연결되지 않았다면 영향 없음. |

PC와 클라우드는 단일 트랜잭션으로 처리할 수 없으므로 다음 순서를 사용한다.

1. 서버에 `삭제 진행 중`과 승인 기록을 저장하여 검색에서 제외한다.
2. PC가 파일 버전을 확인하고 휴지통 이동을 수행한다.
3. PC 완료가 확인되면 클라우드 휴지통 상태를 확정한다.
4. PC 실패가 확정되면 동시 변경 여부를 확인하여 이전 클라우드 상태로 복구한다.
5. PC 결과가 불명이면 삭제 진행 상태를 유지하고 실행 기록을 대조한다. 성공으로 추정하지 않는다.
6. PC는 성공했으나 클라우드 확정에 실패하면 `PC 완료 / 클라우드 처리 대기`로 표시하고 서버 단계만 재처리한다.

**권장 복원 정책:** 클라우드 복원은 보관함과 사본만 복원한다. PC 파일은 Windows 휴지통에서 별도로 복원한다. PC에서 복원해도 클라우드 자료를 자동 복원하지 않는다. 두 위치의 상태를 구분하여 표시한다.

### 8.3 클라우드 휴지통 — 웹 자료는 MVP, 파일 사본은 확장 단계

MVP에서 웹 자료를 휴지통으로 옮길 때는 사용자가 승인한 자료의 소유권·버전·현재 상태를 확인하고 보관 수명을 `휴지통`으로 바꾼다. 보관함·검색·새 채팅 문맥에서 즉시 제외하며, 복원하면 다시 포함한다. MVP의 웹 자료에는 Cloud Storage 원본 객체가 없다.

클라우드 휴지통은 MVP에서 자동 만료시키지 않는다. 영구 삭제는 별도 선택과 확인을 거쳐 본문·검색용 데이터와 연결된 접수 기록 제거까지 확인한다. 확장 단계의 파일 자료에는 원본 객체·추출 내용 제거도 적용한다. 실패하면 완료로 표시하지 않는다. 접수 기록이 제거되면 과거 날짜의 `received_count`도 줄어든다. 작업 감사 기록에는 자료 ID를 제거한 작업 ID·상태·시간만 남기고 지운 본문을 복제해 두지 않는다. 이전 대화의 인용 문구는 대화 삭제 전까지 남을 수 있음을 영구 삭제 화면에 알린다.

## 10. 검색·AI 답변·대화 기록

- 기본 검색은 제목·설명·추출 본문·메모의 키워드, 기간, 종류, 프로젝트를 사용한다. 전체 대상 검색과 화면 페이지네이션을 구분한다.
- 자연어에서 추출한 검색 조건은 서버에서 검증하며, 사용자가 화면에서 조건을 수정할 수 있다.
- [권장 구현안] 검색 엔진은 실제 Firestore 에디션과 자료량을 확인한 뒤 서버/Python 검색, 미리 만든 키워드, Firestore Enterprise 텍스트 검색을 비교하여 선택한다. Firestore Standard와 Enterprise의 기능을 동일하게 가정하지 않는다. 결과나 처리 범위를 제한했다면 “일부 자료 기준”이라고 표시한다. [Firestore Enterprise 텍스트 검색 문서](https://firebase.google.com/docs/firestore/enterprise/text-search)
- 권장 답변 문맥: 관련 자료 최대 5건, 자료 본문 합계 20,000자, 질문 2,000자, 최근 유효 대화 6개 메시지. 우선순위에 따라 선택하며 한도 초과를 숨기지 않는다.
- 매 질문마다 보관 상태·권한·AI 분석 제외 여부를 재확인한다. 이전 대화에 있던 삭제·미승인·AI 분석 제외 자료를 그대로 다시 AI에 보내지 않는다. 사용자가 직접 입력한 질문은 자료로 자동 보관하지 않는다.
- URL만 있는 자료는 링크와 사용자 제공 정보만 소개한다. 설치파일·압축파일에 대해서는 기본 정보만 근거로 삼는다.
- 답변 출처는 실제 전달한 자료 ID와 대조한다. URL이 없는 파일은 파일명과 보관함 상세 링크를 표시한다.
- 답변에는 실제 확인된 원문 요약과 비서의 해석·제안을 구분해 적는다. 관련 자료 연결도 사용자가 확정한 것과 제안 상태를 구분한다.
- 자료에 쓰인 지시문은 분석 대상이며 시스템 명령이 아니다. 채팅 답변이나 문서 내용으로 PC 작업 승인을 대신할 수 없다.
- 결과 없음, 검색 실패, AI 호출 실패를 구분한다. 검색 실패를 “저장한 자료가 없다”로 표현하지 않는다.
- 응답과 출처를 저장한 뒤 성공을 반환한다. 저장 실패는 상태와 재시도를 제공하며 request_id로 중복 메시지를 방지한다.
- 대화는 자동 저장·목록·복원·삭제를 지원한다. 대화 삭제 시 하위 메시지도 삭제한다. 표본/개인 자료 대화는 서로 섞지 않는다.
- 채팅은 현재 모드의 `/api/data/summary` 기본값을 주입하고 응답에 출처를 명시한다. **개인 모드는 보관 승인·보관 완료·활성 자료만 집계한 실제 `kept_count`(`source=actual`)**, 표본 모드는 표본 기록(`source=sample`)이다. 개인 모드의 수기 기록은 사용자가 요청할 때만 `사용자 입력 기록`으로 따로 조회하며 실제 값과 합산하지 않는다. 미승인·대기 항목의 제목·본문은 어떤 경우에도 채팅 문맥에 보내지 않는다. 내용이 없는 실제 `received_count` 합계를 채팅에 넣을지는 Open Decision 4에 둔다.

## 11. 과제용 시계열 데이터와 요약 [권장 구현안]

사용자 중요도는 높음·보통·낮음으로 유지한다. 과제의 `date, value, memo`와 100건 이상의 숫자 데이터는 파일 크기 대신 **날짜별 자료 접수·보관 건수**로 구성한다. `materials`는 URL·텍스트·파일 등 실제 비서 자료, `data`는 숫자 시계열 기록이다. 두 컬렉션과 API의 책임을 분리한다.

### 11.1 지표와 CRUD

- `received_count`: 한국 날짜 기준 해당 날짜의 자료 접수 건수. URL·텍스트·파일을 포함한다. 접수 기록(§9.2)에서 집계하며 자료가 휴지통에 있을 때는 이력을 유지한다. 영구 삭제한 자료의 접수 기록은 지우고 해당 날짜의 건수를 다시 계산한다.
- `kept_count`: 해당 날짜에 보관 승인한 자료 중 **현재 보관 완료·활성** 상태인 건수. `materials`에서 집계하므로 이후 휴지통 이동·영구 삭제로 제외되면 해당 승인일의 값도 함께 바뀐다.
- `date`: 접수는 등록일, 보관은 승인일의 한국 날짜. `value`: 0 이상의 정수 건수. `memo`: 관측 설명. `metric_type`, `origin`, `mode`, `version`을 별도 필드로 둔다.
- [권장 구현안] **실제(자동) 지표는 `data`에 행으로 저장하지 않는다.** `source=actual` Summary 요청 시 접수 기록과 `materials`에서 계산한다. 이벤트 중복·누락으로 저장된 집계값과 실제 자료가 어긋나는 문제를 피하고, 수정할 수 없는 행을 CRUD 목록에 섞지 않는다. 자료 수가 늘어 조회 비용이 문제가 되면 캐시를 추가하되 캐시는 원천이 아니다.
- 과제의 POST/GET/PUT/DELETE `/api/data`는 **수기·표본 숫자 기록**만 다룬다. 사용자가 명시적으로 저장한 숫자 기록은 그 저장 동작으로 확정된다. 날짜·지표·값·메모를 추가·수정·삭제할 수 있고, 잘못된 날짜·음수·소수가 포함된 건수는 422로 거부한다.
- 수기·표본 값은 실제 지표와 합산하지 않는다. 실제 집계와 사용자 입력을 서로 다른 `origin`으로 표시한다. 어떤 수치도 외부 AI 시장 동향이나 실제 업무 성과로 표현하지 않는다.

### 11.2 Summary 기본값과 계산

`GET /api/data/summary`는 `source=actual|manual|sample`로 출처를 구분한다. `manual`·`sample`은 `data.origin`에 대응하고 `actual`은 저장된 숫자 행이 아니라 자료 상태에서 계산한다. **개인 자료 모드 기본값은 `source=actual`, 표본 모드 기본값은 `source=sample`이며 기본 지표는 `kept_count`다.** 개인 모드는 시스템이 이미 아는 실제 보관 현황을 요약하고, 표본 모드는 `/api/data`에 저장한 표본 기록을 요약한다. 개인 모드의 수기 기록은 `source=manual`을 명시해 요청한다. `metric_type=received_count` 등 다른 지표도 명시적으로 선택한다. 서로 다른 지표·출처·모드를 한 평균에 섞지 않는다. `metric_type=all`을 제공한다면 지표별로 분리된 결과를 반환한다.

응답에는 지표명·출처·모드·조회 기간, 일별 값, 일수, 합계, 일평균, 일별 최소·최대와 추세를 포함한다. 관측 시작 이후 조회 기간의 기록 없는 날은 0건이다. 기록이 전혀 없으면 기간·평균·최소·최대·추세는 null로 표시하고 총합은 0건이다. 자료의 중요도별 개수는 별도의 자료 현황으로 표시하며 숫자 지표의 평균에 섞지 않는다.

추세의 기준일 D는 개인 모드에서는 현재 한국 날짜, 표본 모드에서는 표본 데이터의 최신 날짜다. D를 포함한 최근 7일의 일평균과 그 이전 7일의 일평균을 비교한다. 관측 시작 이후 14일이 되지 않았으면 `비교 부족`이다. 증감률 +10% 이상 증가, -10% 이하 감소, 그 사이는 유지로 제안한다. 이전 기간 0건이면 백분율을 만들지 않고 `새 보관 발생` 또는 `양쪽 모두 0건`으로 표시한다. 이 수치는 사용자의 접수·보관 활동이며 생산성 점수가 아니다.

채팅은 같은 모드의 `/api/data/summary` 기본 계산을 재사용하고 `source`를 함께 전달한다. 과제 표본 모드에서는 명시적으로 생성한 표본 자료와 표본 숫자 기록만 사용하고 실제 개인 자료와 섞지 않는다. **표본 모드**에서 `kept_count` 기록을 수정·삭제하면 다음 기본 Summary와 채팅 요약에 반영된다. 이것이 과제 제출 시연의 `CRUD → 요약 → AI 답변` 흐름이다. 개인 모드에서는 자료를 보관 승인하거나 휴지통으로 옮기면 다음 Summary와 채팅 요약이 바뀐다. 다른 지표를 선택한 화면·질문은 해당 지표의 Summary를 사용한다.

### 11.3 표본 데이터

과제 검증용으로 최소 100개 숫자 Data Point를 준비한다. 예를 들어 60일 동안 `received_count`와 `kept_count`를 각각 생성하면 120개 지표별 기록이다. **표본 숫자 기록은 표본 자료와 독립된 시계열이다.** 생성 시에는 표본 자료 분포를 참고할 수 있지만, 이후 CRUD로 값이 바뀌어도 표본 자료와 일치시키지 않는다. 지표는 `metric_type`과 `source`를 함께 해석한다. 화면·API·채팅에서 `kept_count + actual`은 `현재 보관 자료 수`, `kept_count + manual`은 `사용자 입력 보관 기록`, `kept_count + sample`은 `가상 보관 기록`으로 표시한다. 표본 숫자를 실제 보관 자료 수로 설명하지 않는다.

표본 자료는 채팅 근거 검증용으로 명시적으로 표본·보관 승인·보관 완료·활성 상태로 생성한다. 표본 원본 파일이 실제로 없으면 파일을 읽었거나 사본이 있는 것처럼 표시하지 않는다.

표본 생성은 반복 실행해도 중복되지 않고 개인 자료를 덮어쓰지 않는다. 표본 모드에서 실제 PC 변경 명령을 생성하지 않는다. 실제 파일 기능 검증은 별도 테스트 폴더의 PNG·PDF·Office·텍스트·설치/압축 파일로 수행한다.

| AI Provider Adapter | FastAPI가 호출하는 분석·분류·중요도 제안·답변 인터페이스. MVP 로컬 실행 경로는 Hermes API |

Web → FastAPI → AI Provider Adapter → **Hermes API** → 모델 → 분석·분류·중요 이유·관련 프로젝트 제안·채팅을 MVP의 기본 실행 경로로 둔다. Adapter는 `analyze_material()`, `classify_material()`, `suggest_importance()`, `answer_question()`의 책임을 가진다.

[확정 요구사항] 이번 MVP의 AI 실행 경로를 **Hermes API**로 변경했다. 로컬에서는 `http://127.0.0.1:8642/v1`에 서버 간 통신으로 연결하며 브라우저에 Hermes 키를 전달하지 않는다. Hermes `api_server`의 도구 세트는 비활성으로 유지한다. Adapter는 호출 직전에 이를 확인하고 도구가 켜졌거나 확인할 수 없으면 실패 처리한다.

[검증 결과] 로컬 Hermes의 OpenAI 호환 API에서 Python `openai` SDK로 `provider=openai-codex`, `model=gpt-6-luna` 텍스트 응답이 정상 종료됐다(T01.04). 같은 날 Hermes의 Claude 구독 경로는 upstream 429로 실패했다. Codyssey `gpt-5-mini`는 과거 T01.03의 별도 검증 결과이며 현재 기본 경로가 아니다. 이미지 입력은 확장 단계 A27에서 확인한다.

[권장 구현안] Python `openai` SDK의 `OpenAI(base_url=<Hermes 주소>, api_key=<Hermes API 서버 키>)`와 요청별 `provider=openai-codex`, `model=gpt-5.5`를 사용한다. 환경변수는 `OPENAI_API_KEY`(Hermes API 서버 키), `AI_PROVIDER_BASE_URL`, `AI_PROVIDER_MODEL`, `AI_PROVIDER_ROUTE`다. Hermes가 내부 구독 경로를 선택하므로 이 키를 모델 제공사의 직접 API 키라고 설명하지 않는다. 과제의 API 사용 조건 충족 여부는 제출 전에 별도로 확인한다.

Hermes의 `/v1/models`는 에이전트 이름을 반환하므로 내부 모델 목록으로 해석하지 않는다. 사용 가능한 구독 경로와 모델은 `/api/model/options`에서 확인하고 요청에 둘 다 명시한다. T01.03의 Codyssey 기록은 과거 검증 증거로 보존한다.

**구현 검증:** A25는 현재 Hermes 경로에서 도구 비활성 확인과 Python `openai` SDK 텍스트 호출로 판정한다. HTTP 200이라도 `finish_reason=error`나 빈 응답은 실패다. Rate Limit·사용량·비용과 이미지 입력 지원 여부는 확인 범위만 기록하고 A25 통과 조건으로 삼지 않는다. 과제의 Python 패키지와 Pydantic 검증은 제출 시 확인한다. **확장 단계(A27):** PC 연결 프로그램에서 텍스트를 추출하고, FastAPI는 사용자가 AI 분석을 승인한 범위만 Provider에 전달한다. 이미지·스캔 PDF의 OCR은 PC에서 가능한 범위를 우선 검증하고 실제 Provider의 이미지 입력 가능 여부를 확인한다. **이미지 입력이 지원되지 않으면** 로컬 OCR로 추출한 텍스트만 Provider에 보내고, 해당 자료의 분석 범위에 `텍스트만 분석 · 화면 구성 미분석`을 표시한다. 스크린샷의 작업용·정보성 분류도 텍스트 근거만으로 판단하며 확신이 낮으면 `판단 보류`로 둔다. Render 무료 인스턴스에서 전체 OCR을 수행한다고 전제하지 않는다. 파서·OCR·Windows 파일 작업 라이브러리는 실제 표본으로 선택한다.

브라우저와 클라우드 서버는 PC 파일을 직접 조작하지 않는다. 연결 프로그램이 인증된 HTTPS 연결로 작업을 가져오고 결과를 보고한다. PC에 외부 공개 포트를 열지 않는다. 로그인은 Firebase Authentication 같은 단일 소유자 인증을 권장한다.

- PC 연결은 짧은 유효기간의 일회용 연결 코드로 승인한다. 장치 자격증명은 PC의 OS 보안 저장소에 보관하고 해제 시 폐기한다.
- PC에 Firebase 관리자 키나 공용 AI 키를 배포하지 않는다. 장치 권한은 등록 폴더와 승인 작업으로 제한한다.
- [초기 가설] 마지막 장치 응답 후 60초가 지나면 `연결 확인 필요`로 표시한다. 서버 지연과 PC 종료를 같은 오프라인 원인으로 단정하지 않는다. 실제 장치 연결이 확인되지 않으면 새 파일 작업을 실행하지 않는다. 기존 요약과 클라우드 사본은 조회할 수 있다.
- [초기 가설] 승인 직후 연결이 끊기면 시작하지 않은 작업은 10분 후 승인을 만료시키는 방식을 검증한다. 이미 시작한 작업은 실제 결과를 대조한다.
- 작업을 서버 메모리에만 보관하지 않는다. 서버·PC 재시작 뒤에도 이어 확인할 수 있게 영속 큐, 실행 임대, 작업 ID를 사용한다.
- (확장 단계) 원본 다운로드는 서버가 소유권·보관 상태를 확인하여 제공한다. 영구 공개 URL을 만들지 않으며 휴지통 자료를 일반 다운로드 API로 가져올 수 없게 한다.
- Windows 휴지통 동작은 실제 대상 파일시스템에서 검증한다. 휴지통 사용 실패 시 영구 삭제로 대체하지 않는다. [Microsoft 파일 작업 옵션 문서](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-setoperationflags)
- Cloud Storage 직접 접근을 허용한다면 사용자와 경로별 규칙을 적용한다. 관리자 권한을 쓰는 서버는 자체 소유권 검증도 수행한다. [Firebase Storage 접근 조건 문서](https://firebase.google.com/docs/storage/security/rules-conditions)
- (확장 단계) MVP는 Cloud Storage 없이 Firestore와 AI Provider만으로 동작한다. 확장 단계에서 Cloud Storage for Firebase 사용 전 Blaze 요금제 요구, 무료 사용 범위, 버킷 지역, 예상 저장량과 다운로드량을 확인하고 과금 가능성을 사용자에게 제시한다. 현재 공식 문서는 Blaze 요금제를 요구하며 일부 사용량은 무료 범위에 들어갈 수 있다고 안내한다. [Firebase Storage 요금제 FAQ](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024)

## 13. API 계약 개요 [권장 구현안]

모든 API는 인증, 소유자, 자료 모드, 버전을 검증한다. 목록은 페이지네이션한다. 인증 정보가 없거나 무효하면 401, 다른 소유자의 리소스는 존재를 숨기는 404, 잘못된 입력과 허용 범위 밖·금지 문자 등 잘못된 작업 경로는 422, 버전 충돌·승인 후 변경된 파일·대상 이름 충돌은 409로 응답한다. 작업 접수는 202와 작업 ID를 사용하며 실제 파일 작업 완료를 뜻하지 않는다. `/api/data`는 숫자 기록만, `/api/materials`는 비서 자료만 다룬다.

| API | 역할·계약 |
|---|---|
| POST /api/data | 날짜·지표·건수·메모가 있는 수기/표본 숫자 기록 추가 |

| GET /api/data/summary | §11의 지표별 기간·개수·합계·평균·최소·최대·추세. 기본값은 개인 모드 `source=actual`(자료에서 계산), 표본 모드 `source=sample`(표본 CRUD 반영)의 `kept_count`. `source=manual`은 명시 요청 |
| GET /api/data/{id} | 숫자 기록 상세·버전 |

`/api/data/summary`는 동적 ID 경로와 충돌하지 않게 정의한다. 모든 변경 요청에 중복 방지 ID를 사용하고 PC 작업 보고는 작업·장치·단계와 대조한다. **자료·PC 파일 삭제의 단일 진입점은 검토·승인 API**다. `/api/data/{id}` 삭제는 숫자 기록에만 적용하고 PC 원본이나 연결된 클라우드 사본을 건드릴 수 없다. 클라우드 휴지통 복원·영구 삭제는 기존 별도 확인 규칙을 따른다.

## 14. 비기능 요구사항 [확정 요구사항·초기 가설]

- 키는 서버 환경변수로 관리한다. 프론트에는 공개 API 주소와 공개 인증 설정만 전달한다. CORS는 실제 허용 도메인으로 제한한다.
- 서버에 필요한 비밀은 Firebase 서비스 계정과 Hermes API 서버 키이고, 확장 단계에서 저장소 연결 정보가 추가된다. AI 설정은 `OPENAI_API_KEY`(Hermes API 서버 키), `AI_PROVIDER_BASE_URL`(Hermes 주소), `AI_PROVIDER_MODEL`(선택 모델), `AI_PROVIDER_ROUTE`(구독 경로)다. 구독 계정 자격증명은 Hermes 호스트에서만 관리한다.
- 로컬 실제 키는 `M1-2/.env`에만 두고 커밋하지 않는다. `M1-2/.env.example`에는 변수 이름과 빈 예시 값만 보관한다. `M1-2/.gitignore`는 `.env`, `.env.*`를 제외하고 `.env.example`만 허용하며 서비스 계정 원본 파일을 둘 `secrets/`도 제외한다. Render·Vercel에는 필요한 값을 각 서비스 환경변수로 입력하고, 프론트에는 `API_BASE_URL`과 공개 인증 설정만 전달한다. 기존 M1-1의 `.env` 값은 이 문서나 예시 파일로 복사하지 않는다.
- M1-1의 `.env.example`에는 YouTube 키만 있고 자체 `.gitignore`는 `.env`를 제외한다. 따라서 M1-1의 파일은 M1-2 환경변수의 완전한 목록으로 취급하지 않는다. 배포 전에는 `OPENAI_API_KEY`, `FIREBASE_SERVICE_ACCOUNT_JSON` 또는 키 경로, `API_BASE_URL`, `ALLOWED_ORIGINS`의 실제 사용 위치와 과제 요구를 README에 대응시킨다.
- 바닐라 프론트에서 API_BASE_URL을 빌드/배포 설정으로 주입하는 방법을 README에 명시한다. 브라우저가 서버 환경변수를 직접 읽는다고 가정하지 않는다.
- 입력과 문서 내용을 안전한 텍스트로 렌더링한다. HTML·매크로·설치파일·코드 실행을 분석 기능에 포함하지 않는다.
- [초기 가설] 일별 AI Provider 요청 50회, 출력 1,500토큰 상당을 검토 시작값으로 둔다. 로컬 Hermes 호출 시간은 우선 120초로 설정하고 실제 응답 시간을 측정한다. **20개 분석 묶음과 50회 호출은 별개**다. `파일 20개 = AI 1회`로 계산하지 않는다. 한 자료를 여러 번 호출하면 실제 Hermes API 요청 횟수를 모두 기록하고 분석·채팅에 공통 사용량을 표시한다.
- 비용이 발생할 수 있는 AI 분석은 파일·묶음별 전송 범위, 예상 요청 수(알 수 없으면 추정 불가), 현재 사용량과 과금 가능성을 보여준 뒤 사용자가 시작한다. 제공 문서에 비용 정보가 없다면 금액을 지어내지 않는다. 질문 제출은 채팅 호출 시작 의사로 처리하되 사용량과 제한을 입력 화면에 표시한다.
- 한도 도달 또는 Provider Rate Limit 발생 시 남은 자료는 `AI 분석 대기`로 유지한다. 실패·분실로 처리하지 않고 `사용량 37/50 · 남은 요청 13 · 대기 자료 42건`처럼 요청과 파일 건수를 구분해 표시한다. 재개는 사용자가 선택하며 일자 변경만으로 무한 자동 호출하지 않는다.
- 파일 전송·OCR·AI 분석은 별도 단계 진행률을 표시한다. 긴 작업은 요청 연결이 종료되어도 상태 조회가 가능해야 한다.
- 입력 저장을 우선 보장하고 분석 실패만 재시도한다. 불확실한 파일 작업이나 비용이 드는 AI 작업을 무한 자동 재시도하지 않는다.
- 로그에는 작업 ID·상태·오류 분류를 남기고 원문·토큰·비밀키를 기록하지 않는다.
- 콜드스타트·연결 실패 시 재시도와 상태 문구를 제공한다. 서버 응답 지연만으로 PC가 꺼졌다고 단정하지 않는다. 실제 배포 요금제의 제한은 배포 시 확인한다.

| A21 | AI 분석 제외 파일·자료의 본문과 이미지가 어떤 AI Provider 요청·임시 AI 업로드에도 포함되지 않는다. 제외 해제 전 재분석도 실행되지 않는다. |
| A22 | 묶음 스크린샷에서 작업 종료와 선택 파일을 확인하기 전에는 삭제 승인 단계로 진행할 수 없다. `아직 작업 중`과 제외 파일은 실행 대상이 아니다. |
| A23 | 실제 Provider 요청 수를 사용량으로 기록한다. 한도 도달 후 남은 자료는 실패가 아닌 분석 대기 상태로 유지되며 사용량·대기 건수를 구분해 보여준다. |
| A24 | Milestone A에서 Firestore 숫자 CRUD, Summary, 승인 자료 기반 AI Chat, Conversation 저장·불러오기, Render/Vercel 배포·Swagger·제출 화면·모바일 웹 사용을 검증한다. 표본 모드에서 `kept_count` 기록 수정 → 기본 Summary 변화 → 같은 질문의 AI 숫자 답변 변화를 확인하고, 답변은 가상 기록임을 밝힌다. 개인 모드에서는 자료를 보관 승인·휴지통 이동한 뒤 채팅의 실제 보관 수가 바뀌는지 확인한다. |
| A25 | **스모크 테스트(MVP):** Hermes API의 도구 세트 비활성을 확인하고 Python `openai` SDK로 명시한 구독 경로·GPT 모델의 텍스트 채팅을 1회 호출한다. 실제 응답 모델·정상 종료·비어 있지 않은 응답을 확인한다. 오류·한도 응답은 실제 관찰했거나 별도로 재현한 경우에만 기록한다. 이미지 입력은 MVP 통과 조건이 아니다. |
| A26 | (MVP) 웹 자료를 휴지통으로 옮기면 보관함·검색·새 채팅 문맥에서 제외되고 `kept_count`가 줄어든다. 복원하면 다시 포함된다. 영구 삭제는 별도 확인 뒤 본문·검색용 데이터·접수 기록을 제거하며 실패를 완료로 표시하지 않는다. |
| A27 | (확장 단계) Provider의 이미지 입력을 1회 검증한다. 지원하지 않으면 연결 프로그램의 로컬 OCR 텍스트만 보내는 대체 경로를 1회 검증하고 분석 범위에 `텍스트만 분석 · 화면 구성 미분석`을 표시한다. |

실제 파일 검증은 전용 테스트 폴더에서 수행한다. 원본 손상·무승인 변경·미승인 자료의 답변 유입은 출시 차단 항목이다. 검색 품질은 평가 질문과 정답 자료를 먼저 고정하고 검증한다.

README에는 서비스 소개, 구조·기술 스택, 배포 주소, 웹·서버·PC 연결 프로그램 실행 및 연결 방법, 환경변수, 표본 생성, 형식별 한계, 휴지통 복원 방법을 포함한다. 제출 화면은 숫자 요약과 질문·답변, 데이터 CRUD, 대화 불러오기를 포함한다.

배포·제출 전 `git ls-files`에 `.env`·서비스 계정 원본·실제 키가 없고 `.env.example`만 포함되는지 확인한다. 이 검사는 키의 유효성이나 과제의 Provider 인정 여부를 대신하지 않는다.

## 16. 개발 순서와 기술 검증 항목 [확정 요구사항·권장 구현안]

MVP 인수 기준은 A01·A02·A13(웹 자료 범위)·A14~A19·A23~A26이다. A03~A12·A20~A22·A27은 확장 단계 인수 기준이다. A16·A17은 두 단계에 걸쳐 적용한다.

### Milestone A — MVP·과제 제출 가능 상태

웹 URL·텍스트 입력 → Firestore `materials` 저장 → 검토·보관 승인 → AI Provider Adapter(Hermes API) 분석·채팅 → 근거 자료 표시·대화 자동 저장까지 한 흐름으로 구현한다. 제출 시연은 **표본 모드**에서 진행한다. 별도 `data`의 날짜·값·메모 CRUD, 100건 이상 표본, 지표별 Summary, 대화 목록·불러오기·삭제, Render API·Swagger, Vercel 웹, 모바일 웹 사용, README와 제출 화면을 완료한다. 로컬 Hermes의 `127.0.0.1`은 Render에서 접근할 수 없으므로 배포 전에 인증된 원격 경로(인터넷 구간은 HTTPS 또는 같은 Render 네트워크의 내부 경로)와 구독 사용 가능성을 별도 검증한다. 이 경로가 준비되지 않으면 배포·MVP 완료로 표시하지 않는다. 과제의 API 사용 조건도 별도 확인한다. PC 파일 연결과 클라우드 원본 사본에 의존하지 않아도 이 흐름이 동작해야 한다.

### Milestone B — 확장 단계: PC 파일 정리

Windows 연결 프로그램과 허용 폴더 등록, 버튼을 누르는 수동 확인, 스크린샷 묶음 정리, Downloads 파일 분석·이름 제안·이동·새 폴더 생성, Windows 휴지통 삭제, 모바일 승인, 승인 원본의 클라우드 사본, PC·클라우드 연동 삭제, 부분 실패 복구·작업 기록·되돌리기, 최종 인수 검증을 완료한다. PC 파일 실제 변경은 Milestone B의 승인·버전·경로 검증을 통과한 경우에만 실행한다.

Milestone A 완료를 MVP 완료로, Milestone B 완료를 확장 단계 완료로 별도 표시한다. MVP 완료를 PC 정리를 포함한 전체 개인 비서 기능 완료로 소개하지 않는다. 확장 단계는 MVP 제출 뒤 착수하며 MVP 완료 조건이 아니다. 가장 높은 기술 위험은 Hermes의 배포 경로, 모바일에서 승인한 PC 파일 작업, Office·PDF 추출 범위, PC·클라우드 연동 삭제다. Milestone A 진행 중 작은 표본으로 이 위험과 Hermes 구독 경로의 제한·비용을 확인한다.

구현 착수 시 확인할 기술 항목은 Hermes의 원격 배포·인증·도구 제한·구독 사용 가능성, Firestore 검색 에디션·전략, Cloud Storage 요금제·버킷 지역·예상 용량, 연결 프로그램 배포·Windows 휴지통 라이브러리, 구형 Office 호환성, OCR 위치, [초기 가설]의 한도 수치다. 검증이 어려워도 사용자 확정 기능을 임의로 완료 처리하거나 확장 단계에서 삭제하지 않는다. 범위 변경이 필요하면 실제 검증 결과와 대안을 제시한다.

## 17. 목업에서 다음에 반영할 차이

1. 스크린샷·Downloads는 MVP에서 `확장 단계 예정`과 PC 미연결 상태를 표시하고, 확장 단계에서 연결·확인·승인·결과 상태를 추가한다.
2. 외부 관심·개인 관련성 숫자 점수를 중요도 높음·보통·낮음과 이유로 교체한다.
3. URL만 받은 자료에 본문·자막을 확인했다고 쓰지 않는다. 실제 입력·추출 범위를 표시한다.
4. 검토에서 보관·이름 변경·이동·삭제를 구분하고 수정·제외·작업 종료 확인을 제공한다.
5. PC 연결·허용 폴더·새 폴더 제안·부분 실패·승인 만료를 추가한다.
6. 보관함에 사본 상태와 클라우드 휴지통을 추가하고 PC 삭제의 연결 영향을 보여준다.
7. 표본 모드, `data` 건수 기록 CRUD·지표별 요약, 실제 개인 자료와의 구분을 추가한다.
8. 받은 자료·통합 검토·스크린샷·Downloads의 역할을 분명히 하고 모든 승인 버튼이 같은 객체와 규칙을 사용하게 한다.
9. 같은 URL 경고와 과거 관련 자료 제안·연결 선택을 구분한다. 목업의 `새 연결`·`자료 연결` 카드가 실제 자료 후보로 이어지게 한다.
10. 이름 변경·이동 되돌리기, AI 분석 제외, Provider 사용량·대기 상태를 화면에 표시한다.

## Open Decisions

다음은 사용자의 최종 선택이 필요한 사항이다. 선택 전에는 한 방향을 확정 요구사항으로 표시하지 않는다.

1. **한 자료와 여러 프로젝트의 관계:** ✅ 2026-10-01 결정 — 주 프로젝트 하나(`primary_project_id`) + 관련 프로젝트 여러 개(`related_project_ids[]`). 상세는 `docs/decisions.md`.
2. **저장 이유와 메모:** ✅ 2026-10-01 결정 — 별도 필드 `save_reason`(선택, 2,000자). 메모는 나중 생각용. 상세는 `docs/decisions.md`.
3. **모바일 스크린샷 삭제 확인:** 파일명·요약·판단 이유만으로 승인할지, 삭제 직전 썸네일 수준의 확인을 추가할지. 원본 전체 뷰어는 MVP 필수로 확정하지 않았다.
4. **채팅에 실제 `received_count` 주입:** C16은 승인 자료만 채팅에 참고하도록 한다. 미승인 자료의 접수 건수 합계도 답변 문맥에 허용할지는 아직 결정되지 않았다. 결정 전에는 `source=actual`의 `received_count`를 채팅에서 제외한다.
5. **AI 분석 제외 자료의 메타데이터:** 보관 승인한 제외 자료의 사용자 입력 제목·파일명·날짜만 채팅 근거로 허용할지(본문·이미지는 계속 제외), 채팅에서 완전히 제외할지.
