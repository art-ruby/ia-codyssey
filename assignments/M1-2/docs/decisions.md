## T04.01 AI Adapter·구조화 분석 결과 (2026-10-02, 착수 전 검토의 추천안으로 진행 지시)
- **결과 필드:** AI 제안값은 모두 `ai_` 접두어로 사용자 최종값과 분리한다. `ai_title`(200자) · `ai_summary`(600자, 3문장 이하) · `ai_importance`(`high|medium|low|null`, null = 판단 보류) · `ai_importance_reason` · `ai_primary_project_id` · `ai_kind` · `ai_keywords[]`(8개, T05.02 관련 자료용) · `ai_uncertainties[]` · `ai_recommended_action` · `ai_evidence[]` · `ai_checked_scope`. T04.01은 검증된 객체(`AnalysisResult.to_fields()`)까지, 저장은 T04.02.
- **요약 문장 수:** 2~3문장을 요청하지만 검증은 3문장 이하만 본다. 제목만 있는 짧은 입력은 한 문장 요약이 자연스러워 하한을 두지 않는다. 문장부호 뒤 공백이 없어도 나눈다(`One.Two.`). 소수점·도메인처럼 뒤에 숫자·영문 소문자가 바로 붙으면 나누지 않는다(코드 리뷰 보완).
- **구조화 방식:** 프롬프트로 JSON만 요청하고 서버에서 Pydantic(정의 밖 필드 거부, 엄격한 타입)으로 검증한다. 코드 블록 표시 한 겹은 벗긴다. 실패는 `invalid_output`이며 자동 재시도하지 않는다. `response_format=json_object`는 2026-10-02 실제 호출에서 받아들여졌지만(`finish_reason=stop`) 기능은 이것에 의존하지 않는다.
- **근거 검증:** AI가 입력에서 그대로 옮긴 인용 `evidence` 1~3개를 내고, 서버가 공백을 정리한 뒤 실제로 보낸 입력에 들어 있는지 확인한다(8자 미만은 무효). 인용은 한 필드 안에 있어야 하고(필드 경계를 넘으면 무효), 자료 내용(제목·설명·본문) 인용이 하나 이상 있어야 한다. 저장 이유·메모만 인용하면 사용자 자신의 말이므로 `ungrounded_output`. 요약 자체의 사실 검증이 아니라 대리 지표다.
- **잘못된 값:** 형식 오류·허용 밖 중요도·근거 없음은 전체 실패. 목록에 없는(또는 비활성) 프로젝트, 목록 밖 종류는 해당 필드만 비우고 불확실한 점에 사유를 남긴다. 종류 목록: `article|document|note|reference|tool|other`.
- **보내는 것:** 제목·설명·본문·저장 이유·메모(값이 있는 것만), URL 문자열(열어 보지 않았다고 명시), 활성 프로젝트의 `id`·`name`. 사용자 최종 중요도·프로젝트는 보내지 않는다. 확인 범위는 서버가 계산한다(`fields`, `chars`, `url_fetched=false`).
- **호출 전 거부:** `ai_excluded` 자료(`ai_excluded`), 제목·설명·본문이 모두 빈 URL 전용 자료(`no_content`)는 Provider를 부르지 않는다.
- **오류 분류 추가:** `rate_limited`(429), `timeout`, `output_truncated`(`finish_reason=length`, 출력 한도 초과)를 기존 `provider_http_error`·`provider_connection_error`·`provider_incomplete_response`와 나눈다(T04.03 한도·대기 처리용). `ProviderError.request_sent`는 요청이 Provider에 나갔는지 알려 준다. 호출 전 거부(설정·도구 확인·`ai_excluded`·`no_content`)만 거짓이고, 검증 실패·연결 오류(도달 불확실)는 참으로 보아 사용량에 센다.
- **비활성 프로젝트:** 호출하는 쪽이 넘긴 목록에 `active=false`가 섞여도 Adapter가 빼고 보낸다.
- **보완 검토 후 남은 한계(T04.02 이후 처리):** ① 요약은 문장별 글자쌍 겹침으로만 대조하므로, 입력 단어로 뜻을 뒤집은 문장(예: '종료 계획이 없다')은 통과할 수 있다. 제목·중요 이유·권장 행동·핵심어·불확실한 점은 숫자 검사만 받는다. ② 검증 실패 응답의 토큰 사용량은 오류에 담기지 않는다(요청 수는 `request_sent`로 센다). ③ 기본 요청 시간이 60초라 PRD 초깃값 120초와 다르다(T04.03에서 설정 조정). ④ 본문 20,000자 입력 + 출력 1,500토큰에서 `output_truncated`가 나는지는 실제 긴 표본으로 확인하지 않았다. ⑤ 지시문 삽입이 정당한 근거와 같은 방향을 요구하면 구분할 수 없다.
- **책임 넷, 호출 하나:** `analyze_material`만 Provider를 부르고 `classify_material`·`suggest_importance`는 그 결과에서 꺼낸다. `answer_question`은 텍스트 호출을 그대로 전달하며 채팅 문맥은 T07.02.
- **지시문 삽입:** 자료는 JSON 문자열 값으로만 넣고 시스템 메시지에서 데이터로 고정한다. 완전히 막을 수는 없으므로 도구 비활성 확인·출력 검증·사용자 승인으로 피해를 막는다. 삽입 문장이 정당한 근거와 같은 방향(예: 중요도 높음)을 요구하면 구분할 수 없다.
- **문장 주장 검증(코드 리뷰 보완, 2026-10-02):** 인용만 맞으면 입력과 무관한 요약도 통과하던 문제를 고쳤다. ① 요약의 각 문장이 실제로 보낸 입력과 글자쌍 35% 이상을 공유해야 한다(측정: 실제 요약 문장 0.44~0.96, 무관한 주장 0~0.12, 뜻을 뒤집은 문장 0.29). ② 제목·요약·중요 이유·권장 행동에 입력에 없는 숫자(날짜·금액 등)가 있으면 거부한다. 둘 다 `ungrounded_output`이며 자동 재시도하지 않는다. ③ 중요 이유·권장 행동·제목·핵심어는 추론·조언이라 겹침 검사를 하지 않고, 결과의 `ai_grounding`(`unverified` 목록, `fact_checked=false`)으로 '사실 확인 안 됨'을 표시하게 한다. 화면 표시는 T04.02·T04.04에서 이 값을 쓴다.
- **검증 빈틈 보완(2차 코드 리뷰, 2026-10-02):** ① 글자쌍이 없는 요약 문장(`X.`·`??`)을 겹침 100%로 보던 것을 0으로 바꾸고, 요약은 문장부호·공백을 뺀 글자 10자 이상이어야 한다(`invalid_output`). ② 숫자 검사를 핵심어·불확실한 점까지 넓혔다(`2029 launch` 같은 핵심어 거부). ③ 같은 점검에서 찾은 것: 인용 8자 기준을 문장부호·공백을 뺀 글자로 세어 `--------` 같은 구분선 인용을 막고, 제목·중요 이유가 문장부호뿐이면 거부한다. 불확실한 점도 겹침 검사를 하지 않으므로 `ai_grounding.unverified`에 넣었다.

## T04.02 사용자 시작 분석·상태 조회·재시도 (2026-10-02, 착수 전 검토의 추천안으로 진행 지시)
- **응답 방식:** `POST /api/materials/{id}/analyze`는 원자적으로 `analyzing`으로 바꾸고 202를 준다. AI 호출은 같은 프로세스의 FastAPI 백그라운드 작업이 하며, 화면은 `GET /api/materials/{id}`를 3초 간격으로 조회한다. 창을 닫아도 결과는 저장된다. 기한 전 분석 중 자료에 새 키로 시작하면 409 `analysis_in_progress`.
- **버전 정책:** 분석 상태·결과는 저장소의 새 `transform`(원자적 조건부 쓰기, 버전 증가 없음)으로 쓴다. 시작할 때만 `expected_version`으로 사용자가 본 내용인지 확인한다. 작업이 끝날 때 내용 지문이 시작 때와 다르면 결과를 버리고 `awaiting_start` + `input_changed`. 늦게 끝난 작업은 작업 ID가 다르면 아무것도 쓰지 않는다.
- **입력 지문:** 보낼 내용(입력 필드 + URL) + 활성 프로젝트 `id`·`name` + `PROMPT_VERSION`. 모델명은 넣지 않는다. 완료된 같은 지문이면 200 `reused`이며 AI를 부르지 않는다. 결과가 지금 내용 기준인지는 내용 지문(`ai_content_hash`)만으로 비교해 `analysis_outdated`를 계산한다(조회마다 프로젝트를 읽지 않기 위해서).
- **상태:** `link_only`·`awaiting_start`·`analyzing`·`done`·`failed`. `quota_waiting`은 T04.03, '부분 확인'은 MVP 텍스트 한도(20,000자) 안에서 생기지 않아 쓰지 않는다. 완료 후 내용 수정은 상태를 `done`으로 두고 `analysis_outdated`로 알린다. 실패 후 내용 수정은 `awaiting_start`로 되돌린다.
- **결과 확인 필요:** `analysis_deadline_at` = 시작 + 요청 시간(`AI_TIMEOUT_SECONDS`) × 2. 지난 뒤 조회 때 `analysis_stale=true`. 자동 재호출은 없고, 이 상태와 `failed`에서 사용자가 같은 API에 새 키로 다시 시작한다.
- **시작 거부:** 휴지통 `trashed`, AI 분석 제외 `ai_excluded`, URL만 `no_content`(모두 409, AI 호출 없음). 검토 상태(미검토·나중에 보기·승인)와는 무관하다.
- **화면:** 받은 자료 상세와 검토 카드에 공통 분석 패널(`web/js/analysis.js`). 시작 전 보낼 항목·글자 수·요청 1회 안내 → 분석 중 조회 → 결과('AI 제안 · 사실 확인 안 됨', 근거 인용, 확인 범위) · 실패 사유 · 확인 필요 · 다시 분석. 사용량 숫자·남은 한도는 T04.03.
- **사용량 자리:** `analysis_request_sent`, `analysis_total_tokens`를 저장해 두고 집계는 T04.03에서 한다.
- **남은 한계:** ① 백그라운드 작업은 프로세스 안에서만 돌아 서버 재시작 시 사라진다(확인 필요로 복구). Render 무료 인스턴스가 잠들면 같은 일이 생긴다. ② 서버를 끈 시점에 이미 Hermes로 나간 요청은 사용량에 잡히지 않는다(작업이 사라져 기록할 곳이 없음). ③ 사용자 최종값이 없을 때 AI 제안을 화면 기본값으로 쓸지는 T04.04에서 정한다.
- **분석 중 AI 분석 제외(코드 리뷰 보완, 2026-10-02):** 결과 저장 직전 비교하는 내용 지문에 `ai_excluded`가 없어, 분석 중 제외를 켜도 결과가 저장될 수 있었다. 저장 직전에 현재 `ai_excluded`를 따로 확인해 켜져 있으면 결과를 버리고 `awaiting_start` + `analysis_error=ai_excluded`로 둔다. 이미 Provider로 나간 요청은 되돌릴 수 없으므로 `analysis_request_sent`만 남긴다. 제외를 지문에 넣지 않은 이유: 제외를 껐다 켜는 것만으로 '내용 변경'이나 재분석 대상이 되면 안 되기 때문이다. 분석 중 휴지통 이동은 결과를 저장하지만 휴지통 자료는 화면·채팅 대상이 아니라 그대로 둔다.

## T04.03 AI 사용량·한도·전송 범위 표시 (2026-10-02, 착수 전 검토의 추천안으로 진행 지시)
- **집계 단위:** 소유자 전체(개인·표본 합산), 서울 날짜. 표본 시연도 같은 Hermes 구독을 실제로 쓰기 때문이다. 기록은 `ai_usage/{sha256(소유자·날짜)}` 한 문서(`used`·`failed_sent`·`analysis_count`·`chat_count`·`total_tokens`·`refunded`). 모드 격리 저장소 밖의 소유자 단위 메서드(`read_usage`·`change_usage`, 원자적)로 읽고 쓴다. 클라이언트 접근은 기존 전면 거부 규칙에 포함된다.
- **예약 방식:** 분석 시작(202 전)에 `used < limit`이면 1을 원자적으로 차감한다. 작업이 끝나면 `request_sent=false`만 환불하고, 보낸 요청은 실패·429·시간 초과도 사용으로 남긴다. 서버가 죽어 결과를 모르는 요청은 실제로 나갔을 수 있어 사용으로 남긴다(한도를 넘지 않는 쪽). 환불·결과 기록은 예약한 날짜의 기록에 한다.
- **한도 도달:** 200 `quota_waiting`, 자료는 `analysis_status=quota_waiting`. Provider 429도 `quota_waiting` + `rate_limited`. 날짜가 바뀌어도 자동 호출하지 않고, 사용자가 '다시 시작'할 때만 다시 예약한다. 분석 중·재사용·거부는 예약 전에 걸러 사용량을 쓰지 않는다.
- **표시:** `GET /api/ai/usage`(PRD 외 추가). 분석 확인 상자에 '오늘 AI 요청 37/50 · 남은 요청 13 · 한도 대기 자료 42건 · 비용: 구독 경로, 금액 미확인'. 한도에 도달했으면 버튼이 '한도 대기로 남기기'로 바뀐다. 채팅 입력 영역 표시는 T07에서 같은 API를 쓴다.
- **설정:** 요청 시간 코드 기본값을 120초로 맞췄다(PRD 초깃값, `.env`는 이미 120). 출력 1,500토큰은 요청 1회의 출력 상한으로 해석한다(하루 총량이 아님).
- **세지 않는 호출:** Hermes 도구 확인(`/toolsets`, 모델 호출 아님), 수동 스모크 스크립트(`smoke_*.py`).
- **남은 한계:** ① 대기 자료 수는 100건까지만 센다. ② 여러 자료를 한 번에 시작하는 묶음 분석 UI는 아직 없다(요청 1회 = 자료 1건). ③ 사용량 기록은 Firestore 문서 하나에 몰리므로 초당 수십 건 이상의 동시 예약에서는 트랜잭션 재시도가 늘 수 있다(개인용 MVP 규모에서는 문제없음).
- **검증 실패 응답의 토큰(코드 리뷰 보완, 2026-10-02):** 응답이 도착한 뒤 형식·근거 검증에 실패하면 Adapter가 오류만 던져 그 응답의 `total_tokens`가 버려졌다. `ProviderError.total_tokens`에 응답의 토큰 수를 담고(Adapter의 검증 단계를 `_validate`로 분리해 한곳에서 붙임), 분석 작업이 정산과 `analysis_total_tokens`에 그대로 넘긴다. 연결 오류·시간 초과처럼 응답 자체가 없으면 토큰은 알 수 없어 더하지 않는다.

## T04.04 오늘·AI 동향·중요도 수정 화면 (2026-10-02, 착수 전 검토의 추천안으로 진행 지시)
- **최종 중요도:** 사용자 값(`user_importance`), 없으면 AI 제안(`ai_importance`). AI 값은 분석 완료(`done`)이고 결과 뒤에 내용을 고치지 않았을 때(`analysis_outdated=false`)만 쓴다. 화면은 출처를 '내가 정함' / 'AI 제안'으로 붙인다. 둘 다 없으면 판단 보류. 사용자가 일부러 판단 보류로 둔 것과 아직 고르지 않은 것은 구분하지 못한다(둘 다 null, MVP 한계).
- **대응 필요:** AI 출력에 `needs_action`(bool, 필수)을 더했다. 기한·변경·종료·요청처럼 사용자가 해야 할 일이 적혀 있으면 참이며, 참이면 권장 행동이 있어야 한다(없으면 `invalid_output`). 기존 근거 검증을 그대로 받는다. 출력 계약 변경으로 `PROMPT_VERSION`을 2026-10-02.2로 올렸다(기존 결과는 재분석 대상이 되지만 자동 호출은 없다). 이전 결과에는 값이 없어 '대응 여부 미확인'으로 표시하고 학습 자료 묶음에 둔다.
- **정렬:** `GET /api/materials/priority`(PRD 외 추가)가 현재 모드의 자료를 최대 500건 읽어 Python에서 정렬한다(최종 중요도 → 대응 필요 → 최신 접수 → ID). 활성 자료만, 휴지통 제외. 기존 `owner_id·mode·created_at` 색인으로 읽어 새 색인이 필요 없다.
- **화면 대상:** 휴지통을 뺀 활성 자료 모두. 미승인은 '검토 대기', 나중에 보기·AI 분석 제외·보관됨도 표시한다. AI 분석 제외 자료도 사용자가 정한 중요도가 있으면 포함한다(화면 표시는 AI 전송이 아니다).
- **오늘(S01):** 같은 정렬에서 높음·보통만 최대 3건, 각 건의 이유(사용자가 정했으면 저장 이유 우선, 아니면 AI 중요 이유), 검토 대기·보관 수. 자료가 없으면 빈 상태, 높음·보통이 없으면 판단 보류 수와 AI 동향 안내.
- **AI 동향(S04):** 대응 필요 / 학습 자료(미확인 포함) / 판단 보류 세 묶음. 카드에서 '내 중요도'를 고르면 `PUT user_importance` 후 서버 순서로 다시 그린다. AI 제안은 그대로 둔다.

## T05.01 보관함 검색·필터·페이지네이션 (2026-10-02, "task 05.01 진행" 지시 — 착수 전 결정을 기본값으로 정함)

- **필드:** 사용자가 제공한 제목·설명·본문·저장 이유·메모·URL. 명세의 '제목·설명·입력/추출 본문·메모'에 저장 이유와 URL을 더했다(사용자 입력이므로). AI 결과(요약·핵심어)는 사실 확인 전 제안이라 검색하지 않는다. 추출 본문은 MVP에 없다(확장 단계 파일).

- **검색 전략:** Firestore Standard(전문 검색 없음, `asia-northeast3`). 2026-10-02 실제 자료량은 소유자 기준 표본 모드 보관 51건·개인 0건이다. 최신 접수부터 최대 1,000건을 읽어 Python에서 거르고, 일치 결과를 20건(최대 50건)씩 나눠 준다. 응답의 `scope`로 검색 범위와 한도 초과(`truncated`)를 알리고 화면에도 표시한다. 자료가 수천 건을 넘으면 미리 만든 키워드 색인이나 Enterprise 텍스트 검색으로 바꾼다.

- **코드 리뷰 보완(2026-10-02):** ① '더 보기'를 응답 전에 여러 번 누르면 같은 커서로 요청이 여러 번 나가 목록이 겹칠 수 있었다. 검색·더 보기를 기존 `single-flight`로 묶어 요청 중에는 두 버튼을 끄고 추가 클릭을 무시하며, 이어 붙일 때도 ID로 중복을 거른다(`mergePage`). ② 메모를 고쳐도 결과를 다시 계산하지 않아, 메모로 걸린 자료가 메모를 지운 뒤에도 남았다. 메모 저장 후 **마지막으로 검색한 조건**(폼에 입력만 하고 검색하지 않은 값이 아니라)으로 다시 검색한다.

## T05.02 관련 자료 제안·연결·해제 (2026-10-02, "T05.02 진행" 지시 — 착수 전 결정을 기본값으로 정함)
- **후보 대상:** 같은 모드의 보관 완료 자료(PRD §6.4 '보관 승인·활성'). 자기 자신, 같은 URL 비교 키 자료(중복 처리 T03.02의 영역), 이미 연결했거나 관련 없음으로 판단한 짝은 뺀다. 기준 자료는 미승인이어도 된다(검토 중에 후보를 본다).
- **근거 계산:** AI를 호출하지 않는 결정적 계산. ① 같은 프로젝트(주·관련) ② 공통 핵심어: 지금 내용 기준으로 끝난 AI 핵심어가 상대 사용자 내용에 들어 있는지 ③ 함께 나오는 단어: 제목·설명·본문·저장 이유·메모에서 조사·어미 한 번 떼기(남는 부분 2자 이상일 때만), 숫자 섞인 단어·1자·불용어 제외. 형태소 분석기는 쓰지 않는다.
- **근거가 약함의 기준:** (같은 프로젝트 + 단어·핵심어 1개 이상) 또는 핵심어 2개 이상 또는 단어 3개 이상이 아니면 후보로 내지 않는다(A19 '근거가 약한 후보는 강제 연결하지 않는다'). 점수 = 프로젝트 2 + 핵심어 2×개수 + 단어 개수, 최대 5건.
- **판단 기록:** 승인 API `action=link` + `link: {target_id, target_version, decision}`. 결정은 짝마다 문서 하나(`material_links`, ID = 두 자료 ID를 정렬한 해시)에 두 자료 ID·당시 버전·당시 근거·상태(linked|unrelated|unlinked)·시각으로 남긴다. 두 자료의 버전이 보낸 값과 다르면 `conflict`. 자료 자체의 버전은 올리지 않는다(관계는 자료 내용이 아니다).
- **판단별 효과:** 연결 → 확정 목록, 관련 없음 → 다시 제안하지 않음(나중에 연결로 바꿀 수 있음), 해제 → 근거가 충분하면 다시 제안에 나타남. 해제는 상대가 휴지통에 있어도 가능하다.
- **화면:** 검토 카드와 지식 보관함 상세에 '관련 자료' 패널. 후보 계산이 자료를 훑는 작업이라 '관련 자료 보기'를 눌렀을 때만 불러온다. 제안과 '내가 연결한 자료'를 따로 보여주고, 근거를 그대로 표시한다.
- **T05.03에 넘길 일:** 자료를 영구 삭제하면 그 자료가 들어간 `material_links` 기록도 지워야 한다(남은 관계는 삭제 상태로 처리, task.md T05.03 산출).
- **함께 고친 것:** 검토 화면 안내문의 'AI 요약·중요 이유는 분석 기능이 연결되면 함께 표시됩니다'(분석 연결 전 문구)를 현재 기능에 맞게 고쳤다.
- **코드 리뷰 보완(2026-10-02):** ① 묶음 중복 검사가 (자료, 상대) 순서까지 같아야 중복으로 봐, A→B와 B→A를 한 요청에 다른 결정으로 보내면 둘 다 성공으로 응답하고 마지막 결정만 남았다. 관련 자료 판단은 정렬한 ID 쌍으로 비교해 422로 거부한다. ② 두 자료의 버전 확인과 기록 쓰기가 따로라, 그 사이 수정·휴지통 이동이 있어도 오래된 버전으로 저장될 수 있었다. 저장소에 `run_transaction`(여러 문서를 읽고 확인한 뒤 읽은 문서만 쓰는 원자적 작업, Firestore 트랜잭션)을 더하고, 두 자료·기존 기록 읽기와 확인·쓰기를 그 안에서 한다. 확인 함수는 Firestore 재시도에 대비해 부수 효과가 없다. 근거에 쓰는 프로젝트 이름은 정합성과 무관해 트랜잭션 밖에서 읽는다. 읽은 문서가 다른 소유자·모드 것이면 쓰지 않는다.

## T05.03 웹 자료 휴지통 이동·복원·영구 삭제 (2026-10-02, 착수 전 검토의 추천안으로 진행 지시)
- **이동·복원:** 승인 API `action=trash`로 활성 자료(미승인 포함)를 `lifecycle=trash` + `trashed_at`. 복원은 `active`로 되돌리고 `trashed_at`을 비우며 검토 상태·승인일은 그대로 둔다(미승인 자료가 승인 자료가 되지 않음). 자동 만료 없음.
- **영구 삭제 2단계:** `DELETE /api/trash/{id}?expected_version&confirm=permanent`. ① `lifecycle=deleting` + 작업 ID(모든 화면·목록·분석·수정에서 제외) ② 접수 기록 → URL 예약 → 관련 자료 기록 → 중복 요청 기록 정리 → 자료 문서. 실패하면 `partial`과 실패 단계를 알리고 자료는 `deleting`으로 남아 휴지통에 '일부 실패 · 다시 시도'로 보인다. 다시 부르면 이어서 하며, 이미 지운 것은 건너뛴다.
- **중복 요청 기록:** 지우지 않고 응답 본문만 `{"deleted": true}`로 비운다(같은 키 재전송이 작업을 다시 실행하지 않게). 지문은 해시이고 자료 ID가 무작위 UUID라 되살릴 수 없다. 소유자 단위로 훑는다(`redact_requests`).
- **휴지통 목록:** 새 복합 색인 `owner_id·mode·lifecycle·created_at DESC`로 `trash`·`deleting` 자료를 빠짐없이 읽어(최대 500) 휴지통에 넣은 시각 최신순. 2026-10-02 사용자 확인 후 `firebase deploy --only firestore:indexes`로 배포, 빌드 약 4분.
- **감사 기록:** `audit_events`에 작업 ID·상태·단계·시각만. 자료 ID·본문 없음. 영구 삭제 감사 기록은 남겨 두는 기록이라 시험 후에도 지우지 않는다.
- **확인 단계(화면):** 지워지는 범위(본문·AI 결과, 접수 기록과 접수 건수, URL 예약, 관련 자료 기록, 요청 기록의 자료 내용)와 '이전 대화에 인용된 문장은 그 대화를 따로 지우기 전까지 남을 수 있습니다'를 보여준 뒤에만 보낸다. API도 `confirm=permanent` 없이는 422.
- **화면:** 지식 보관함 '보관 자료 | 휴지통' 탭(휴지통은 처음 열 때 불러오고, 복원하면 보관 자료 검색을 다시 함), 보관함 상세·받은 자료 상세의 '휴지통으로 이동'.
- **T06.02에 넘길 일:** 영구 삭제가 접수 기록을 지우므로 접수 건수(`received_count`)가 줄어든다. 보관 건수(`kept_count`) 감소와 함께 T06.02에서 통합 검증한다.
- **채팅(T07)에 넘길 일:** 대화 기록에 남은 인용문은 이 작업에서 지우지 않는다. 대화 삭제 기능(T07)에서 다룬다.
- **코드 리뷰 보완(2026-10-02):** ① 관계 기록을 방향별 100건까지만 조회해 그보다 많으면 삭제된 자료 ID가 남았다. `find`에 커서가 없어, 정리 단계를 '조회해서 지우기'를 결과가 없을 때까지 되풀이하도록 바꿨다(접수 기록·URL 예약도 같은 방식, 지웠는데 같은 문서가 다시 보이면 멈춤). ② 자료 문서를 지운 뒤 감사 완료 기록에 실패하면 감사가 running에 남고 재시도는 404였다. `run_transaction`이 문서 삭제(쓰기 값 None)도 하도록 넓히고, 자료 삭제와 감사 완료를 한 트랜잭션으로 한다. 실패하면 자료가 남아 `partial` + 재시도로 끝낼 수 있다. 남은 한계: 관련 자료 화면의 판단 기록 조회(`links_for`)는 방향별 100건까지라, 한 자료에 판단이 그보다 많으면 일부 판단한 짝이 다시 제안될 수 있다(개인용 규모에서는 드묾).

## T05.04 검색·채팅에 전달할 자료의 공통 필터 (2026-10-02, "다음 task 진행" 지시 — 착수 전 결정을 기본값으로 정함)
- **공통 함수(`materials/eligibility.py`):** `material_is_chat_eligible(doc, ctx)` = 소유자·모드 일치 + 활성 + 보관 승인 + 보관 완료 + AI 분석 제외 아님. `exclusion_reason`이 빠진 이유를 하나 돌려준다(`not_found`·`trashed`·`unapproved`·`not_kept`·`ai_excluded`, 앞 조건 우선). 영구 삭제 진행 중(`deleting`)도 `trashed`로 본다. 다른 소유자·모드는 존재를 드러내지 않게 `not_found`.
- **보관함 표시와 AI 문맥의 구분:** `library_visible` = 소유자·모드 + 보관 완료(AI 분석 제외와 무관). AI 분석 제외 자료는 보관함·검색에는 보이지만 AI 문맥에는 보내지 않는다. Open Decision 5 결정 전까지 제외 자료의 제목·날짜 같은 메타데이터도 보내지 않는다(엄격한 쪽, T03.04 결정 유지).
- **질문 때 다시 읽기:** `refresh_and_filter(store, ctx, ids)`가 자료를 최신 문서로 다시 읽어 거른다(없으면 `not_found`). 중복 제거·순서 유지. 새 질문과 과거 대화 문맥 모두 T07에서 이 함수를 쓴다. 이유별 건수는 화면의 '근거에서 뺀 자료' 안내에 쓴다.
- **AI로 보내는 필드:** `ai_payload` = 제목·설명·본문·저장 이유·메모·URL·접수일 중 값이 있는 것. 자료 ID·소유자·모드·AI 결과·내부 작업 필드는 보내지 않는다(근거 표시는 서버가 자료 ID와 연결해 관리한다, T07).
- **기존 함수와의 관계:** `materials.service.chat_eligible`(소유자·모드 없는 단순 판정)은 그대로 두고, AI 문맥에 넣는 경로는 이 모듈을 쓴다. 지금 AI에 자료를 보내는 경로는 분석(T04, 자료 한 건·제외 자료는 호출 전 거부)뿐이며, 관련 자료 후보는 AI에 보내지 않는다. 채팅(T07)이 이 모듈을 처음 실제로 쓴다.
- **함께 고친 것:** T05.03 휴지통 목록 순서 시험이 Windows 시계 해상도로 가끔 실패했다(두 이동의 `trashed_at`이 같음). 서버 정렬에 ID 순 동률 처리를 넣고 시험에 짧은 간격을 두었다.

## T06.01 숫자 기록 CRUD와 입력 검증 (2026-10-02, "진행" 지시 — 착수 전 결정을 기본값으로 정함)

## T06.02 실제·수기·표본 Summary와 추세 계산 (2026-10-02, "진행" 지시 — 착수 전 결정을 기본값으로 정함)
- **허용 출처:** 개인 모드 `actual`(기본)·`manual`, 표본 모드 `sample`(기본)·`actual`(표본 모드 자료로 계산). 개인 모드의 `sample`, 표본 모드의 `manual`은 422 — 출처·모드가 섞이지 않게 한다.
- **실제 값:** 접수 수는 접수 기록의 `received_at`을 서울 날짜로 센다(휴지통이어도 유지, 영구 삭제하면 기록이 지워져 빠짐, PRD §11.1). 보관 수는 지금 `is_kept`인 자료를 `storage_approved_at`의 서울 날짜로 센다(휴지통·삭제 중이면 빠지고 복원하면 돌아옴). 저장된 집계값은 없다.
- **수기·표본:** `data`에서 `origin`이 같은 기록만 지표별·날짜별 합계.
- **기간:** 관측 시작 = 그 계열의 첫 날짜. 요청 시작일이 그보다 이르면 관측 시작으로 맞춘다. 끝은 요청 끝일 또는 기준일. 시작이 끝보다 늦으면 빈 결과(추세는 계산).
- **추세:** 기준일 D = 개인 모드 오늘(서울), 표본 모드 그 계열의 최신 날짜. D 포함 최근 7일 합계와 이전 7일 합계를 비교(같은 일수라 평균 비율과 같음). 변화율 = (최근-이전)×100/이전(부동소수 오차를 줄이려고 나눗셈을 마지막에), 소수 첫째 자리. +10% 이상 증가·-10% 이하 감소·사이 유지, 관측 14일 미만 `insufficient`, 이전 0건은 `new`/`both_zero`.
- **조회 방식:** 기존 오름차순 색인으로 `intake_records`·`materials`·`data`를 읽어(각 최대 10,000/5,000) 서버에서 계산. 새 색인 없음.
- **채팅(T07)에 넘길 일:** 같은 모드의 기본 요약을 채팅 문맥에 주입하고 `source`·`label`을 함께 보여준다(PRD §11.2).

## T07.01 질문 검색·자료 문맥·숫자 요약 구성 (2026-10-02, "진행" 지시 — 착수 전 결정을 기본값으로 정함)

## T07.02 근거 답변·출처 검증·실패 구분 (2026-10-02, "다음 진행" 지시 — 착수 전 결정을 기본값으로 정함)
- **답 형식:** 모델은 JSON 하나로 답한다 — `from_materials`(자료에서 실제 확인한 내용, 자료 번호 표기)·`interpretation`(비서의 해석·제안)·`sources`(자료 번호)·`related_suggestions`(번호 쌍)·`limitations`. JSON이 아니거나 필드 타입이 틀리면 `invalid_output`(Provider 실패, 토큰은 사용량에 남김). 정의 밖 필드(예: 자료 속 지시로 생긴 승인·삭제 '작업')는 버린다.
- **출처 대조:** 모델은 자료 ID를 모른다. `sources`와 본문의 '자료 N' 언급을 실제 전달한 자료 번호(1~전달 수)와 대조해 ID로 바꾼다. 범위 밖 번호는 출처에 넣지 않고 `rejected_source_numbers`로, 본문에서 언급한 없는 번호는 한계 문구로 알린다. 숫자가 아닌 값은 버린다. 출처를 새로 만들지 않는다.
- **URL-only:** URL은 있고 설명·본문이 없는 자료. 문맥에 '확인 범위: 링크와 사용자가 쓴 정보만(본문 미확인)'을 붙이고, 출처로 쓰이면 `basis: link_only`와 '본문을 확인하지 않은 자료' 한계를 붙인다.
- **관련 자료:** 전달한 자료끼리 `material_links.state=linked`인 쌍은 모델 언급과 무관하게 `user_confirmed`로 보여 준다(문맥에도 '사용자가 확정한 관련 자료' 번호로 알림). 모델이 제안한 나머지 쌍은 `ai_suggested`. 범위 밖 번호·같은 번호 쌍은 버린다.
- **숫자:** 응답 `numbers`는 문맥에 넣은 서버 Summary 그대로에 `virtual`(표본 출처 여부)을 붙인 것. 답변 문장의 숫자가 질문·요약·전달 자료 어디에도 없으면 `unverified_numbers`와 한계 문구(답을 막지는 않는다). '자료 N'의 번호와 앞자리 0은 비교에서 뺀다.
- **실패 구분:** 문맥 구성 중 저장소 오류 → 503 `search_failed`(예약 전이라 사용량 없음, '저장한 자료가 없다는 뜻이 아님'), 한도 도달 → 429 `quota_exceeded`(Provider 미호출), Provider 오류·형식 오류 → 502 `provider_failed` + `kind`(보내기 전 실패는 환불, 보낸 뒤는 실패·토큰 기록), AI 설정 없음 → 502 `missing_ai_settings`. 결과 없음은 성공 응답에 서버가 '근거가 되는 보관 자료를 찾지 못했습니다.'를 첫 한계로 붙인다. 실패는 모두 아무것도 저장하지 않은 `NoChange`라 같은 키로 다시 보낼 수 있다.
- **Provider 호출:** 근거 자료가 없어도 숫자 요약이 있으므로 호출한다(한계 문구는 서버가 붙임).
- **저장 후 성공:** `conversations` 문서(`title`·`messages[]`·`message_count`·`last_message_at`)에 질문과 답(검증된 출처·관련·당시 숫자 요약·`request_id`)을 저장한 뒤 200. 이어지는 질문(`conversation_id`)은 저장된 메시지를 과거 대화로 쓰고 버전 확인으로 덧붙인다. 다른 모드·소유자의 대화는 404(Provider 미호출). 대화당 200개 메시지(문서 1MB 보호) 넘으면 409 `conversation_full`. 같은 Idempotency-Key는 저장된 응답을 재생(AI 재호출 없음). 목록·복원·삭제·저장 실패 상태와 재시도는 T07.03.

## T07.03 대화 자동 저장·불러오기·삭제 (2026-10-02, "진행" 지시 — 착수 전 결정을 기본값으로 정함)
- **구조:** `conversations` 문서 하나에 `messages[]`를 둔다(PRD §9.2가 허용한 '문서 안 messages'). 대화를 지우면 메시지도 같은 문서와 함께 원자적으로 사라진다. 대화당 200개 메시지(문서 1MB 보호).
- **덧붙이기:** T07.02의 '버전 확인 후 update'를 트랜잭션 덧붙이기(`append_messages`)로 바꿨다. 같은 대화에 동시에 질문해도 한쪽이 409로 답을 잃지 않는다. 이미 있는 메시지 ID는 다시 넣지 않는다.
- **저장 실패:** AI 답을 받은 뒤 대화 저장에 실패하면 검증된 질문·답을 `chat_pending`(새 컬렉션, ID = 답변 메시지 ID)에 보관하고 503 `{reason: save_failed, saved: false, pending_id, retryable: true, answer…}`를 돌려준다. 이 응답도 요청 기록에 남아 같은 키 재전송은 AI를 다시 부르지 않는다. 보관마저 실패하면 `pending_id: null`, `retryable: false`와 '다시 질문' 안내(그 답은 복구할 수 없음).
- **재저장:** `POST /api/conversations {pending_id}`. 서버가 보관한 답만 옮기고 보관본 삭제와 한 트랜잭션이라 두 번 저장되지 않는다(두 번째는 404, 같은 키는 재생). 원래 대화가 사라졌거나 가득 찼으면 새 대화(ID = 보관 ID)로 저장하고 `moved_to_new: true`. 본문은 `title`·`pending_id` 중 하나만, 그 밖의 필드(메시지·답변·출처)는 422 — 클라이언트가 답을 지어 넣을 수 없다. 대기 답변은 `DELETE /api/conversations/pending/{id}`로 버릴 수 있다.
- **목록:** 현재 모드의 대화를 생성 최신순(새 복합 색인 `conversations(owner_id, mode, created_at DESC)` 배포), 메시지 제외. '최근 대화한 순'은 색인·쓰기 비용이 더 들어 MVP에서는 쓰지 않는다. 저장 대기 답변(`pending`)도 함께(같음 조건 조회라 추가 색인 없음).
- **상세:** 답변 출처마다 지금 자료 상태 `current_status`(available·trashed·deleted·unapproved·not_kept·ai_excluded)를 붙인다. 기록은 고치지 않는다(PRD §8.2 '기록은 유지하고 현재 삭제 상태를 표시'). 그 출처에 기댄 과거 답변을 AI 문맥에서 빼는 일은 T07.01이 질문 때마다 한다.
- **삭제:** 대화와 그 대화의 저장 대기 답변을 한 트랜잭션으로 지우고, 요청 기록(Idempotency)의 응답 본문 중 이 대화·대기 답변 ID를 담은 것을 `{deleted: true}`로 가린다(같은 키 재전송이 지운 답을 다시 내주지 않게, T05.03과 같은 방식). 영구 삭제한 자료의 인용문이 대화에 남아 있으면 이 삭제로 지운다(T05.03에서 넘긴 일).
- **남은 한계:** 서버가 AI 답을 받은 직후 죽으면 보관도 못 해 요청 기록이 `processing`으로 남는다. 같은 키는 409 `in_progress`이고 새 키로 다시 질문해야 한다(사용량은 이미 1 썼다).
