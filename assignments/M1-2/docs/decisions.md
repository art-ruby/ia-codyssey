## T04.01 AI Adapter·구조화 분석 결과 (2026-10-02, 착수 전 검토의 추천안으로 진행 지시)
- **결과 필드:** AI 제안값은 모두 `ai_` 접두어로 사용자 최종값과 분리한다. `ai_title`(200자) · `ai_summary`(600자, 3문장 이하) · `ai_importance`(`high|medium|low|null`, null = 판단 보류) · `ai_importance_reason` · `ai_primary_project_id` · `ai_kind` · `ai_keywords[]`(8개, T05.02 관련 자료용) · `ai_uncertainties[]` · `ai_recommended_action` · `ai_evidence[]` · `ai_checked_scope`. T04.01은 검증된 객체(`AnalysisResult.to_fields()`)까지, 저장은 T04.02.
- **요약 문장 수:** 2~3문장을 요청하지만 검증은 3문장 이하만 본다. 제목만 있는 짧은 입력은 한 문장 요약이 자연스러워 하한을 두지 않는다. 문장부호 뒤 공백이 없어도 나눈다(`One.Two.`). 소수점·도메인처럼 뒤에 숫자·영문 소문자가 바로 붙으면 나누지 않는다(코드 리뷰 보완).
- **구조화 방식:** 프롬프트로 JSON만 요청하고 서버에서 Pydantic(정의 밖 필드 거부, 엄격한 타입)으로 검증한다. 코드 블록 표시 한 겹은 벗긴다. 실패는 `invalid_output`이며 자동 재시도하지 않는다. `response_format=json_object`는 2026-10-02 실제 호출에서 받아들여졌지만(`finish_reason=stop`) 기능은 이것에 의존하지 않는다.
- **근거 검증:** AI가 입력에서 그대로 옮긴 인용 `evidence` 1~3개를 내고, 서버가 공백을 정리한 뒤 실제로 보낸 입력에 들어 있는지 확인한다(8자 미만은 무효). 인용은 한 필드 안에 있어야 하고(필드 경계를 넘으면 무효), 자료 내용(제목·설명·본문) 인용이 하나 이상 있어야 한다. 저장 이유·메모만 인용하면 사용자 자신의 말이므로 `ungrounded_output`. 요약 자체의 사실 검증이 아니라 대리 지표다.
- **잘못된 값:** 형식 오류·허용 밖 중요도·근거 없음은 전체 실패. 목록에 없는(또는 비활성) 프로젝트, 목록 밖 종류는 해당 필드만 비우고 불확실한 점에 사유를 남긴다. 종류 목록: `article|document|note|reference|tool|other`.
- **보내는 것:** 제목·설명·본문·저장 이유·메모(값이 있는 것만), URL 문자열(열어 보지 않았다고 명시), 활성 프로젝트의 `id`·`name`. 사용자 최종 중요도·프로젝트는 보내지 않는다. 확인 범위는 서버가 계산한다(`fields`, `chars`, `url_fetched=false`).
- **호출 전 거부:** `ai_excluded` 자료(`ai_excluded`), 제목·설명·본문이 모두 빈 URL 전용 자료(`no_content`)는 Provider를 부르지 않는다.
- **오류 분류 추가:** `rate_limited`(429), `timeout`, `output_truncated`(`finish_reason=length`, 출력 한도 초과)를 기존 `provider_http_error`·`provider_connection_error`·`provider_incomplete_response`와 나눈다(T04.03 한도·대기 처리용). `ProviderError.request_sent`는 요청이 Provider에 나갔는지 알려 준다. 호출 전 거부(설정·도구 확인·`ai_excluded`·`no_content`)만 거짓이고, 검증 실패·연결 오류(도달 불확실)는 참으로 보아 사용량에 센다.
- **비활성 프로젝트:** 호출하는 쪽이 넘긴 목록에 `active=false`가 섞여도 Adapter가 빼고 보낸다.
- **보완 검토 후 남은 한계(T04.02 이후 처리):** ① 요약은 문장별 글자쌍 겹침으로만 대조하므로, 입력 단어로 뜻을 뒤집은 문장(예: '종료 계획이 없다')은 통과할 수 있다. 제목·중요 이유·권장 행동·핵심어·불확실한 점은 숫자 검사만 받는다. ② 검증 실패 응답의 토큰 사용량은 오류에 담기지 않는다(요청 수는 `request_sent`로 센다). ③ 기본 요청 시간이 60초라 PRD 초깃값 120초와 다르다(T04.03에서 설정 조정). ④ 본문 20,000자 입력 + 출력 1,500토큰에서 `output_truncated`가 나는지는 실제 긴 표본으로 확인하지 않았다. ⑤ 지시문 삽입이 정당한 근거와 같은 방향을 요구하면 구분할 수 없다.
- **책임 넷, 호출 하나:** `analyze_material`만 Provider를 부르고 `classify_material`·`suggest_importance`는 그 결과에서 꺼낸다. `answer_question`은 텍스트 호출을 그대로 전달하며 채팅 문맥은 T07.02.
- **지시문 삽입:** 자료는 JSON 문자열 값으로만 넣고 시스템 메시지에서 데이터로 고정한다. 완전히 막을 수는 없으므로 도구 비활성 확인·출력 검증·사용자 승인으로 피해를 막는다. 삽입 문장이 정당한 근거와 같은 방향(예: 중요도 높음)을 요구하면 구분할 수 없다.
- **문장 주장 검증(코드 리뷰 보완, 2026-10-02):** 인용만 맞으면 입력과 무관한 요약도 통과하던 문제를 고쳤다. ① 요약의 각 문장이 실제로 보낸 입력과 글자쌍 35% 이상을 공유해야 한다(측정: 실제 요약 문장 0.44~0.96, 무관한 주장 0~0.12, 뜻을 뒤집은 문장 0.29). ② 제목·요약·중요 이유·권장 행동에 입력에 없는 숫자(날짜·금액 등)가 있으면 거부한다. 둘 다 `ungrounded_output`이며 자동 재시도하지 않는다. ③ 중요 이유·권장 행동·제목·핵심어는 추론·조언이라 겹침 검사를 하지 않고, 결과의 `ai_grounding`(`unverified` 목록, `fact_checked=false`)으로 '사실 확인 안 됨'을 표시하게 한다. 화면 표시는 T04.02·T04.04에서 이 값을 쓴다.
- **검증 빈틈 보완(2차 코드 리뷰, 2026-10-02):** ① 글자쌍이 없는 요약 문장(`X.`·`??`)을 겹침 100%로 보던 것을 0으로 바꾸고, 요약은 문장부호·공백을 뺀 글자 10자 이상이어야 한다(`invalid_output`). ② 숫자 검사를 핵심어·불확실한 점까지 넓혔다(`2029 launch` 같은 핵심어 거부). ③ 같은 점검에서 찾은 것: 인용 8자 기준을 문장부호·공백을 뺀 글자로 세어 `--------` 같은 구분선 인용을 막고, 제목·중요 이유가 문장부호뿐이면 거부한다. 불확실한 점도 겹침 검사를 하지 않으므로 `ai_grounding.unverified`에 넣었다.

## T04.02 사용자 시작 분석·상태 조회·재시도 (2026-10-02, 착수 전 검토의 추천안으로 진행 지시)
- **응답 방식:** `POST /api/materials/{id}/analyze`는 원자적으로 `analyzing`으로 바꾸고 202를 준다. AI 호출은 같은 프로세스의 FastAPI 백그라운드 작업이 하며, 화면은 `GET /api/materials/{id}`를 3초 간격으로 조회한다. 창을 닫아도 결과는 저장된다. 기한 전 분석 중 자료에 새 키로 시작하면 409 `analysis_in_progress`.
- **버전 정책:** 분석 상태·결과는 저장소의 새 `transform`(원자적 조건부 쓰기, 버전 증가 없음)으로 쓴다. 시작할 때만 `expected_version`으로 사용자가 본 내용인지 확인한다. 작업이 끝날 때 내용 지문이 시작 때와 다르면 결과를 버리고 `awaiting_start` + `input_changed`. 늦게 끝난 작업은 작업 ID가 다르면 아무것도 쓰지 않는다.
- **입력 지문:** 보낼 내용(입력 필드 + URL) + 활성 프로젝트 `id`·`name` + `PROMPT_VERSION`. 모델명은 넣지 않는다. 완료된 같은 지문이면 200 `reused`이며 AI를 부르지 않는다. 결과가 지금 내용 기준인지는 내용 지문(`ai_content_hash`)만으로 비교해 `analysis_outdated`를 계산한다(조회마다 프로젝트를 읽지 않기 위해서).
- **상태:** `link_only`·`awaiting_start`·`analyzing`·`done`·`failed`. `quota_waiting`은 T04.03, '부분 확인'은 MVP 텍스트 한도(20,000자) 안에서 생기지 않아 쓰지 않는다. 완료 후 내용 수정은 상태를 `done`으로 두고 `analysis_outdated`로 알린다. 실패 후 내용 수정은 `awaiting_start`로 되돌린다.
- **결과 확인 필요:** `analysis_deadline_at` = 시작 + 요청 시간(`AI_TIMEOUT_SECONDS`) × 2. 지난 뒤 조회 때 `analysis_stale=true`. 자동 재호출은 없고, 이 상태와 `failed`에서 사용자가 같은 API에 새 키로 다시 시작한다.
- **시작 거부:** 휴지통 `trashed`, AI 분석 제외 `ai_excluded`, URL만 `no_content`(모두 409, AI 호출 없음). 검토 상태(미검토·나중에 보기·승인)와는 무관하다.
- **화면:** 받은 자료 상세와 검토 카드에 공통 분석 패널(`web/js/analysis.js`). 시작 전 보낼 항목·글자 수·요청 1회 안내 → 분석 중 조회 → 결과('AI 제안 · 사실 확인 안 됨', 근거 인용, 확인 범위) · 실패 사유 · 확인 필요 · 다시 분석. 사용량 숫자·남은 한도는 T04.03.
- **사용량 자리:** `analysis_request_sent`, `analysis_total_tokens`를 저장해 두고 집계는 T04.03에서 한다.
- **남은 한계:** ① 백그라운드 작업은 프로세스 안에서만 돌아 서버 재시작 시 사라진다(확인 필요로 복구). Render 무료 인스턴스가 잠들면 같은 일이 생긴다. ② 서버를 끈 시점에 이미 Hermes로 나간 요청은 사용량에 잡히지 않는다(작업이 사라져 기록할 곳이 없음). ③ 사용자 최종값이 없을 때 AI 제안을 화면 기본값으로 쓸지는 T04.04에서 정한다.
- **분석 중 AI 분석 제외(코드 리뷰 보완, 2026-10-02):** 결과 저장 직전 비교하는 내용 지문에 `ai_excluded`가 없어, 분석 중 제외를 켜도 결과가 저장될 수 있었다. 저장 직전에 현재 `ai_excluded`를 따로 확인해 켜져 있으면 결과를 버리고 `awaiting_start` + `analysis_error=ai_excluded`로 둔다. 이미 Provider로 나간 요청은 되돌릴 수 없으므로 `analysis_request_sent`만 남긴다. 제외를 지문에 넣지 않은 이유: 제외를 껐다 켜는 것만으로 '내용 변경'이나 재분석 대상이 되면 안 되기 때문이다. 분석 중 휴지통 이동은 결과를 저장하지만 휴지통 자료는 화면·채팅 대상이 아니라 그대로 둔다.

## T04.03 AI 사용량·한도·전송 범위 표시 (2026-10-02, 착수 전 검토의 추천안으로 진행 지시)
- **집계 단위:** 소유자 전체(개인·표본 합산), 서울 날짜. 표본 시연도 같은 Hermes 구독을 실제로 쓰기 때문이다. 기록은 `ai_usage/{sha256(소유자·날짜)}` 한 문서(`used`·`failed_sent`·`analysis_count`·`chat_count`·`total_tokens`·`refunded`). 모드 격리 저장소 밖의 소유자 단위 메서드(`read_usage`·`change_usage`, 원자적)로 읽고 쓴다. 클라이언트 접근은 기존 전면 거부 규칙에 포함된다.
- **예약 방식:** 분석 시작(202 전)에 `used < limit`이면 1을 원자적으로 차감한다. 작업이 끝나면 `request_sent=false`만 환불하고, 보낸 요청은 실패·429·시간 초과도 사용으로 남긴다. 서버가 죽어 결과를 모르는 요청은 실제로 나갔을 수 있어 사용으로 남긴다(한도를 넘지 않는 쪽). 환불·결과 기록은 예약한 날짜의 기록에 한다.
- **한도 도달:** 200 `quota_waiting`, 자료는 `analysis_status=quota_waiting`. Provider 429도 `quota_waiting` + `rate_limited`. 날짜가 바뀌어도 자동 호출하지 않고, 사용자가 '다시 시작'할 때만 다시 예약한다. 분석 중·재사용·거부는 예약 전에 걸러 사용량을 쓰지 않는다.
- **표시:** `GET /api/ai/usage`(PRD 외 추가). 분석 확인 상자에 '오늘 AI 요청 37/50 · 남은 요청 13 · 한도 대기 자료 42건 · 비용: 구독 경로, 금액 미확인'. 한도에 도달했으면 버튼이 '한도 대기로 남기기'로 바뀐다. 채팅 입력 영역 표시는 T07에서 같은 API를 쓴다.
- **설정:** 요청 시간 코드 기본값을 120초로 맞췄다(PRD 초깃값, `.env`는 이미 120). 출력 1,500토큰은 요청 1회의 출력 상한으로 해석한다(하루 총량이 아님).
- **세지 않는 호출:** Hermes 도구 확인(`/toolsets`, 모델 호출 아님), 수동 스모크 스크립트(`smoke_*.py`).
- **남은 한계:** ① 대기 자료 수는 100건까지만 센다. ② 여러 자료를 한 번에 시작하는 묶음 분석 UI는 아직 없다(요청 1회 = 자료 1건). ③ 사용량 기록은 Firestore 문서 하나에 몰리므로 초당 수십 건 이상의 동시 예약에서는 트랜잭션 재시도가 늘 수 있다(개인용 MVP 규모에서는 문제없음).
- **검증 실패 응답의 토큰(코드 리뷰 보완, 2026-10-02):** 응답이 도착한 뒤 형식·근거 검증에 실패하면 Adapter가 오류만 던져 그 응답의 `total_tokens`가 버려졌다. `ProviderError.total_tokens`에 응답의 토큰 수를 담고(Adapter의 검증 단계를 `_validate`로 분리해 한곳에서 붙임), 분석 작업이 정산과 `analysis_total_tokens`에 그대로 넘긴다. 연결 오류·시간 초과처럼 응답 자체가 없으면 토큰은 알 수 없어 더하지 않는다.

## T04.04 오늘·AI 동향·중요도 수정 화면 (2026-10-02, 착수 전 검토의 추천안으로 진행 지시)
- **최종 중요도:** 사용자 값(`user_importance`), 없으면 AI 제안(`ai_importance`). AI 값은 분석 완료(`done`)이고 결과 뒤에 내용을 고치지 않았을 때(`analysis_outdated=false`)만 쓴다. 화면은 출처를 '내가 정함' / 'AI 제안'으로 붙인다. 둘 다 없으면 판단 보류. 사용자가 일부러 판단 보류로 둔 것과 아직 고르지 않은 것은 구분하지 못한다(둘 다 null, MVP 한계).
- **대응 필요:** AI 출력에 `needs_action`(bool, 필수)을 더했다. 기한·변경·종료·요청처럼 사용자가 해야 할 일이 적혀 있으면 참이며, 참이면 권장 행동이 있어야 한다(없으면 `invalid_output`). 기존 근거 검증을 그대로 받는다. 출력 계약 변경으로 `PROMPT_VERSION`을 2026-10-02.2로 올렸다(기존 결과는 재분석 대상이 되지만 자동 호출은 없다). 이전 결과에는 값이 없어 '대응 여부 미확인'으로 표시하고 학습 자료 묶음에 둔다.
- **정렬:** `GET /api/materials/priority`(PRD 외 추가)가 현재 모드의 자료를 최대 500건 읽어 Python에서 정렬한다(최종 중요도 → 대응 필요 → 최신 접수 → ID). 활성 자료만, 휴지통 제외. 기존 `owner_id·mode·created_at` 색인으로 읽어 새 색인이 필요 없다.
- **화면 대상:** 휴지통을 뺀 활성 자료 모두. 미승인은 '검토 대기', 나중에 보기·AI 분석 제외·보관됨도 표시한다. AI 분석 제외 자료도 사용자가 정한 중요도가 있으면 포함한다(화면 표시는 AI 전송이 아니다).
- **오늘(S01):** 같은 정렬에서 높음·보통만 최대 3건, 각 건의 이유(사용자가 정했으면 저장 이유 우선, 아니면 AI 중요 이유), 검토 대기·보관 수. 자료가 없으면 빈 상태, 높음·보통이 없으면 판단 보류 수와 AI 동향 안내.
- **AI 동향(S04):** 대응 필요 / 학습 자료(미확인 포함) / 판단 보류 세 묶음. 카드에서 '내 중요도'를 고르면 `PUT user_importance` 후 서버 순서로 다시 그린다. AI 제안은 그대로 둔다.
- **검토 카드(A02):** 중요도 선택 옆에 'AI 제안 중요도: 높음 — 이유'와 '제안 적용'. 자동으로 채우지 않으며, 적용하거나 직접 고른 값만 승인 때 저장된다.
- **문구:** 외부 인기 숫자·관련성 점수, '개인 브리핑'처럼 예약 작업이 실행된 듯한 문구를 쓰지 않는다. AI 요약은 '사실 확인 안 됨'을 붙인다.
- **코드 리뷰 보완(2026-10-02):** ① 우선순위 조회가 오래된 순으로 읽어, 500건을 넘으면 최신 자료가 비교에서 빠질 수 있었다. 최신 접수부터 읽도록 바꿨다(기존 `owner_id·mode·created_at DESC` 색인 사용). ② `PROMPT_VERSION`을 올렸지만 화면은 내용이 바뀐 경우에만 재분석 버튼을 보여, 이전 기준의 결과를 다시 분석할 방법이 없었다. 완료 시 `analysis_prompt_version`을 저장하고, 조회 때 `analysis_prompt_outdated`(버전이 다르거나 없음)를 계산한다. 화면은 '분석 완료 · 다시 분석 가능'과 이유를 보여주고 '다시 분석'으로 사용자가 시작한다. 결과는 계속 쓰고 자동 호출은 없다. 재사용 조건에도 프롬프트 버전 일치를 명시했다.

## T05.01 보관함 검색·필터·페이지네이션 (2026-10-02, "task 05.01 진행" 지시 — 착수 전 결정을 기본값으로 정함)
- **대상:** 현재 모드의 보관 완료 자료(`is_kept`). 미승인·나중에 보기·휴지통 제외(PRD S03 '승인·보관 완료 자료').
- **필드:** 사용자가 제공한 제목·설명·본문·저장 이유·메모·URL. 명세의 '제목·설명·입력/추출 본문·메모'에 저장 이유와 URL을 더했다(사용자 입력이므로). AI 결과(요약·핵심어)는 사실 확인 전 제안이라 검색하지 않는다. 추출 본문은 MVP에 없다(확장 단계 파일).
- **일치:** 공백으로 나눈 검색어가 모두 있어야 한다(AND). NFC 정규화·대소문자 무시·부분 일치(한글 형태소 분석 없음). 결과는 최신 접수 → ID 순이며 관련도 순위는 없다.
- **필터:** 기간은 접수일의 서울 날짜(양 끝 포함), 종류는 AI 종류(`ai_kind`)와 원본 종류(`source_type`)를 따로, 프로젝트는 주·관련 모두(Open Decision 1).
- **검색 전략:** Firestore Standard(전문 검색 없음, `asia-northeast3`). 2026-10-02 실제 자료량은 소유자 기준 표본 모드 보관 51건·개인 0건이다. 최신 접수부터 최대 1,000건을 읽어 Python에서 거르고, 일치 결과를 20건(최대 50건)씩 나눠 준다. 응답의 `scope`로 검색 범위와 한도 초과(`truncated`)를 알리고 화면에도 표시한다. 자료가 수천 건을 넘으면 미리 만든 키워드 색인이나 Enterprise 텍스트 검색으로 바꾼다.
- **페이지:** 커서는 검색어·필터 지문 + 결과 위치다. 다른 조건의 커서는 422. 페이지 사이에 자료가 바뀌면 위치가 어긋날 수 있다(MVP 한계).
- **오류:** 저장소 오류를 결과 0건으로 바꾸지 않고 5xx로 올린다. 화면은 목록을 비우지 않고 '검색하지 못했습니다'와 공통 오류 안내를 보여준다.
- **화면(S03):** 검색어·기간·종류·링크/텍스트·프로젝트 필터, 일치한 필드와 문맥, 범위 문구, 더 보기, 상세(URL·설명·본문·저장 이유 읽기, 메모 수정, 분석 패널). 관련 자료 연결은 T05.02, 휴지통 탭은 T05.03.
- **코드 리뷰 보완(2026-10-02):** ① '더 보기'를 응답 전에 여러 번 누르면 같은 커서로 요청이 여러 번 나가 목록이 겹칠 수 있었다. 검색·더 보기를 기존 `single-flight`로 묶어 요청 중에는 두 버튼을 끄고 추가 클릭을 무시하며, 이어 붙일 때도 ID로 중복을 거른다(`mergePage`). ② 메모를 고쳐도 결과를 다시 계산하지 않아, 메모로 걸린 자료가 메모를 지운 뒤에도 남았다. 메모 저장 후 **마지막으로 검색한 조건**(폼에 입력만 하고 검색하지 않은 값이 아니라)으로 다시 검색한다.
