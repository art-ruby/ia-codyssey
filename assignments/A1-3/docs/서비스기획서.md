## 2. 목적과 배경

LAPIS는 B1-2 과제에서 만든 프리미엄 오 드 퍼퓸 브랜드다. 브랜드 홈페이지는 이미 6개 섹션의 원페이지로 완성되어 있지만, **방문자가 할 수 있는 일이 "읽는 것"뿐**이다. 향수는 직접 맡아보기 전에는 고르기 어려운 제품인데, 온라인에서는 그 시도조차 할 수 없다.

이 과제에서는 여기에 **AI 향 큐레이터**를 더한다. 방문자가 자기 상황과 기분을 입력하면 그에 어울리는 향의 3층 구성(Top / Heart / Base)과 브랜드 톤의 카피를 생성해 보여준다.

**목적 두 가지**

1. **사용자 관점** — 향을 맡을 수 없는 웹에서, 자신의 언어로 향을 탐색해 보는 경험을 제공한다.
2. **브랜드 관점** — "읽고 나가는" 페이지를 "한 번 해보고 나가는" 페이지로 바꾼다.

**과제 학습 목표와의 연결**

| 과제 목표 | 이 서비스에서 다루는 부분 |
|---|---|
| HTML/CSS/JS 역할 구분 | 인라인 CSS·JS를 `css/`, `js/` 로 분리 (§6.1) |
| 입력 → fetch → 화면 반영 흐름 | §6.2 데이터 흐름 |
| Serverless Functions 구조 | `api/curate.py` (§6.2, §6.3) |
| 환경 변수로 키 관리 | §11 |
| 로컬과 배포 환경의 차이 | §10 검증 방법 |
| 오류 원인 파악과 수정 | §7 실패 처리 — 503 대응이 이 서비스의 핵심 설계 과제 |

## 3. 타겟 사용자

B1-2에서 정의한 브랜드 타겟을 그대로 승계한다.

- **주 타겟** — 절제된 고급감과 조용한 존재감을 선호하는 20대 후반–30대 초반 여성
- **성향** — 화려한 광고보다 무드와 디테일로 설득되는 소비층. 브랜드 스토리를 소비 근거로 삼는다
- **유입 경로 가정** — SNS를 통한 모바일 유입이 다수. 따라서 반응형 우선순위는 **mobile → desktop**

**큐레이터 섹션에서의 사용자 상태**

이 섹션에 도달한 방문자는 이미 Hero → Brand Story → Notes를 스크롤해 노트 구성이 무엇인지 읽은 상태다. 큐레이터는 "탑·하트·베이스가 무엇인지 읽었으니, 이제 당신의 조합을 찾아보세요"라는 맥락 위에서 동작한다. 이 위치 선정이 §4의 근거다.

## 4. 페이지(섹션) 구성과 네비게이션

원페이지 스크롤 구조를 유지하고, 기존 6섹션에 큐레이터 1섹션을 더해 **총 7섹션**으로 만든다. 과제 요구사항인 "최소 3개 이상의 페이지 또는 섹션"을 충족한다.

| # | 섹션 | 앵커 | 내용 | 상태 |
|---|---|---|---|---|
| 01 | Hero | `#hero` | 브랜드명, 태그라인, CTA | 기존 |
| 02 | Brand Story | `#story` | 왜 라피스인가 + 추상 패널 | 기존 |
| 03 | Notes | `#notes` | Top / Heart / Base 3카드 | 기존 |
| 04 | **Curator** | `#curator` | **AI 향 큐레이션** | **신규** |
| 05 | Collection | `#collection` | LAPIS / LUNA 라인업 | 기존 |
| 06 | Philosophy | `#philosophy` | 헤리티지·장인정신·지속가능성 | 기존 |
| 07 | Contact | `#contact` | 뉴스레터 구독 + 푸터 | 기존 |

**네비게이션**

- 상단 고정 내비게이션에서 각 섹션 앵커로 스무스 스크롤
- 820px 미만에서는 메뉴 아이콘으로 축소되고 오버레이로 펼쳐짐 (기존 동작 유지)
- 내비게이션에 `큐레이터` 항목 1개를 추가한다

**큐레이터를 별도 페이지로 분리하지 않은 이유**

별도 페이지(`curator.html`)의 실질적 이점은 결과에 고유 공유 URL을 붙일 수 있다는 점인데, 이번 범위에는 결과를 저장하는 저장소가 없어 그 이점이 실현되지 않는다. 반면 원페이지 섹션으로 두면 기존의 검증된 반응형 4구간·스크롤 모션 설계를 그대로 상속받고, 내비게이션·폰트·토큰을 두 파일에 중복 관리하지 않아도 된다.

## 5. 핵심 기능 — AI 향 큐레이터

### 5.1 입력

**선택형 3항목 + 자유입력 1항목**의 하이브리드 구조다.

| 항목 | 필수 | 형태 | 값 |
|---|---|---|---|
| 계절 | 필수 | 단일 선택 | `spring` / `summer` / `autumn` / `winter` |
| 시간대 | 필수 | 단일 선택 | `day` / `dusk` / `night` |
| 무드 | 필수 | 단일 선택 | `calm` / `bold` / `warm` |
| 순간 | 필수 | 자유 텍스트 (1–120자) | 예: "퇴근길 지하철에서 창밖을 볼 때" |

선택형만으로 가면 결과가 몇 가지 조합으로 수렴해 AI가 없어도 되는 기능처럼 보인다. 자유입력만으로 가면 입력이 막연할 때 출력 품질 편차가 커진다. 둘을 섞어 프롬프트의 뼈대는 선택형이 잡고, 개인화는 자유입력이 담당한다.

선택형 3항목에는 기본값을 두지 않는다. 사용자가 직접 고른 값이어야 결과에 대한 납득이 생긴다.

### 5.2 출력

향 하나를 구성해 카드 형태로 보여준다.

| 필드 | 내용 |
|---|---|
| `name` | 향 이름 (영문) — 예: "Quiet Amber" |
| `name_kr` | 향 이름 (국문) — 예: "조용한 앰버" |
| `copy` | 브랜드 톤의 한 줄 카피 |
| `notes.top` | 원료 목록 + 설명 — 첫인상 |
| `notes.heart` | 원료 목록 + 설명 — 중심 |
| `notes.base` | 원료 목록 + 설명 — 잔향 |
| `scene` | 착용 씬 한 줄 |

영문명과 국문명을 모두 둔다. 영문명은 향수 제품명의 관례이고, 국문명은 의미 전달을 맡는다.

**화면 배치** — 입력 폼 아래로 결과가 펼쳐지는 세로 스택. 결과의 3층 노트는 데스크톱에서 가로 3카드로 배치되어 03 Notes 섹션의 3카드 그리드와 같은 리듬을 갖는다. 모바일에서는 1열로 스택된다.

### 5.3 사용자에게 제공하는 가치

- **탐색의 시작점** — 향수 카테고리를 모르는 사람도 "가을 / 해질녘 / 차분한 / 퇴근길"이라는 자기 언어로 진입할 수 있다
- **브랜드 언어의 학습** — 결과가 Top/Heart/Base 구조로 나오므로, 03 Notes에서 읽은 개념을 자기 사례로 다시 확인하게 된다
- **개인화된 결과물** — 같은 선택지를 골라도 자유입력이 다르면 다른 결과가 나온다

### 6.3 API 계약

**엔드포인트** — `POST /api/curate`

`GET` + 쿼리스트링을 쓰지 않는다. 사용자가 쓴 문장이 URL·서버 접근 로그·브라우저 히스토리에 남지 않게 한다.

**요청**

```json
{
  "season": "autumn",
  "time": "dusk",
  "mood": "calm",
  "moment": "퇴근길 지하철에서 창밖을 볼 때"
}
```

**성공 응답 (200)**

```json
{
  "name": "Quiet Amber",
  "name_kr": "조용한 앰버",
  "copy": "해가 넘어간 뒤에도 방 안에 남는, 말수 적은 온기.",
  "notes": {
    "top":   { "materials": ["베르가못", "핑크페퍼"], "description": "첫 10분, 서늘하게 문을 여는 인상" },
    "heart": { "materials": ["아이리스", "제비꽃"],   "description": "체온에 닿아 부드러워지는 중심" },
    "base":  { "materials": ["앰버", "샌달우드"],     "description": "떠난 뒤에 남는 잔향" }
  },
  "scene": "해질녘, 불을 켜지 않은 거실",
  "attempts": 1
}
```

`attempts` 는 성공까지 걸린 시도 횟수다. 과제 보고서에서 재시도 정책의 효과를 수치로 제시하는 근거로 쓴다.

**실패 응답**

형태를 하나로 통일해 프론트 분기를 단순하게 유지한다.

```json
{ "error": { "code": "EMPTY_INPUT", "message": "닿고 싶은 순간을 한 줄 남겨 주세요." } }
```

| `code` | HTTP | 발생 조건 |
|---|---|---|
| `EMPTY_INPUT` | 400 | 필수값 누락 (서버 재검증에서 걸린 경우) |
| `INVALID_INPUT` | 400 | 화이트리스트 위반 또는 `moment` 길이 초과 |
| `MODEL_UNAVAILABLE` | 503 | Gemini 503/429/타임아웃으로 3회 모두 실패 |
| `INVALID_RESPONSE` | 502 | 스키마 검증을 3회 모두 통과하지 못함 |
| `SERVICE_UNAVAILABLE` | 500 | 키 미설정·인증 실패 등 운영자 조치가 필요한 상태 |

**보안 설계 두 가지**

- **서버에서 다시 검증한다.** 클라이언트 검증은 우회할 수 있다. `season`·`time`·`mood` 는 화이트리스트로, `moment` 는 길이 상한으로 서버에서 재검증해 프롬프트 남용과 토큰 비용 폭주를 막는다.
- **모델 출력을 `innerHTML` 로 넣지 않는다.** 생성된 문자열은 모두 `textContent` 로 렌더한다. 모델 출력을 그대로 DOM에 삽입하면 XSS 경로가 된다.

## 7. 실패 처리 기준

### 7.1 재시도 정책

**배경** — a1-2의 Gemini 호출에는 재시도도 타임아웃도 없어(`travel_planner.py:125`, `:347`), 일시적인 `503 UNAVAILABLE`(모델 과부하) 한 번에 실행 전체가 중단된다. 실제로 재현되는 문제이며, 이번 서비스의 가장 중요한 실패 처리 대상이다.

**총 예산 기반 재시도**

```text
서버 총 예산 25초 · 최대 3회 시도
  시도 1 → 실패 → 0.5초 대기 (+지터)
  시도 2 → 실패 → 2.0초 대기 (+지터)
  시도 3 → 실패 → 에러 응답

각 시도의 타임아웃 = min(12초, 남은 예산)
남은 예산 < 3초면 더 시도하지 않고 즉시 타임아웃 응답
```

횟수만 늘리면 최악의 경우 지연이 3배가 된다. 횟수와 총 예산을 함께 걸어 상한을 고정한다.

백오프 첫 간격을 0.5초로 둔 것은 스키마 위반처럼 즉시 재시도해도 되는 경우를 위해서고, 두 번째를 2초로 벌린 것은 503이 스파이크성이기 때문이다. 너무 빨리 재시도하면 같은 과부하에 그대로 부딪힌다.

**모든 오류를 재시도하지 않는다**

| 상황 | 재시도 | 근거 |
|---|---|---|
| 503 (모델 과부하) | O | 대부분 일시적. 재시도가 가장 잘 듣는 케이스 |
| 429 (호출 한도) | O | 백오프 후 풀릴 수 있음 |
| 네트워크 오류·타임아웃 | O | 일시적 |
| 스키마 위반·JSON 파싱 실패 | O | 같은 프롬프트로도 다음 응답은 통과할 수 있음 |
| 401 / 403 (인증 실패) | **X** | 3번 더 시도해도 같은 결과. 지연만 3배가 된다 |
| 400 (요청 형식 오류) | **X** | 우리 코드의 버그. 재시도로 가려지면 안 된다 |

키가 잘못된 상태에서 사용자를 25초 기다리게 하는 것이 가장 나쁜 시나리오다. 이 구분이 재시도 횟수보다 중요하다.

**3회차는 대체 모델로 전환한다.** 과부하는 특정 모델에 몰리는 현상이므로, 같은 모델을 세 번 두드리는 것보다 마지막 한 번을 다른 모델로 돌리는 편이 성공률이 높다. 기본 모델은 a1-2에서 검증된 값을 사용한다. 대체 모델 ID는 §12의 열린 항목이다.

**타임아웃 예산**

| 구간 | 값 |
|---|---|
| 시도 1회당 상한 | 12초 |
| 서버 총 예산 | 25초 |
| 함수 `maxDuration` | 서버 예산 + 마진 (§12) |
| 클라이언트 `AbortController` | 30초 |

클라이언트 중단 시간은 서버 예산보다 **길어야** 한다. 짧으면 서버가 2회차에서 성공했는데 화면에는 이미 타임아웃이 떠 있는 상황이 된다.

### 7.2 상태별 화면

과제 요구사항은 "빈 입력 / API 오류 / 지연" 중 최소 1개에 대한 안내인데, 세 가지를 모두 다룬다.

| 상태 | 화면 | 설계 근거 |
|---|---|---|
| **① 빈 입력** | 자유입력 밑줄이 에러 색으로 바뀌고 아래 인라인 안내. 포커스가 입력으로 이동 | **fetch를 보내지 않는다.** 서버·토큰을 쓰지 않고 즉시 안내한다 |
| **② 대기 0–6초** | 결과 자리에 스켈레톤. 문구 "당신의 노트를 고르는 중". 제출 버튼 비활성 | 스켈레톤을 미리 깔아 결과 도착 시 레이아웃이 밀리지 않게 한다. 버튼 비활성으로 중복 제출을 막는다 |
| **③ 대기 6초 이후** | 문구만 "조금 더 걸리고 있습니다"로 교체 | 재시도는 서버 안에서 일어난다. "재시도 2/3" 같은 내부 사정은 노출하지 않는다 — 사용자에게 의미가 없고 불안만 만든다 |
| **④ 대기 15초 이후** | 문구만 "거의 다 왔습니다"로 교체 | 30초를 스피너 하나로 버티게 하면 고장으로 받아들인다 |
| **⑤ 3회 모두 실패** | "지금은 향을 고르지 못했습니다 / 향을 짓는 곳이 잠시 붐비고 있습니다" + **다시 시도** 버튼 + 코드 표기 | 입력값을 보존해 다시 입력하지 않아도 되게 한다. **가짜 결과로 대체하지 않는다** — 그럴듯한 폴백은 AI가 동작한 것처럼 보이게 만들어 사실과 달라진다 |
| **⑥ 키 오류 (401/403)** | "지금은 큐레이터를 이용할 수 없습니다 / 잠시 후 다시 방문해 주세요" — **재시도 버튼 없음** | 몇 번을 눌러도 같은 결과인 버튼을 보여주지 않는다 |

**화면에 기술 원인을 쓰지 않는다.** "API 키" 같은 표현은 사용자에게 의미가 없고 시스템 내부를 노출한다. 상세 원인은 서버 로그에만 남긴다.

**색** — 에러 표시는 디자인 토큰 `--state-error #B5654F` 를 쓴다. 경고용 빨강이 아니라 LAPIS 팔레트 안의 낮은 채도 테라코타라 브랜드 톤을 깨지 않으면서 구분된다.

## 8. 반응형과 접근성

### 8.1 반응형

브레이크포인트는 기존 4구간을 상속한다 — mobile(<600) / tablet(600–1023) / desktop(1024–1439) / wide(≥1440).

큐레이터 섹션에만 규칙을 추가한다.

| 요소 | 모바일 | 데스크톱 |
|---|---|---|
| 칩 3줄 | 라벨 위 / 칩 아래로 줄바꿈 | 라벨 + 칩 한 줄 |
| 칩 터치 타겟 | **최소 44×44px** | 기본 패딩 |
| 결과 3층 노트 | 1열 세로 스택 | 3열 그리드 |
| 자유입력 | 폭 100% | 폭 100% |

칩 터치 타겟이 실질적 함정이다. 데스크톱 기준 패딩 그대로면 모바일에서 손가락으로 누르기 어렵다.

**확인 기준** — 과제 요구사항이 "최소 2가지 화면 크기"이므로 **375px(모바일) / 1280px(데스크톱)** 을 기준으로 하고, 배포 후 실제 휴대폰에서도 확인한다.

### 8.2 접근성

동적으로 결과가 생성되는 섹션이라 정적 페이지보다 위험이 크다.

- **칩은 `<input type="radio">` + `<label>` 로 구현한다.** `div` 에 클릭 핸들러만 붙이면 키보드로 접근할 수 없고 스크린리더에 선택 그룹으로 읽히지 않는다.
- **결과·에러 영역에 `aria-live="polite"` 를 건다.** 버튼을 눌러 화면이 바뀌었는데 알림이 없으면 스크린리더 사용자는 아무 일도 일어나지 않은 것으로 인식한다.
- **전체를 `<form>` 으로 감싼다.** Enter 키로 제출된다.
- **`prefers-reduced-motion` 대응** — 스켈레톤 셰이머와 결과 fade-up을 끈다. 디자인 시스템 하드룰이며 `tokens.css` 하단에 대응 블록이 이미 있다.
- 모든 이미지에 무드를 담은 `alt` 를 단다 (디자인 시스템 하드룰 7).

## 9. UX 보너스

보너스 과제의 배움 포인트가 "사용성 개선과 **개선 효과를 확인하는 방법**을 함께 설계"이므로, 개선과 측정을 한 쌍으로 넣는다.

**마이크로 인터랙션**

- 칩 선택 시 골드 언더라인 전환
- 결과 3카드 순차 등장 (stagger)
- 대기 중 스켈레톤 셰이머

모두 브랜드 모션 규칙을 따른다 — `--ease-out` / `--ease-in-out` 만 사용하고 바운스·스프링 이징은 쓰지 않는다 (디자인 시스템 하드룰 3).

Vercel Analytics를 붙인다. 쿠키를 쓰지 않아 동의 배너가 필요 없다. 측정 항목은 둘로 좁힌다.

- 큐레이터 섹션까지 스크롤 도달한 비율
- 제출 후 이탈률

**다크 모드는 제외한다.** LAPIS는 이미 다크 팔레트가 기본이라 토글을 붙여도 의미 있는 변화가 없다.

## 10. 검증 방법

### 10.1 로컬

`vercel dev` 로 정적 파일과 Python 함수를 함께 띄운다. 스크립트를 직접 실행하는 방식과 달리 프론트의 `fetch('/api/curate')` 가 실제로 라우팅되는지까지 확인된다.

### 10.2 자동 테스트

Gemini 호출과 판단 로직을 분리한다. 한 덩어리로 두면 테스트할 때마다 Gemini를 불러야 하는데, 그 Gemini가 지금 503을 뱉고 있다.

| 순수 함수 | 테스트 내용 |
|---|---|
| `validate_request(body)` | 화이트리스트 위반, `moment` 빈 값·121자 초과 |
| `should_retry(status)` | 503·429 → True / 401·403·400 → False |
| `next_delay(attempt)` | 0.5초 → 2.0초 백오프 |
| `validate_response(data)` | 필드 누락, `notes` 3층 구조 위반 |

이 넷은 네트워크 없이 pytest로 돌아간다. Gemini 호출부는 얇은 껍데기로 남겨 통합 확인 때만 쓴다.

`pytest` 는 `requirements.txt` 에 넣지 않는다. 그 파일은 Vercel이 함수를 빌드할 때 설치하는 목록이라, 테스트 도구가 배포 환경에 들어갈 이유가 없다. 개발용 의존성은 `requirements-dev.txt` 로 분리한다.

### 10.3 실패 경로 수동 확인

자동 테스트로 덮이지 않는 화면 동작이다.

| 확인 항목 | 방법 | 기대 결과 |
|---|---|---|
| 빈 입력 | 자유입력을 비우고 제출 | 개발자도구 네트워크 탭에 **요청이 잡히지 않는다** |
| 키 오류 | 로컬 `.env` 의 키를 일부러 틀리게 | ⑥번 화면 (재시도 버튼 없음) |
| 지연 | 인위적 지연 주입 | 6초·15초 문구가 실제로 교체된다 |
| 503 | 자연 발생 대기 또는 모킹 | ⑤번 화면 + `MODEL_UNAVAILABLE` |

### 10.4 배포 후 체크리스트

- 7섹션 네비게이션 이동
- 375px / 1280px 레이아웃
- AI 기능 입력 → 결과 출력
- 실패 안내가 배포본에서 실제로 노출됨

### 10.5 증빙 자료

**스크린샷** — B1-2의 `capture-homepage.cjs`(Playwright)를 `scripts/capture.cjs` 로 복사해 셋을 바꾼다.

1. URL을 Vercel 배포 주소로
2. 섹션 목록에 `curator` 추가, **뷰포트 1440 / 375 두 벌**로 반복
3. AI 동작 장면 — 칩 클릭 → 자유입력 → 제출 → 결과 대기 → 캡처. 로딩·에러 화면도 같은 방식으로 남긴다

**AI 코딩 도구 사용 과정** — B1-2의 `PRODUCTION_LOG.md` 기록 방식을 이어간다. 설계 단계의 판단(원페이지 섹션 채택, 재시도 3회 결정, 키 오류 시 재시도 버튼 숨김)이 그대로 증빙이 된다.

## 11. 배포와 환경 변수

**Vercel 설정**

| 항목 | 값 |
|---|---|
| 연동 저장소 | `art-ruby/ia-codyssey` |
| Root Directory | `assignments/a1-3` |
| Framework Preset | Other (프레임워크 없음) |
| 함수 | `api/*.py` 가 자동으로 서버리스 함수가 됨 |
| 의존성 | `requirements.txt` |

**환경 변수**

| 이름 | 위치 | 비고 |
|---|---|---|
| `GEMINI_API_KEY` | Vercel 프로젝트 환경 변수 + 로컬 `.env` | 저장소에 커밋하지 않는다 |

- `.env` 는 `.gitignore` 에 등록하고, 저장소에는 값이 빈 `.env.example` 만 둔다
- 키는 `os.getenv()` 로만 읽는다. 코드에 직접 쓰지 않는다
- **화면 캡처에 `.env` 파일을 띄우지 않는다.** 값을 색으로 덮어도 편집기의 미니맵·탭 미리보기에 축소 렌더링되어 남을 수 있다. 증빙이 필요하면 `.env.example` 과 `.gitignore` 를 대신 캡처한다
- 키가 유출되면 파일을 지워도 커밋 기록에 남는다. 발급처에서 즉시 폐기하고 재발급한다

이 원칙은 a1-2의 README에 정리된 내용을 그대로 따른다.

## 12. 열린 항목

구현 단계에서 확인해 확정한다. 추정으로 코드에 박지 않는다.

| 항목 | 상태 | 결과 |
|---|---|---|
| 기본 모델 ID | **확정** | `gemini-3.5-flash` — a1-2에서 검증된 값. 실측 응답 6.5초 |
| 대체 모델 ID (재시도 3회차용) | **확정** | `gemini-3.5-flash-lite` — 아래 §12.1 |
| `python-dotenv` 포함 여부 | **확정** | 넣지 않는다. `requirements.txt` 는 `google-genai` 하나. 테스트는 `.env` 를 직접 읽고, 배포 환경은 Vercel이 환경 변수를 주입한다 |
| 함수 `maxDuration` 상한 | **미확정** | `vercel.json` 에 30초로 두고 배포 로그에서 플랜 한도를 확인한다 (§11) |

### 12.1 대체 모델 후보 검증 기록

`client.models.list()` 로 `generateContent` 지원 모델 37개를 받은 뒤, 실제 프롬프트와 `responseSchema` 로 후보를 직접 호출해 골랐다.

| 모델 | 결과 | 응답 시간 |
|---|---|---|
| `gemini-3.5-flash` (기본) | 성공 | 6.53초 |
| `gemini-2.5-flash` | **404 NOT_FOUND — 더 이상 제공되지 않음** | — |
| `gemini-3.5-flash-lite` | 성공 | **2.22초** |
| `gemini-3.7-flash` | 성공 | 4.17초 |

**목록에 나오는 모델이라고 호출되는 것은 아니다.** `gemini-2.5-flash` 는 `models.list()` 에 포함되지만 호출하면 404를 돌려준다. 목록만 보고 골랐다면 폴백 경로가 죽은 채로 배포됐을 것이고, 이 결함은 정상 경로에서는 드러나지 않는다 — 503이 두 번 연속 터진 3회차에만 나타난다.

`gemini-3.5-flash-lite` 를 고른 이유는 두 가지다. 예산이 거의 소진된 마지막 시도에서 3배 빠르고, lite 계열은 처리량 위주로 배정되어 수요 스파이크에 덜 걸린다. `gemini-3.7-flash` 는 세대가 달라 용량 독립성이 더 나을 수 있으나 응답이 두 배 느리다.
