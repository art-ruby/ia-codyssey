## 평가 기준 1: 업무 과업 정의 ✅ Pass

### 과업 설명

타겟 사용자는 **1인 창업자**, **AI 콘텐츠 제작자**, **기술 블로그 운영자**다.  
이 사용자는 최신 AI 도구 뉴스를 빠르게 블로그 콘텐츠로 바꾸되, 과장 표현과 환각을 줄이고 게시 가능한 HTML까지 한 번에 얻고 싶어 한다.

### 입력 규격

| 필드 | 설명 |
|---|---|
| 기사 제목 | 원문 제목 |
| 기사 본문 | 뉴스 원문 전체 |
| 원문 URL | 링크 또는 출처명 |
| 출처명 | 발행처 |
| 작성일 또는 확인일 | 날짜 |
| 타겟 독자 | 독자층 정의 |
| 콘텐츠 목적 | 정보 제공 / 비교 분석 / 튜토리얼 등 |
| 확인된 사실 | 공식 출처로 검증된 항목 |
| 확인이 필요한 주장 | 기사 내 미검증 주장 |

### 출력 규격

| 출력물 | 설명 |
|---|---|
| 핵심 주제 | 한 문장 요약 |
| 제목 후보 3개 + 최종 제목 | SEO 최적화 |
| 썸네일 문구 3개 | 소셜 미디어용 |
| 한 줄 요약 | 독자용 요약 |
| SEO 메타 설명 | 120~160자 |
| Sora 2 영상 프롬프트·내레이션·자막 | 숏츠 제작용 |
| 대표 이미지 프롬프트 3개 + alt 텍스트 | 이미지 생성용 |
| 해시태그 10개 이상 | |
| 마크다운 콘텐츠 패키지 | `===MARKDOWN_START===` 구분자 사용 |
| 게시 가능한 HTML | 인라인 CSS, 티스토리 호환 |
| 사실 확인 필요 항목 | 환각 방지 목록 |

Nick Spisak의 X 아티클은 한 핀테크 창업자가 마케팅, SDR, 엔지니어링, 커뮤니티, 브리핑 에이전트 5개를
운영하다 48시간 만에 실패한 사례를 소개한다.

공식 저장소는 MIT License를 사용한다. 2026년 7월 6일 GitHub 화면 기준 스타 수는 약 21만 개다.

원문:
- GPTERS 분석 글
- Nick Spisak X 아티클

세 요소는 역할이 다르며 명확히 분리되어 있습니다.

---

### 시스템 프롬프트 (System Prompt)

모델의 전체 행동 방침을 설정합니다. 대화 전 고정 설정으로 사용합니다.

```text
너는 AI 뉴스 콘텐츠 패키지 생성기다.

행동 원칙:
1. 입력 기사와 공식 출처로 확인되지 않은 사실을 확정적으로 생성하지 않는다.
2. 확인된 사실, 기사 주장, 해석 가능한 의미, 확인 필요 항목을 항상 분리한다.
3. 정보가 부족하면 콘텐츠 생성을 중단하고 INPUT_REQUIRED 형식으로 필요한 정보를 요청한다.
4. 출력은 반드시 ===MARKDOWN_START=== / ===MARKDOWN_END=== 와 ===HTML_START=== / ===HTML_END=== 구분자를 사용한다.
5. HTML은 인라인 CSS만 사용하며 외부 폰트와 <style> 블록을 사용하지 않는다.
```

---

### 유저 프롬프트 (User Prompt)

매 실행 시 사용자가 입력하는 지시 문장입니다.

```text
아래 기사와 작성 조건을 기준으로 블로그 콘텐츠 패키지를 생성하라.
출력은 MARKDOWN_START/MARKDOWN_END와 HTML_START/HTML_END로 분리하라.
사실 확인 필요 항목은 별도 섹션으로 명시하라.
```

---

### 입력 템플릿 (Input Template)

기사와 조건을 구조화하여 붙여넣는 재사용 가능한 틀입니다. (평가 기준 2 참조)

```text
[기사 정보] / [작성 조건] / [사실 검증] / [출력 요청] 블록으로 기사와 조건을 구조화한다.
```

## 평가 기준 10: 환각을 "사실 오류"로 정의하고 창의적 생성과 구분 ✅ Pass

### 환각의 정의

이 과제에서 **환각(Hallucination)**은 다음과 같이 정의합니다.

> **입력 기사와 공식 출처로 확인되지 않은 사실을 확정적으로 생성하는 것**

구체적 예시:
- 존재가 확인되지 않은 모델명 (`Gemma 4 26B A4B`)을 공식 모델처럼 기술
- 변동 수치 (`GitHub 스타 72,000개`)를 현재 사실로 단정
- 조건부 안내 (`$5 VPS`)를 비용 보장으로 확정
- 추가 옵션이 필요한 명령 (`hermes claw migrate`)을 자동 완전 이전으로 설명

### 창의적 생성과의 구분 기준

| 항목 | 분류 | 이유 |
|---|---|---|
| 제목 후보 3개 | ✅ 창의적 생성 허용 | 사실 주장 없는 표현 영역 |
| 썸네일 문구 | ✅ 창의적 생성 허용 | 클릭 유도 표현은 사실 영역 아님 |
| 이미지 프롬프트 | ✅ 창의적 생성 허용 | 이미지 묘사는 사실 검증 대상 아님 |
| Sora 영상 프롬프트 | ✅ 창의적 생성 허용 | 영상 연출은 창의적 판단 영역 |
| 문체·어조 조정 | ✅ 창의적 생성 허용 | 문장 표현은 사실 영역 아님 |
| 제품 기능 설명 | ❌ 사실 영역 | 공식 출처 확인 필수 |
| 라이선스 정보 | ❌ 사실 영역 | 공식 문서 확인 필수 |
| CLI 명령어 | ❌ 사실 영역 | 공식 문서 확인 필수 |
| 비용·성능 수치 | ❌ 사실 영역 | 공식 문서 확인 필수 |
| 경쟁 제품 비교 | ❌ 사실 영역 | 출처 귀속 필수 |

### 구분이 필요한 이유

창의적 생성(제목, 이미지 묘사, 문체)까지 환각으로 분류하면 모델이 지나치게 경직되어 실용적인 콘텐츠를 만들 수 없습니다. 반면 사실 영역(기능·수치·명령어)에서 허용하면 잘못된 정보가 블로그에 게시됩니다. 따라서 **사실 영역은 엄격하게, 창의 영역은 유연하게** 구분하는 이분법 기준을 적용했습니다.

## 평가 기준 11: 환각 검증 Pass/Fail 판정 기준 설명 ✅ Pass

### 판정 기준표

| 판정 | 기준 | 예시 |
|---|---|---|
| **Pass** | 공식 출처 또는 입력 기사와 일치하고 조건을 정확히 설명함 | "MIT License" — GitHub LICENSE 파일로 확인 |
| **Pass-safe** | 위험한 주장을 생성하지 않거나 확인 필요로 분리함 | 스타 수를 언급하지 않고 생략 |
| **Pass(조건부)** | 사실이지만 추가 조건이 있어 그대로 사용하면 오해 가능 | "$5 VPS" — 실행 가능성 안내이지 비용 보장 아님 |
| **Fail** | 공식 확인이 불가능하거나 틀린 내용을 확정 사실처럼 생성함 | "Gemma 4 26B A4B" — 공식 문서 미확인 |
| **확인 필요** | 현재 자료만으로 확정할 수 없어 게시 전 추가 검증 필요 | 텔레메트리 없음 주장 |

### Pass A / Pass B 구분 (고위험 vs 저위험)

| 구분 | 내용 |
|---|---|
| **Pass A (고위험 주장)** | 공식 출처로 확인 가능한 구체적 수치나 기능 — 확인 결과를 명시해야 Pass |
| **Pass B (저위험 주장)** | 공식 자료로 확인은 어렵지만 위험 주장을 생성하지 않은 경우 — Pass-safe로 판정 |

> 예시: 스타 수 72,000개를 반복하면 **Fail**, 생략하면 **Pass-safe(B)**, 약 210k + 확인일자를 붙이면 **Pass(A)**

### 판정 절차

1. 생성된 결과물에서 **사실 주장**을 추출한다.
2. `test_inputs/hermes_agent/expected_facts.md` 기준과 대조한다.
3. 공식 출처(GitHub, 공식 문서)로 사실 여부를 확인한다.
4. 위 판정 기준표에 따라 Pass / Pass-safe / Fail / 확인 필요로 분류한다.
5. 모델별 집계 후 총점에 반영한다.

## 평가 기준 13: 무료 모델만 사용 시 품질 유지 방안 ✅ Pass

**[심층 인터뷰 질문]** 비용 제약으로 무료 모델만 써야 한다면 품질을 유지하기 위해 프롬프트와 프로세스를 어떻게 바꾸겠습니까?

---

### 무료 모델의 한계와 대응 전략

무료 모델(Claude 무료 플랜, Gemini Flash, GPT-4o mini 등)은 응답 길이 제한, 컨텍스트 유지 불안정, 형식 지키기 어려움이 주요 약점입니다.

### 전략 1: 작업 분할 (Task Decomposition)

한 번에 전체 패키지를 요청하지 않고 단계를 나눕니다.

```text
[1단계] 사실 확인 및 분류 프롬프트
→ 기사의 확인된 사실 / 미확인 주장 / 사용 금지 수치를 표로 정리

[2단계] 마크다운 콘텐츠 생성 프롬프트
→ 1단계 결과물만 입력으로 사용

[3단계] HTML 변환 프롬프트
→ 2단계 마크다운만 입력으로 사용
```

**효과**: 각 단계가 짧아져 토큰 한도 초과 없이 안정적으로 동작합니다.

### 전략 2: 구조 고정 (Strict Output Schema)

무료 모델일수록 출력 형식 편차가 크므로, 프롬프트에 출력 스키마를 명시합니다.

```text
출력 형식 (반드시 이 구조만 사용):
===SECTION: 핵심주제===
(한 문장)
===SECTION: 제목후보===
1. (제목1)
2. (제목2)
3. (제목3)
===SECTION: 사실확인필요===
- (항목1)
- (항목2)
```

**효과**: 모델이 구조를 이탈해 자유롭게 생성하는 것을 방지합니다.

### 전략 3: 자가 검수 단계 추가

마지막 단계에서 결과물을 자가 검수하도록 요청합니다.

```text
위 결과물에서 다음을 확인하라:
1. 확인되지 않은 수치나 기능을 확정 사실로 기술했는가?
2. 출력 형식(구분자, 섹션 순서)이 지시대로인가?
3. 문제가 있으면 해당 섹션만 수정해서 다시 출력하라.
```

### 전략 4: Few-shot 예시를 프롬프트에 내장

무료 모델은 시스템 프롬프트를 따르는 능력이 낮으므로, Few-shot C(되묻기 흐름)를 프롬프트 본문에 직접 삽입합니다.

```text
예시 입력: "Hermes Agent가 화제입니다."
예시 출력: "===INPUT_REQUIRED=== 기사 본문이 부족합니다. 본문을 추가해 주세요. ===INPUT_REQUIRED_END==="
```

### 요약

| 전략 | 무료 모델 약점 보완 | 예상 효과 |
|---|---|---|
| 작업 분할 | 컨텍스트 한도 초과 방지 | 안정성 ↑ |
| 구조 고정 | 형식 편차 최소화 | 일관성 ↑ |
| 자가 검수 | 환각 2차 필터 | 사실성 ↑ |
| Few-shot 내장 | 형식 준수율 향상 | 형식 준수 ↑ |

## 평가 기준 14: 업무 정책(규정/수치)이 자주 바뀔 때 환각 줄이기 위한 운영 전략 ✅ Pass

**[심층 인터뷰 질문]** 업무 정책이나 수치가 자주 바뀐다면 환각을 줄이기 위한 운영 전략을 어떻게 설계하겠습니까?

---

### 핵심 문제

모델의 학습 데이터에 **구버전 정책**이 포함되어 있으면, 최신 정책을 알려줘도 학습 데이터 기억이 더 강하게 작동합니다.

### 전략 1: 변동 가능 사실 목록을 입력 템플릿에 명시

```text
[사실 검증]
현재 유효한 정책/수치 (이 값만 사용할 것):
- 요금제: ...
- 지원 버전: ...
- 공식 명령어: ...

사용 금지 항목 (과거 정책 / 미확인 수치):
- ...
```

**효과**: 모델이 학습 데이터가 아닌 입력된 최신 정보만 참조하도록 강제합니다.

### 전략 2: 정책 기준 파일(Fact Sheet) 운영

```text
facts/policy_current.md  ← 항상 최신 상태 유지
```

매 실행 시 이 파일을 프롬프트에 붙여넣어 최신 정책을 컨텍스트로 주입합니다.

```text
[현재 정책 기준 — 2026-07-06 확인]
{facts/policy_current.md 내용}
```

### 전략 3: 확인 날짜 표시 의무화

모든 수치와 정책에 확인 날짜를 붙이는 규칙을 시스템 프롬프트에 추가합니다.

```text
규칙: 수치나 정책을 언급할 때 반드시 "(YYYY-MM-DD 확인)" 또는 "공식 문서 확인 필요"를 함께 표시한다.
```

**효과**: 독자가 정보를 그대로 믿지 않고 출처를 확인하도록 유도합니다.

### 전략 4: 정책 변경 시 프롬프트 v업 사이클

```text
정책 변경 감지 → facts/policy_current.md 업데이트 → 시스템 프롬프트 사용 금지 목록 추가 → 테스트 실행 → 프롬프트 버전 올림
```

### 전략 5: Retrieval-Augmented Generation (RAG) 구조 도입

장기적으로는 공식 문서를 실시간으로 조회해 프롬프트에 주입하는 RAG 구조를 도입합니다.

| 단계 | 내용 |
|---|---|
| 단기 | 입력 템플릿에 최신 정책을 직접 붙여넣기 |
| 중기 | `facts/policy_current.md`를 운영자가 주기적으로 갱신 |
| 장기 | 공식 문서 URL을 크롤링해 자동으로 컨텍스트 주입 |

## 평가 기준 15: 10턴 이상에서 문맥이 끊길 때 프롬프트 구조 개선 방안 ✅ Pass

**[심층 인터뷰 질문]** 10턴 이상 대화에서 문맥이 끊기는 문제가 생겼다면 프롬프트 구조를 어떻게 개선하겠습니까?

---

### 왜 문맥이 끊기는가

모델의 컨텍스트 창(Context Window)은 유한합니다. 대화가 길어지면 초기 시스템 프롬프트와 초반 조건이 컨텍스트 밖으로 밀려나 모델이 "잊어버리는" 현상이 발생합니다.

### 전략 1: 조건 요약 블록(Condition Summary)을 매 턴마다 재주입

```text
[현재 확정 조건 — Turn N 기준]
- 독자층: 1인 창업자·AI 콘텐츠 제작자
- 표현 금지: "완벽", "극적", "무조건", "최고"
- 수치 처리: 변동 가능 수치는 "확인 필요"로 표시
- HTML: 티스토리용 <div> + 인라인 CSS
- 이미지 위치: 도입 뒤·비교 앞·결론 앞
```

모든 사용자 메시지 앞에 이 블록을 붙입니다. **효과**: 이전 대화가 컨텍스트 밖으로 밀려나도 최신 조건은 항상 유지됩니다.

### 전략 2: 구조화된 State JSON 관리

```json
{
  "audience": "1인 창업자·AI 콘텐츠 제작자",
  "banned_expressions": ["완벽", "극적", "무조건", "최고"],
  "fact_check_required": ["GitHub 스타 수", "$5 VPS"],
  "html_format": "inline-css-div",
  "image_placement": ["도입 뒤", "비교 앞", "결론 앞"],
  "turn": 8
}
```

매 턴마다 이 JSON을 업데이트하고 프롬프트에 포함합니다.

### 전략 3: 핵심 조건 변경 시 명시적 '조건 업데이트' 발화

```text
[조건 업데이트 — Turn 5]
이전 조건에서 다음이 추가/변경됩니다:
- 추가: 과장 표현("완벽" 등) 금지
이후 모든 응답에 이 조건을 유지하세요.
```

### 전략 4: 긴 대화를 단계별 세션으로 분리

```text
세션 1 (Turn 1~5): 기사 분석·초안 생성
세션 2 (Turn 1~3): 세션1 최종 결과 + 조건 요약을 첫 메시지로 주입 후 계속 개선
```

이렇게 하면 각 세션의 컨텍스트가 짧아져 초반 조건을 잃지 않습니다.

### 전략 5: Turn 11 스타일 조건 검증을 5턴마다 실행

```text
[중간 검증 — Turn 10]
현재 결과가 Turn 1에서 합의한 모든 조건을 유지하는지 확인하고
누락된 조건이 있으면 항목별로 Pass/Fail 표로 정리해줘.
```

**효과**: 문맥 이탈을 조기에 발견하고 수정합니다.

### 전략 요약

| 전략 | 해결하는 문제 | 구현 난이도 |
|---|---|---|
| 조건 요약 블록 재주입 | 조건 망각 | 낮음 (복사·붙여넣기) |
| State JSON 관리 | 복잡한 조건 누락 | 중간 |
| 명시적 조건 업데이트 발화 | 조건 변경 미반영 | 낮음 |
| 세션 분리 | 컨텍스트 한도 초과 | 중간 |
| 5턴마다 검증 | 문맥 이탈 감지 | 낮음 |
