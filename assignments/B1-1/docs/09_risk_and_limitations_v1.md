# 09_risk_and_limitations_v1.md

## 1. 문서 목적
이 문서는 **AI 테크 뉴스 블로그 자동화 프로젝트의 주요 리스크와 실패 사례를 체계적으로 정의하는 문서**이다.  
자동화 파이프라인 운영 중 발생할 수 있는 품질 저하, 구조 오류, 사실 왜곡, 형식 이탈 등을 사전에 식별하고 대응 기준을 마련하는 것을 목표로 한다.

이 문서의 목적은 다음과 같다.

- 자동화 과정에서 발생 가능한 실패 유형을 미리 정의한다.
- 각 실패 유형별 원인, 영향, 탐지 방법, 대응 방안을 정리한다.
- 실험 및 운영 과정에서 재발 방지 기준으로 활용한다.
- 실행 로그 문서와 연결하여 문제 대응 체계를 만든다.

---

## 2. 적용 범위

이 문서는 아래 범위에 적용된다.

- 뉴스 수집 단계
- 뉴스 정리/정규화 단계
- 핵심 뉴스 선별 단계
- 블로그 본문 생성 단계
- 비교 분석 단계
- HTML 변환 단계
- 결과 검수 및 게시 직전 단계

아래 항목은 현재 문서 범위에서 제외한다.

- 서버 인프라 장애 대응 매뉴얼
- API 인증/과금 시스템 운영 정책
- 티스토리 계정 보안 정책
- 외부 서비스 전체 장애 복구 절차

---

## 3. 리스크 관리 원칙

### 3.1 사전 정의 원칙
문제가 생긴 뒤 대응하는 것보다, 어떤 실패가 가능한지 먼저 정의한다.

### 3.2 단계별 분리 원칙
실패는 전체가 아니라 특정 단계에서 발생하므로 단계별로 기록하고 관리한다.

### 3.3 재현 가능성 원칙
실패 사례는 다시 확인할 수 있도록 입력, 프롬프트, 모델, 출력 버전을 함께 남긴다.

### 3.4 운영 영향 우선 원칙
단순 품질 저하보다, 게시 불가/사실 왜곡/브랜드 신뢰 저하 같은 운영 리스크를 더 중요하게 본다.

### 3.5 완전 자동화 맹신 금지 원칙
자동화가 가능하더라도, 핵심 품질 구간은 최소 검수 기준을 유지한다.

---

## 4. 리스크 분류 체계

본 프로젝트의 리스크는 크게 아래 6개 범주로 구분한다.

1. 입력 데이터 리스크
2. 모델 생성 리스크
3. 구조/형식 리스크
4. 해석/비교 리스크
5. 운영/재현성 리스크
6. 게시 직전 품질 리스크

---

## 5. 입력 데이터 리스크

## 5.1 중복 기사 과다 수집

### 설명
같은 내용을 다룬 기사 여러 개가 중복 반영되어 실제 이슈보다 과대 대표될 수 있다.

### 원인
- 유사 제목 기사 다수 수집
- 중복 제거 규칙 부족
- 언론사만 다른 재가공 기사 포함

### 영향
- 핵심 뉴스 선별 왜곡
- 한 이슈에 편향된 본문 생성
- 비교 관점이 단조로워짐

### 탐지 방법
- 제목 유사도 확인
- 링크/출처/발행시간 중복 확인
- 핵심 문장 반복 여부 확인

### 대응 방안
- 정규화 단계에서 유사 기사 그룹화
- 대표 기사 1건만 남기고 나머지는 참고용 처리
- 동일 이슈 다중 기사 수 제한

---

## 5.2 오래된 기사 혼입

### 설명
최신 뉴스 기반 글을 작성해야 하는데, 오래된 기사가 섞여 현재 상황 판단을 흐릴 수 있다.

### 원인
- 검색 범위 설정 미흡
- 날짜 필터 불완전
- 기사 본문 내 과거 사례와 현재 기사 혼동

### 영향
- 최신 동향 정리 실패
- 시점 불일치
- 독자 신뢰 하락

### 탐지 방법
- 발행일 확인
- 기사 내 시간 표현 검토
- 최신성 기준일 비교

### 대응 방안
- 수집 단계에서 날짜 필터 강제
- 기준일보다 오래된 기사 자동 제외 규칙 적용
- 예외 허용 시 “배경 설명용”으로 명시

---

## 5.3 신뢰도 낮은 출처 포함

### 설명
검증되지 않은 출처나 과장형 기사로 인해 전체 글의 신뢰도가 떨어질 수 있다.

### 원인
- 출처 등급 기준 부재
- 클릭 유도형 콘텐츠 포함
- 소문/추정 기사 반영

### 영향
- 사실 왜곡
- 잘못된 비교 분석
- 브랜드 신뢰성 손상

### 탐지 방법
- 출처 리스트 관리
- 선정적 제목 패턴 확인
- 사실 인용 근거 유무 확인

### 대응 방안
- 허용 출처 목록 운영
- 저신뢰 출처는 보조 참고만 허용
- 핵심 주장에는 복수 출처 확인 원칙 적용

---

## 6. 모델 생성 리스크

## 6.1 환각(Hallucination)

### 설명
입력 기사에 없는 사실이나 해석을 모델이 임의로 추가하는 문제.

### 원인
- 모델의 일반화 습관
- 비교 설명 요구가 과도할 때
- 프롬프트에 사실 제한 규칙이 약할 때

### 영향
- 잘못된 정보 게시
- 기업 비교 왜곡
- 운영 신뢰도 저하

### 탐지 방법
- 입력 기사와 출력 문장 대조
- 근거 없는 수치/발언/전략 표현 확인
- “~로 보인다” 식 과잉 추론 점검

### 대응 방안
- “입력에 없는 사실 추가 금지” 명시
- 사실/해석 문단 분리
- 핵심 문장에 근거 검수 단계 추가

---

## 6.2 과잉 요약

### 설명
핵심 정보가 지나치게 압축되어 독자가 맥락을 이해하기 어려운 상태.

### 원인
- 길이 제한 과도
- 짧은 출력 우선 프롬프트
- 단계별 요약이 반복되며 정보 손실 발생

### 영향
- 정보 밀도 부족
- 차이점 설명 약화
- 블로그 글 가치 하락

### 탐지 방법
- 기사 핵심 포인트 누락 여부 확인
- “무슨 일이 왜 중요한지”가 보이는지 점검
- 비교 근거 부족 여부 확인

### 대응 방안
- 요약과 해설 구간 분리
- 최소 포함 요소 정의
- 본문 길이 하한선 설정

---

## 6.3 과잉 장문 생성

### 설명
핵심 대비 지나치게 긴 설명이 생성되어 가독성이 떨어지는 문제.

### 원인
- 모델의 장문 선호
- 해설 요구 범위 과다
- 반복 문장 발생

### 영향
- 독자 피로 증가
- 핵심 흐림
- HTML 변환 후 밀도 과다

### 탐지 방법
- 문단 길이 점검
- 유사 의미 반복 확인
- 요약 대비 본문 과다 여부 확인

### 대응 방안
- 문단당 문장 수 제한
- 반복 제거 후처리
- 핵심 질문 중심 재작성

---

## 6.4 톤 불안정

### 설명
문체가 뉴스 요약, 마케팅 문구, 과장형 해설 사이를 오가며 일관성을 잃는 문제.

### 원인
- 프롬프트 역할 정의 부족
- 모델별 스타일 편차
- 단계별 출력 재조합 과정의 어조 혼합

### 영향
- 블로그 품질 저하
- 전문성 약화
- 독자 신뢰도 저하

### 탐지 방법
- 과장형 표현 확인
- 문단별 어조 차이 점검
- 지나친 감탄/예언형 문장 확인

### 대응 방안
- 문체 기준 고정
- 금지 표현 목록 운영
- 최종 톤 정리 단계 추가

---

## 7. 구조/형식 리스크

## 7.1 JSON/Markdown/HTML 형식 이탈

### 설명
요청한 출력 형식을 정확히 지키지 않는 문제.

### 원인
- 프롬프트 명시 부족
- 모델의 설명 추가 습관
- 형식 요구와 창의적 생성 요구 충돌

### 영향
- 자동 파이프라인 중단
- 후처리 비용 증가
- 게시 지연

### 탐지 방법
- 스키마 검사
- 필수 태그/필드 존재 확인
- HTML 외 텍스트 포함 여부 확인

### 대응 방안
- 형식 우선 프롬프트 사용
- 형식 오류 시 재생성 로직 적용
- 단계별 출력 검증 자동화

---

## 7.2 HTML 태그 깨짐

### 설명
닫힘 태그 누락, 잘못된 중첩, 표 구조 불일치 등으로 HTML이 깨지는 문제.

### 원인
- 장문 HTML 직접 생성
- 표와 본문 동시 생성
- 모델의 구조 유지 실패

### 영향
- 티스토리 붙여넣기 실패
- 레이아웃 붕괴
- 수동 수정 증가

### 탐지 방법
- 태그 쌍 검사
- table 구조 검사
- 렌더링 미리보기 확인

### 대응 방안
- 본문과 HTML 렌더링 분리
- 표를 별도 컴포넌트로 생성
- 템플릿 기반 조립 방식 적용

---

## 7.3 필수 섹션 누락

### 설명
제목, 요약 박스, 비교 표, 결론 등 핵심 구성요소가 빠지는 문제.

### 원인
- 프롬프트 누락
- 긴 생성 중 일부 구조 생략
- 모델의 자체 단순화

### 영향
- 문서 완성도 저하
- 비교형 블로그 목적 상실
- 운영 기준 미달

### 탐지 방법
- 체크리스트 기반 검수
- 섹션명 검색
- 필수 컴포넌트 존재 여부 점검

### 대응 방안
- 필수 섹션 목록 고정
- 누락 시 해당 섹션만 부분 재생성
- 템플릿 변수 기반 생성 사용

---

## 8. 해석/비교 리스크

## 8.1 비교 축 왜곡

### 설명
OpenAI와 Google을 비교할 때 실제 기사 근거보다 임의 프레임으로 비교하는 문제.

### 원인
- 비교 요구가 지나치게 추상적임
- 근거 없는 전략 해석
- 모델이 일반적 업계 인식을 삽입

### 영향
- 글의 설득력 저하
- 사실 기반 비교 실패
- 편향된 분석으로 보일 위험

### 탐지 방법
- 비교 항목별 근거 문장 확인
- 기사 입력에 없는 비교 축인지 점검
- 단정적 문장 표시 확인

### 대응 방안
- 비교 축 후보를 입력 기반으로 제한
- “기사에서 확인 가능한 차이만 비교” 규칙 적용
- 비교표 항목을 사전 정의

---

## 8.2 한 기업 편향

### 설명
특정 기업을 더 혁신적이거나 더 유리하게 반복적으로 묘사하는 문제.

### 원인
- 입력 기사 수 불균형
- 모델의 기존 학습 편향
- 프롬프트의 표현 방향성

### 영향
- 중립성 저하
- 독자 반감 가능성
- 비교 글 신뢰 하락

### 탐지 방법
- 긍정/부정 표현 비율 확인
- 기업별 분량 균형 점검
- 결론 문단 편향성 확인

### 대응 방안
- 기업별 입력량 균형 유지
- 비교 항목 동일 기준 적용
- 결론에서 우열 단정보다 차이 정리 중심 유지

---

## 8.3 의미 과대해석

### 설명
단일 기사 또는 단기 발표를 산업 전체 변화처럼 과장 해석하는 문제.

### 원인
- 클릭 유도형 문장 선호
- 해설 강화 요구
- 모델의 일반화 경향

### 영향
- 과장된 블로그 글 생성
- 장기적으로 신뢰도 하락

### 탐지 방법
- “판도가 바뀐다”, “완전히 재편된다” 같은 표현 확인
- 근거 대비 해석 강도 점검
- 반복 과장 패턴 검토

### 대응 방안
- 과장 금지 표현 목록화
- “가능성”, “시사점” 수준으로 표현 절제
- 결론 문단 별도 검수

---

## 9. 운영/재현성 리스크

## 9.1 같은 입력인데 결과 편차 큼

### 설명
동일 입력/프롬프트인데 실행마다 품질 차이가 크게 나는 문제.

### 원인
- 모델 비결정성
- 프롬프트의 모호성
- 길이/형식 지시 부족

### 영향
- 운영 예측성 저하
- 비교 실험 신뢰성 저하
- 반복 실행 비용 증가

### 탐지 방법
- 동일 테스트 반복 실행
- 결과 길이/형식/품질 편차 비교
- 핵심 섹션 일관성 확인

### 대응 방안
- 프롬프트 구체화
- 단계별 출력 분리
- 운영용과 실험용 프롬프트 구분

---

## 9.2 버전 추적 실패

### 설명
어떤 프롬프트와 어떤 입력으로 어떤 결과가 나왔는지 기록이 남지 않는 문제.

### 원인
- 파일명 규칙 미준수
- 로그 기록 누락
- 프롬프트 파일 분산 관리

### 영향
- 재현 불가
- 개선 방향 추적 어려움
- 문제 원인 분석 실패

### 탐지 방법
- 로그 파일 점검
- 출력물 메타정보 유무 확인
- 입력/프롬프트 링크 존재 확인

### 대응 방안
- 파일명 규칙 강제
- 실행 로그 필수화
- 결과물에 프롬프트 버전 명시

---

## 9.3 수동 수정 과다

### 설명
자동화 결과가 매번 많이 고쳐져야 해서 실제로는 자동화 이점이 줄어드는 문제.

### 원인
- 품질 기준 불명확
- 후처리 설계 부족
- 형식/톤 오류 반복

### 영향
- 운영 효율 저하
- 사람 의존 증가
- 확장성 약화

### 탐지 방법
- 수정 시간 기록
- 자주 수정되는 항목 분석
- 단계별 오류 유형 집계

### 대응 방안
- 반복 수정 항목을 문서 기준으로 환원
- 후처리 체크리스트 정교화
- 가장 자주 깨지는 단계 우선 개선

---

## 10. 게시 직전 품질 리스크

## 10.1 제목과 본문 불일치

### 설명
제목은 강한데 본문은 그 내용을 충분히 다루지 못하는 문제.

### 원인
- 제목 생성이 과도하게 자극적임
- 본문 핵심 메시지와 제목 연결 약함

### 영향
- 독자 기대 불일치
- 클릭 후 이탈 가능성 증가
- 신뢰성 저하

### 탐지 방법
- 제목 키워드가 본문에서 충분히 설명되는지 확인
- 과장형 제목 여부 점검

### 대응 방안
- 제목 생성 시 본문 기반 키워드만 사용
- 게시 전 제목-본문 정합성 검수

---

## 10.2 해시태그 부정확

### 설명
본문과 관련 없는 해시태그 또는 지나치게 일반적인 해시태그만 붙는 문제.

### 원인
- 자동 태그 생성 단순화
- 키워드 추출 품질 부족

### 영향
- 검색성 저하
- 주제 정리력 약화

### 탐지 방법
- 본문 핵심어와 태그 일치 확인
- 불필요한 범용 태그 비율 점검

### 대응 방안
- 기업명/기술명/주제명 균형 규칙 적용
- 태그 개수 범위 고정

---

## 10.3 최종 검수 누락

### 설명
자동 생성 결과를 거의 확인하지 않고 바로 게시하는 문제.

### 원인
- 자동화 신뢰 과잉
- 운영 시간 부족
- 체크리스트 미정착

### 영향
- 오류 게시
- 사실 왜곡 노출
- 수정 비용 증가

### 탐지 방법
- 게시 전 승인 단계 존재 여부 확인
- 검수 기록 유무 확인

### 대응 방안
- 최소 검수 체크리스트 운영
- 게시 전 승인 로그 남기기
- 초기 운영 단계에서는 사람 검수 유지

---

## 11. 리스크 우선순위 분류

운영상 중요도에 따라 리스크를 아래처럼 분류한다.

### 11.1 치명(Critical)
즉시 게시 중단 또는 재생성이 필요한 문제

- 환각으로 인한 사실 오류
- HTML 심각한 깨짐
- 필수 섹션 대규모 누락
- 출처 신뢰도 심각한 문제
- 특정 기업에 대한 왜곡된 비교

### 11.2 중요(High)
게시 가능 여부를 재검토해야 하는 문제

- 중복 기사 과다 반영
- 오래된 기사 혼입
- 비교 축 왜곡
- 과장형 결론
- 결과 편차 과다

### 11.3 보통(Medium)
품질 개선 차원에서 수정이 필요한 문제

- 문단 장문화
- 해시태그 품질 저하
- 어조 불일치
- 제목과 본문 연결 약화
- 요약 박스 표현 품질 저하

### 11.4 경미(Low)
게시는 가능하지만 누적되면 품질 저하로 이어질 수 있는 문제

- 해시태그 개수 과다/과소
- 표현 반복
- 문단 간 길이 불균형
- 강조 박스 문장 약함
- 비교 표 표현 밀도 불균형

---

## 12. 리스크 기록 방식

실패 사례는 단순히 “잘 안 됨” 수준이 아니라,  
나중에 재현·분석·개선할 수 있도록 구조적으로 기록해야 한다.

### 12.1 최소 기록 항목
- 실행 일시
- 실행 단계
- 사용 모델명
- 프롬프트 파일명/버전
- 입력 데이터 파일명
- 출력 파일명
- 발생 문제 유형
- 문제 상세 설명
- 심각도 등급
- 임시 대응 내용
- 근본 원인 추정
- 재발 방지 조치

### 12.2 권장 기록 형식
```text
[Risk Log]
date:
pipeline_step:
model:
prompt_version:
input_file:
output_file:
risk_type:
severity:
issue_summary:
suspected_cause:
temporary_action:
preventive_action:
status:
```

### 12.3 기록 원칙
1. 실패는 숨기지 않고 남긴다.
2. 같은 문제가 반복되면 별도 패턴으로 묶는다.
3. 문제 발생 단계와 수정 단계를 구분해서 기록한다.
4. 추정 원인과 확정 원인을 구분한다.

---

## 13. 실패 대응 프로세스

문제 발생 시에는 아래 순서로 대응하는 것을 기본 원칙으로 한다.

### 13.1 1단계: 문제 식별
- 어떤 단계에서 실패했는지 확인
- 형식 문제인지 내용 문제인지 먼저 구분
- 게시 가능 여부부터 판단

### 13.2 2단계: 심각도 판정
- Critical / High / Medium / Low 중 분류
- Critical은 즉시 게시 중단
- High는 재검토 후 재생성 여부 판단

### 13.3 3단계: 임시 조치
- 해당 단계만 재실행
- 수동 수정으로 복구 가능한지 확인
- 전체 파이프라인 재실행이 필요한지 판단

### 13.4 4단계: 원인 분석
- 입력 문제인지 프롬프트 문제인지 모델 문제인지 구분
- 동일 입력 재실행 시 재현되는지 확인
- 이전 정상 결과와 차이 비교

### 13.5 5단계: 기준 문서 반영
- 반복 문제는 문서 기준으로 승격
- 프롬프트 수정 사항을 버전화
- 체크리스트 또는 후처리 규칙에 반영

---

## 14. 실패 유형별 우선 대응 가이드

### 14.1 환각 발생 시
1. 문제 문장 표시
2. 입력 기사 근거 대조
3. 해당 문장 삭제 또는 재작성
4. 프롬프트에 “입력 근거 없는 사실 추가 금지” 강화
5. 필요 시 사실성 검수 단계 추가

### 14.2 HTML 깨짐 발생 시
1. HTML 외 텍스트 포함 여부 확인
2. 닫힘 태그와 표 구조 검사
3. 본문과 표를 분리해 재생성
4. 템플릿 기반 조립 방식으로 복구
5. 최종 붙여넣기 테스트 재실행

### 14.3 비교 왜곡 발생 시
1. 비교 항목별 근거 확인
2. 근거 없는 전략 해석 제거
3. 비교 축을 사전 정의 항목으로 제한
4. 결론 문단의 우열 표현 삭제
5. 입력 기사 기반 차이만 다시 정리

### 14.4 중복 기사 과다 반영 시
1. 기사 유사도 기준으로 재정렬
2. 대표 기사만 남기고 그룹화
3. 중복 이슈 반영 비중 축소
4. 뉴스 선별 단계 규칙 강화

### 14.5 톤 불안정 발생 시
1. 과장형 문장 표시
2. 문체 기준에 맞춰 일괄 수정
3. 결론/강조 문장 별도 재작성
4. 다음 버전 프롬프트에 톤 규칙 명시

---

## 15. 자동 검수와 수동 검수의 역할 분리

완전 자동화만으로 모든 리스크를 잡기 어렵기 때문에,  
자동 검수와 수동 검수의 역할을 구분한다.

### 15.1 자동 검수에 적합한 항목
- 필수 섹션 존재 여부
- HTML 태그 구조
- 표 열/행 개수
- 파일명 규칙
- 해시태그 개수
- 중복 기사 유사도
- 날짜 범위 조건

### 15.2 수동 검수에 적합한 항목
- 환각 여부
- 비교 해석 적절성
- 문체 일관성
- 제목-본문 정합성
- 과장 표현 여부
- 독자 관점의 가독성

### 15.3 운영 원칙
1. 기계적으로 잡을 수 있는 것은 자동 검수로 이동한다.
2. 신뢰도에 직접 영향 주는 항목은 사람 검수를 유지한다.
3. 반복 수동 수정 항목은 기준 문서로 환원한다.

---

## 16. 재발 방지 원칙

같은 문제가 여러 번 반복되면 운영 효율이 급격히 떨어지므로,  
문제 해결 이후에는 반드시 재발 방지 조치를 남긴다.

### 16.1 재발 방지 수단
- 프롬프트 수정
- 템플릿 고정
- 입력 필터 추가
- 체크리스트 항목 추가
- 실행 로그 항목 보강
- 수동 승인 단계 유지

### 16.2 재발 방지 우선순위
1. 게시 위험이 큰 문제부터
2. 자주 반복되는 문제
3. 수동 수정 시간이 많이 드는 문제
4. 모델 교체와 무관하게 계속 발생하는 문제

---

## 17. 대표 실패 사례 예시

### 사례 1: 비교 표는 그럴듯하지만 근거가 없음
- 유형: 해석/비교 리스크
- 심각도: High
- 문제: 입력 기사에 없는 “수익화 전략 차이”를 단정적으로 표에 삽입
- 대응: 해당 행 삭제 후 입력 근거가 있는 항목만 재구성
- 재발 방지: 비교 항목 사전 정의 목록 사용

### 사례 2: HTML 결과에 설명 문장이 섞임
- 유형: 구조/형식 리스크
- 심각도: High
- 문제: HTML 위에 “아래는 요청하신 HTML입니다” 문장 출력
- 대응: HTML 전용 재생성
- 재발 방지: “설명 금지 / 코드블록 금지 / HTML만 출력” 강화

### 사례 3: 최신 뉴스 글인데 3개월 전 기사 포함
- 유형: 입력 데이터 리스크
- 심각도: High
- 문제: 날짜 필터 미흡으로 오래된 기사 반영
- 대응: 기준일 재설정 후 기사 세트 재구성
- 재발 방지: 수집 단계 날짜 검증 추가

### 사례 4: 결론이 과장되어 신뢰도 하락
- 유형: 해석/비교 리스크
- 심각도: Medium
- 문제: “산업 판도가 완전히 뒤집힌다” 같은 표현 사용
- 대응: 시사점 수준으로 완화
- 재발 방지: 과장 금지 표현 목록 운영

## 18. 실행 로그 문서와의 연결

이 문서는 개념적 기준 문서이며,  
실제 문제 발생 내역은 실행 로그 문서에 누적 기록한다.

### 연결 방식
- 본 문서: 리스크 유형, 정의, 대응 원칙
- 실행 로그 문서: 실제 발생 사례, 날짜, 모델, 조치 내역

### 운영 원칙
1. 새로운 실패가 나타나면 먼저 로그에 기록한다.
2. 반복되거나 중요도가 높으면 본 문서에 유형으로 승격한다.
3. 문서 기준이 바뀌면 관련 프롬프트/파이프라인 문서도 함께 수정한다.

## 21. 현재 버전의 한계

이 문서는 리스크 기준 초안이므로 아래 항목은 후속 보완이 필요하다.

- 실제 운영 중 발생한 실패 사례 기반 보강
- 모델별 실패 빈도 정량화
