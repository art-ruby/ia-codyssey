# 제품화 가능성 검토

2026-09-03 · 기술 통합과는 별개의 질문. **«만들 수 있다» 와 «제품이 된다» 는 다르다.**

---

## 1. 이 시스템이 실제로 해결하는 문제

### 지금 사용자가 시간과 판단력을 가장 많이 쓰는 곳

실제 코드와 데이터가 말해 주는 것:

| 단계 | 자동화 상태 | 사람이 쓰는 것 |
|---|---|---|
| 수집·점수 | ✅ 자동 (777건·1,884 스냅샷) | 0 |
| **무엇을 만들지 고르기** | ❌ 표만 있음 | **판단력. 매일. 기록 없음** |
| 재료 모으기 | ✅ 자동 (댓글·자막·브리프) | 0 |
| **Radar → AutoMaker 전달** | ❌ 수동 4회 복사 | **시간** |
| 제작 | ✅ 거의 자동 | 단계 클릭 |
| **게시 후 판단 검증** | ❌ 없음 | **불가능** |

**핵심 문제는 «제작이 느리다» 가 아니다.** 제작은 이미 자동이다.
문제는 **«무엇을 만들지 정하는 근거가 매번 사라진다»** 는 것이다.

### 이 문제는 반복적인가 — 그렇다

주 2~3편을 낸다면 연 100~150회 발생한다. 매번 30분~2시간의 판단이 든다.

### 현재 어떻게 해결하고 있나

Radar 화면 → 눈으로 판단 → Claude 웹에서 대화 → 손으로 옮김.
**도구는 있는데 판단의 기록이 남지 않는다.**

### 이 시스템이 줄이는 것

| 줄어드는 것 | 근거 |
|---|---|
| 도구 간 복사·붙여넣기 | 4회 → 0회 |
| 반복 분석 | AutoMaker 3단계 LLM 호출 2~4개 생략 |
| 의사결정 부담 | 규칙이 1차로 걸러 3~5건만 남긴다 |
| 채널 설정 이중 관리 | 2곳 → 1곳 |
| **판단 근거의 망각** | ← 이것이 가장 크고, 시간이 갈수록 커진다 |

### 새로 생기는 복잡성 (정직하게)

- 프로세스 2개 → 3개
- 계약 파일 6종 추가. **계약을 어기면 조용히 실패한다**
- Strategist 배포·키 관리가 하나 더 는다
- 잘못된 추천이 «시스템이 그렇게 말했다» 는 이유로 검증 없이 채택될 위험

## 2. 핵심 제품이 무엇인가

| | 위치 |
|---|---|
| **Core Product** | **데이터 기반 콘텐츠 «의사결정» 시스템** — 무엇을 만들지 정하고, 그 근거를 남기고, 나중에 맞았는지 확인하는 것 |
| **Supporting Module** | Radar(발견) · AutoMaker(제작) |
| **Future Expansion** | 성과 학습 · 멀티플랫폼 · 다중 채널 운영 |

지시서의 후보 중 A(YouTube 분석 도구)·D(제작 자동화)는 **이미 시장에 많다.**
F(데이터 기반 의사결정 시스템)가 유일하게 이 조합에서만 나오는 것이다.
G(콘텐츠 운영 OS)는 지금 규모에서는 **과대 명명**이다 — 게시 실적 0건에
운영 OS 라는 이름을 붙이면 자기 기만이 된다.

## 3. 만드는 자동화 vs 판단 자동화

| | Execution Automation | Decision Automation |
|---|---|---|
| 우리 위치 | AutoMaker — 이미 완성도 높음 | **거의 비어 있음** |
| 시장 경쟁 | **매우 치열** (OpusClip·Predis·Ocoya·InVideo·수많은 AI 영상 도구) | 얕음 (vidIQ·1of10 은 «발견» 까지만) |
| 차별화 가능성 | **낮음.** 우리가 더 잘 만들 이유가 없다 | **있음.** 단 조건부 |
| 기술적 실현성 | 이미 됨 | 부분적 |

**결론: 제품 가치는 Decision 쪽에 있다.** 다만 냉정하게 말하면

- Decision Automation 의 «자동» 은 대부분 **규칙 엔진**이 해야 한다. LLM 이
  판단하게 두면 근거 없는 확신이 나온다.
- LLM 이 실제로 잘하는 것은 «판단» 이 아니라 **«근거를 사람이 읽을 문장으로 바꾸는 것»** 과
  **«반대 근거를 빠뜨리지 않는 것»** 이다.
- 즉 파는 것은 «AI 가 대신 결정해 준다» 가 아니라
  **«결정이 기록되고 나중에 검증된다»** 다. 이 차이가 제품의 정직성을 결정한다.

## 4. 고유 자산 후보

| 자산 | 현재 존재 | 위치 | 추가 저장 필요 | 시간이 갈수록 | 복제 난이도 |
|---|---|---|---|---|---|
| 장기 Video Snapshot | ✅ 1,884행 | Radar | — | **커짐** | 중 (시간이 필요) |
| Outlier 탐지 이력 | ❌ 매번 재계산 | — | **필요** | 커짐 | 중 |
| Opportunity 발생 시점 | ❌ | — | **필요** | 커짐 | 중 |
| AI Prediction | ❌ | — | **필요** | **매우 커짐** | **높음** |
| MAKE/WATCH/SKIP 이력 | ❌ | — | **필요** | **매우 커짐** | **높음** |
| Production Brief | ✅ 2건 | Radar | — | 커짐 | 낮음 |
| 실제 제작 결과 | ❌ 0건 | — | 필요 | 커짐 | 낮음 |
| 게시 후 성과 | ❌ | — | **필요** | **매우 커짐** | **높음**(계정 데이터) |
| Prediction vs Actual | ❌ | — | **필요** | **최고** | **최고** |
| 채널별 성공/실패 패턴 | ❌ | — | 필요 | 커짐 | 높음 |
| 검색어별 수요 변화 | 부분 ✅ | Radar | 이력화 필요 | 커짐 | 중 |
| 제목/Angle/Hook ↔ 성과 연결 | ❌ | — | **필요** | **최고** | **최고** |

### 「코드를 복제당해도 남는 것은 무엇인가」

**코드는 전부 복제 가능하다.** 알고리즘(ADViews·Age Bucket·Video Score)도
문서로 공개되어 있어 복제 가능하다.

남는 것은 셋뿐이다.

1. **Prediction → Actual 이력** — 남의 채널 데이터로는 만들 수 없다.
   자기 채널을 실제로 운영해야만 생긴다.
2. **채널별 판단 렌즈의 누적 보정** — «이 채널에서 이 각도는 안 먹혔다» 는 기록.
3. **시간.** 스냅샷은 소급 수집이 불가능하다. 오늘 시작하지 않으면 내일도 없다.

**세 개 모두 «게시» 를 해야만 생긴다. 그런데 지금 게시 실적이 0이다.**
→ **가장 시급한 것은 코드가 아니라 실제 운영 개시다.**

## 5. Data Flywheel — 성립하는가

```
기회 발견 ✅ → AI 판단 ❌ → 제작 ✅ → 게시 ❌ → 실제 성과 ❌
        → 예상과 비교 ❌ → 규칙 개선 ❌ → 다음 선택 개선 ❌
```

**8칸 중 2칸만 있다.** 지금은 Flywheel 이 아니라 반쪽 파이프다.

| 필요 데이터 | 상태 |
|---|---|
| 남의 영상 조회수·구독자 | ✅ 이미 수집 중 |
| 우리 영상 조회수·좋아요·댓글 | **추가하면 쉽다** — `snapshot_collector` 재사용, 비용 ~0 |
| 우리 영상 CTR·시청유지·구독전환 | **YouTube Analytics API(OAuth) 필요** 또는 Studio 수기 입력 |
| 게시 시각·제목·썸네일·각도 | **사람 입력 필요** (URL 한 칸) |
| 판단 시점 점수·근거 | **코드 추가 필요** (DecisionSnapshot) |
| 시청자 반응 질적 분석 | ✅ 기술은 이미 있음 (`comments.analyze`) |

**«데이터가 쌓이면 AI 가 학습한다» 는 표현을 쓰지 않는다.** 실제로 가능한 것은:

- Phase A: 과거 사례를 **프롬프트에 넣는 것** (검색 + Context Injection)
- Phase B: 성공/실패를 **세는 것** (통계)
- Phase C: 그 통계로 **규칙 임계값을 조정하는 것**
- Phase D: (아주 나중에) 별도 랭킹 모델

**A 만으로도 대부분의 체감 가치가 나온다. B 는 30건, C 는 50건 이후다.**

## 6. 최초 타깃 사용자

| 후보 | 문제 강도 | 이미 돈을 쓰는가 | 빈도 | 데이터 확보 | 온보딩 | 설명 난이도 | 현 시스템 적합 |
|---|---|---|---|---|---|---|---|
| A. 얼굴 없는 1인 크리에이터 | **높음** | 일부(vidIQ 등) | 주 2~3 | 자기 채널 | **어려움**(채널 DNA 13항목) | 중 | **최고** |
| B. 다채널 운영자 | **최고** | 예 | 매일 | 좋음 | 어려움 | 중 | 높음 |
| C. 제작 대행사 | 높음 | 예 | 매일 | **고객 계정 필요** | 어려움 | 낮음 | 중 |
| D. SNS 마케팅 대행사 | 중 | 예 | 매일 | 어려움 | 어려움 | 낮음 | 낮음 |
| E~G. 1인사업자·소상공인·기업 | 낮음~중 | 일부 | 낮음 | 나쁨 | 매우 어려움 | 높음 | **낮음** |
| H. 자동화 채널 운영자 | 높음 | 예 | 매일 | 좋음 | 중 | 낮음 | **높음** |
| I. 해외 콘텐츠를 현지화하는 사용자 | **최고** | 일부 | 주 2~5 | 좋음 | 중 | 중 | **최고** — AutoMaker 의 현지화 프롬프트가 이미 이것을 전제로 만들어져 있다 |

**1차 타깃: I + A** — 「해외(한국 등) 콘텐츠를 조사해 일본 시장용 롱폼을 만드는,
얼굴 없는 1인 운영자」. 본인이 정확히 그 사람이다.
**2차 타깃: B + H** — 다채널·자동화 채널 운영자. 온보딩 부담을 감수할 동기가 있다.

**E·F·G(소상공인·기업)는 지금 구조와 맞지 않는다.** Video Score·Age Bucket·
Outlier 는 **YouTube 롱폼 시장 전제**로 만들어진 지표다. 다른 도메인에 옮기면
지표가 아니라 껍데기만 남는다.

## 7. 「본인이 첫 고객」 전략

| 장점 | 단점 |
|---|---|
| 요구사항이 정확하다 (실제로 쓰는 사람이 만든다) | **표본이 1이다.** 내 채널에서 통한 것이 남에게도 통하는지 알 수 없다 |
| 온보딩 비용이 0 (채널 DNA 를 이미 안다) | 온보딩의 어려움을 **체감하지 못한다** — 남에게 팔 때 가장 큰 장벽을 못 본다 |
| 데이터가 진짜다 | 검증에 시간이 오래 걸린다 (30건 = 3~6개월) |
| 실패해도 손실이 작다 | 제품 개발과 채널 운영을 동시에 하면 **둘 다 느려진다** |

**판정: 적절하다. 단 조건이 있다.**

- 제품 개발과 채널 운영을 **동시에 하지 말 것.** 지금 상태(게시 0건)에서
  기능을 더 만드는 것은 **검증 없는 개발**이다.
- **Stage 1 을 먼저 끝내라:** Phase 0~2 만 만들고(2~3주), 그 다음 **콘텐츠 10편을
  실제로 게시**한다. 그 10편이 없으면 Phase 4·5 는 설계도만 남는다.
- 10편을 내는 동안 나오는 «불편» 이 진짜 요구사항이다.

## 8. KPI — MVP 에서 측정할 것과 아직 측정하면 안 되는 것

### 지금 측정해도 되는 것

| 영역 | 지표 | 왜 지금 |
|---|---|---|
| Efficiency | **소재 발견 → 제작 승인까지 걸린 시간** | 지금 바로 잴 수 있고, 개선 여부가 즉시 보인다 |
| Efficiency | 도구 간 수동 복사 횟수 | 4 → 0 |
| Discovery | 추천 후보 중 실제 제작까지 간 비율 | 결정 기록이 생기면 자동 |
| Production | 콘텐츠 1편 제작 소요 시간 | AutoMaker 가 이미 단계별로 안다 |
| Cost | 콘텐츠 1편당 LLM/이미지 비용 | Radar 의 quota 계량 개념을 확장 |

### 아직 측정하면 안 되는 것

| 지표 | 왜 |
|---|---|
| MAKE 판단 콘텐츠의 성과 우위 | **채널 평균이 없다** (게시 0건). 비교 기준이 없는 비율은 숫자 놀이다 |
| Prediction 적중률 | 예측을 아직 저장하지 않는다 |
| CTR·유지율 | 게시 후에만 존재 |
| 「같은 실수 반복률」 | 실수 이력이 0건 |

**규칙: 표본 10건 미만에서는 성과 지표를 화면에 «등급» 으로 표시하지 않는다.**

## 9. Moat 평가

| 후보 | 등급 | 근거 |
|---|---|---|
| 코드 | **LOW** | 복제 가능. 게다가 AutoMaker 는 16,883줄 단일 파일 — 유지보수가 오히려 부채 |
| 분석 알고리즘 | **LOW~MEDIUM** | ADViews·Age Bucket 은 좋은 설계지만 문서에 다 적혀 있고 재현 가능 |
| 데이터(남의 영상) | **LOW** | 누구나 같은 API 로 모을 수 있다 |
| 데이터(우리 성과) | **HIGH** | 계정 데이터. 복제 불가 |
| Workflow | **MEDIUM** | 따라 만들 수는 있으나 «어느 단계에 사람이 들어가야 하는가» 는 경험이 필요 |
| 채널별 Content Memory | **HIGH** | 시간과 실제 운영이 필요 |
| Prediction → Actual History | **HIGH** | 위와 같음. **가장 강한 후보** |
| 사용자별 맞춤 전략 | **MEDIUM** | 데이터가 쌓인 뒤에만 |
| AI Agent | **LOW** | **«LLM 을 붙였다» 는 것 자체는 우위가 아니다.** 누구나 붙인다 |
| Production Automation | **LOW** | 시장에 많다. VOICEVOX·ffmpeg·Flow 모두 공개 도구 |
| 사용자 경험 | **MEDIUM** | Radar 화면의 «경고문을 같이 보여주는» 설계는 실제로 드물다 |

**HIGH 는 셋뿐이고 전부 «실제로 운영해야 생기는 것» 이다.**

## 10. 경쟁 제품 대비 위치

> 아래는 널리 알려진 카테고리 구분이며, 각 서비스의 현재 기능·사용자 수를 확인하지
> 않았다. 확인하지 않은 것을 단정하지 않는다.

| 카테고리 | 대표 | 우리와의 관계 |
|---|---|---|
| 채널 분석·SEO | vidIQ 계열 | Radar 와 **겹침**. 다만 Radar 는 «일본 롱폼·소형채널 아웃라이어» 로 좁다 |
| Outlier/아이디어 발견 | 1of10·OutlierKit 계열 | Radar 와 **가장 많이 겹침** |
| 콘텐츠 재가공 | OpusClip 계열 | AutoMaker 14단계와 겹침 |
| SNS 생성·게시 | Predis·Ocoya 계열 | AutoMaker 와 겹침 |
| 게시·성과 분석 | Metricool 계열 | Phase 4 와 겹침 |

**우리는 이들을 대체하려는 것이 아니다.** 위 카테고리들은
「발견」·「생성」·「게시」를 각각 잘하지만 **그 사이의 «판단» 은 사용자에게 맡긴다.**
우리 자리는 **그 사이**다. 이것은 강점이자 약점이다 —
사이에 있는 제품은 **양쪽이 다 있어야 가치가 생긴다.**

| 2 | 「내 판단이 맞았는지 나중에 확인할 수 있는 콘텐츠 기획 도구」 | 주 2편 이상 내는 사람 | 성과와 판단이 연결 안 됨 | Prediction→Actual |
| 3 | 「해외에서 잘 된 소재를 내 채널 각도로 바꿔 주는 도구」 | 현지화 크리에이터 | 그대로 베끼면 안 되는데 각도를 못 잡음 | 채널 렌즈 기반 Angle |
| 4 | 「소형 채널에서 유난히 잘 된 영상만 골라 오는 레이더」 | 아이디어가 마르는 사람 | 큰 채널만 보인다 | 구독자 대비 + 매크 방어 |
| 5 | 「기획부터 완성 영상까지 복사·붙여넣기 없이」 | 도구를 여러 개 쓰는 사람 | 도구 사이 손 노동 | 파일 계약 |
| 6 | 「같은 주제를 두 번 만들지 않게 기억해 주는 콘텐츠 노트」 | 다작 채널 | 중복 제작 | Content Memory |
| 7 | 「연금·세금 같은 위험한 주제에서 사실 확인을 강제하는 제작 도구」 | 시니어 대상 채널 | 틀리면 사람에게 손해 | Fact Check 게이트 |
| 8 | 「일본 롱폼 시장을 매일 아침 5분에 보는 화면」 | 일본 시장 진출자 | 시장을 모른다 | 좁고 깊음 |

**가장 유력한 셋: 2 · 3 · 1.**
1·4·8 은 이미 있는 제품과 겹치고, 5 는 «편해진다» 이지 «잘 된다» 가 아니다.
**2 가 가장 방어 가능하다** — 경쟁자가 복제하기 가장 어려운 자산과 정확히 맞는다.

## 17. 제품 MVP 재정의

**기술 MVP 가 아니라 «제품 가치를 검증하는 MVP».**

```
Radar         오늘의 기회 3~5개                    ← 이미 있음
   ↓
Strategist    MAKE/WATCH/SKIP + 근거 + 반대 근거    ← 신규 (핵심)
              + Channel Fit + Angle + confidence
   ↓
사람          승인                                 ← 신규 (기록)
   ↓
AutoMaker     프로젝트 자동 생성 + brief.json       ← 연결
   ↓
              콘텐츠 제작                          ← 이미 있음
   ↓
사람          게시 + URL 한 칸 입력                 ← 신규 (최소)
   ↓
Radar         24h/72h/7d 자동 스냅샷               ← 기존 모듈 재사용
   ↓
Strategist    예상 vs 실제 (표본 10건 전엔 «판단 불가»)
```

**MVP 에서 빼도 되는 것:** 자연어 질의 · 중복 소재 방지 · 위키 · 패턴 통계 ·
CTR/유지율 자동 수집 · 숏폼 성과 · 다채널 비교 · 예측값 자체(초기엔 «등급»만)

## 18. 지금 가장 먼저 증명해야 할 가설 3개

1. **「근거가 기록되면 판단이 실제로 나아지는가」**
   → 검증법: 결정 20건을 기록하고, 3개월 뒤 «그때 왜 그렇게 봤는지» 를 읽었을 때
   지금 다시 판단해도 같은 결론이 나오는지 본다. 코드가 아니라 **읽기** 로 검증한다.

2. **「Radar 가 고른 소재가 실제로 우리 채널에서 통하는가」**
   → 검증법: **10편을 실제로 게시한다.** 이것 없이는 어떤 기술적 개선도 검증되지 않는다.

3. **「복사·붙여넣기 제거가 실제로 시간을 줄이는가」**
   → 검증법: 지금 1편 기획에 걸리는 시간을 **먼저 재고**, Phase 3 이후 다시 잰다.
   지금 재지 않으면 나중에 비교할 기준이 없다.

**기술 개발보다 먼저 할 것: ①번의 «시간 측정» 과 ②번의 «게시 개시».**
둘 다 코드가 필요 없다.

## 19. 결론 — 이 시스템은 무엇이 되는 것이 좋은가

| 후보 | 판정 |
|---|---|
| A. 개인 생산성 도구 | **지금은 이것이다.** 그리고 당분간 이것으로 충분하다 |
| B. Creator 전문 Tool | **가능성 있음.** 조건: 게시 30건 + 온보딩 단순화 |
| C. SaaS | **아직 아니다.** 사용자 1명, 게시 0건, 온보딩 13항목 |
| D. Agency/Consulting 내부 OS | **현실적인 중간 경로.** 대행 + 컨설팅에 도구를 얹는 방식 |
| E. 다른 형태 | — |

**판정: A 로 시작해 D 를 거쳐 B 를 노린다. C 는 지금 목표로 삼지 않는다.**

이유:

- 이 시스템의 유일한 진짜 자산(Prediction→Actual)은 **직접 운영해야만 생긴다.**
  따라서 A(자기 운영)가 자산 축적 단계 그 자체다.
- D(대행/컨설팅)는 사용자를 1명에서 3~5명으로 늘리면서 **온보딩의 실제 난이도를
  체감**하게 해 준다. SaaS 로 가려면 반드시 거쳐야 할 단계다.
- B/C 로 바로 가면 «기능은 많은데 아무도 온보딩을 못 끝내는 제품» 이 된다.
  채널 DNA 13항목 필수 입력이 그 증거다.

**가장 정직한 한 줄:**
지금 이 프로젝트에 부족한 것은 기능이 아니라 **실제로 게시된 콘텐츠 10편**이다.
