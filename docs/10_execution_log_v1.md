# 10_execution_log_v1.md

## 1. 문서 목적

이 문서는 **AI 테크 뉴스 블로그 자동화 프로젝트의 실행 기록 기준 문서**이다.

목적은 다음과 같다.

- 각 실행(run)의 입력, 조건, 결과를 일관되게 기록한다.
- 어떤 프롬프트/모델/입력 조합이 좋은 결과를 냈는지 추적한다.
- 실패 원인과 반복 패턴을 축적한다.
- 재실행, 수정, 승인 과정을 나중에 다시 확인할 수 있게 한다.
- 프롬프트 개선과 모델 비교의 근거 자료로 활용한다.

---

## 2. 적용 범위

이 문서는 아래 실행 유형에 적용한다.

- 초안 생성 실행
- 모델 비교 실행
- 프롬프트 버전 비교 실행
- HTML 산출물 생성 실행
- 재실행(run retry)
- 수동 수정 후 승인 기록
- 게시 후보 선정 기록

---

## 3. 운영 원칙

실행 로그는 단순 메모가 아니라 **재현 가능한 운영 기록**이어야 한다.

### 원칙
1. 모든 주요 실행은 run 단위로 기록한다.
2. 입력, 프롬프트, 모델, 결과 파일명을 최소 기록 항목으로 남긴다.
3. 좋았던 실행뿐 아니라 실패한 실행도 기록한다.
4. 모호한 감상보다 관찰 가능한 문제를 적는다.
5. 로그는 짧아도 되지만, 다음 실행에 도움이 되어야 한다.

---

## 4. 로그 기록이 필요한 이유

실행 로그가 없으면 아래 문제가 생긴다.

- 어떤 조합이 잘 됐는지 다시 찾기 어렵다.
- 실패 원인이 입력 문제인지 프롬프트 문제인지 구분하기 어렵다.
- 같은 실수를 반복하게 된다.
- 모델 비교 결과가 감각적인 판단에 머무르게 된다.
- 게시된 결과가 어떤 생성 조건에서 나왔는지 추적이 안 된다.

따라서 로그는 선택이 아니라 운영 필수 항목으로 본다.

---

## 5. 기본 기록 단위

이 프로젝트의 기본 기록 단위는 **1회 실행(run)** 이다.

### 1회 실행의 정의
아래 요소가 하나의 조합으로 묶여 결과가 생성된 경우를 1 run으로 본다.

- 특정 입력 세트
- 특정 프롬프트 버전
- 특정 모델
- 특정 출력 목표
- 1회 생성 결과

예를 들어,
같은 입력으로 모델만 바꿔 3번 돌렸다면 3개의 run으로 기록한다.

---

## 6. run_id 규칙

각 실행은 추적 가능하도록 고유한 `run_id`를 가진다.

### 권장 형식
```text
RUN_YYYYMMDD_001
RUN_YYYYMMDD_002
RUN_YYYYMMDD_003
```

### 예시
```text
RUN_20250704_001
RUN_20250704_002
```

### 원칙
1. 날짜 기준으로 생성한다.
2. 같은 날 여러 번 실행하면 뒤에 일련번호를 붙인다.
3. run_id는 중복되지 않게 관리한다.
4. 관련 출력 파일이나 메모에도 가능하면 같은 run_id를 연결한다.

---

## 7. 최소 기록 항목

모든 run에 대해 아래 항목은 반드시 기록한다.

- `run_id`
- 실행 날짜
- 실행 목적
- 입력 파일명
- 입력 기사 수
- 프롬프트 파일명 또는 버전
- 모델명
- 출력 형식
- 출력 파일명
- 결과 상태
- 주요 문제
- 수동 수정 여부
- 최종 판단

---

## 8. 권장 추가 기록 항목

운영 품질을 높이기 위해 아래 항목도 가능하면 함께 기록한다.

- 기사 주제 요약
- 비교 대상
- 프롬프트의 핵심 지시 차이
- 재실행 여부
- 재실행 사유
- HTML 오류 여부
- 제목 품질 메모
- 비교표 품질 메모
- 결론 품질 메모
- 환각/과장 여부
- 게시 승인 여부
- 다음 액션

---

## 9. 결과 상태 분류 기준

실행 결과는 아래 상태 중 하나 이상으로 분류한다.

### 상태 값 예시
- `Draft Generated`
- `Review Needed`
- `Manual Edit Needed`
- `Manual Edit Done`
- `Rerun Needed`
- `Approved for Posting`
- `Rejected`
- `Archived for Reference`

### 상태 해석
- `Draft Generated`: 초안 생성 완료
- `Review Needed`: 검수 필요
- `Manual Edit Needed`: 수동 수정 필요
- `Manual Edit Done`: 수정 완료
- `Rerun Needed`: 재생성 필요
- `Approved for Posting`: 게시 가능
- `Rejected`: 운영 기준 미달
- `Archived for Reference`: 참고용 보관

---

## 10. 실행 목적 분류 기준

로그에는 이번 실행이 무엇을 위한 것인지도 기록한다.

### 목적 값 예시
- `Draft Creation`
- `Prompt Test`
- `Model Comparison`
- `HTML Validation`
- `Rerun After Failure`
- `Post Candidate Generation`

### 목적 기록 이유
같은 결과라도 실행 목적이 다르면 평가 기준이 달라질 수 있기 때문이다.

예:
- 초안 생성용 실행은 구조 완성이 중요하다.
- 프롬프트 실험은 특정 섹션 개선 여부가 중요하다.
- HTML 검증은 형식 안정성이 가장 중요하다.

---

## 11. 로그 작성 형식

운영 편의상 로그는 **표 형식 요약 + 상세 메모 형식**을 함께 쓰는 것을 권장한다.

### 11.1 요약 로그
빠르게 비교할 수 있는 한 줄 요약 기록

### 11.2 상세 로그
문제 원인, 수정 포인트, 재실행 이유 등을 남기는 기록

이 두 층으로 관리하면 검색과 회고가 쉬워진다.

---

## 12. 요약 로그 템플릿

아래 형식을 기본 템플릿으로 사용한다.

```md
| run_id | date | purpose | input_file | prompt_version | model | output_file | status | final_decision |
|---|---|---|---|---|---|---|---|---|
| RUN_20250704_001 | 2025-07-04 | Draft Creation | input_openai_google_001.md | prompt_compare_v1 | gpt-4.x | draft_openai_google_001.html | Review Needed | Edit |
```

---

## 13. 상세 로그 템플릿

아래 형식을 상세 기록 템플릿으로 사용한다.

```md
## RUN_20250704_001

- Date: 2025-07-04
- Purpose: Draft Creation
- Input File: input_openai_google_001.md
- Input Article Count: 5
- Topic: OpenAI vs Google recent AI strategy signals
- Prompt Version: prompt_compare_v1
- Model: gpt-4.x
- Output Format: HTML
- Output File: draft_openai_google_001.html

### Result Summary
- 구조는 전반적으로 안정적
- 비교표 포함
- 결론이 다소 단정적
- HTML은 큰 오류 없음

### Detected Issues
- 도입부가 약간 일반론적임
- Google 설명보다 OpenAI 설명이 더 길어 균형이 약함
- 결론에서 우열처럼 읽힐 수 있는 표현 존재

### Manual Edit
- 결론 표현 완화
- 비교표 문구 길이 정리
- 도입부 첫 문장 수정

### Final Status
- Status: Manual Edit Done
- Final Decision: Approved for Posting

### Next Action
- prompt_compare_v1의 결론 지시문 보강 검토
```

## 14. 간단 로그 템플릿

## 15. 입력 관련 기록 원칙

입력이 달라지면 결과도 크게 달라지므로 입력 기록은 매우 중요하다.

### 반드시 남길 것
- 입력 파일명
- 기사 수
- 기사 주제
- 비교 대상
- 입력 세트 특징

### 가능하면 남길 것
- 기사 날짜 범위
- 기사 출처 수
- 입력 정제 여부
- 입력 품질 메모

### 예시
```text
입력 기사 5건 / 최근 7일 내 기사 / OpenAI 2건, Google 2건, 시장 분석 1건
```

---

## 16. 프롬프트 관련 기록 원칙

프롬프트는 결과 품질 변화의 핵심 변수이므로 버전 기록이 필수다.

### 기록 항목
- 프롬프트 파일명
- 프롬프트 버전
- 이전 버전 대비 차이
- 실험 목적이 있으면 그 포인트

### 예시
```text
prompt_compare_v2
- v1 대비 결론 과장 억제 문구 추가
- 비교표 축 일관성 지시 강화
```

---

## 17. 모델 관련 기록 원칙

모델별 결과 차이를 비교하려면 모델 정보가 정확해야 한다.

### 기록 항목
- 모델명
- 필요 시 실행 설정 메모
- 동일 입력/동일 프롬프트 조건 여부

### 기록 목적
- 어떤 모델이 구조적으로 안정적인지 확인
- 어떤 모델이 과장 표현이 많은지 확인
- 어떤 모델이 HTML 출력을 더 잘 지키는지 비교

---

## 18. 출력 품질 기록 원칙

단순히 “좋다/나쁘다”가 아니라 항목별로 기록하는 것이 좋다.

### 권장 기록 축
- 제목 품질
- 도입부 품질
- 기사 기반성
- 비교 축 일관성
- 결론 톤
- HTML 안정성
- 수동 수정량

### 예시 메모
```text
- 제목: 무난함
- 도입부: 약간 일반론적
- 비교표: 축 안정적
- 결론: 단정적
- HTML: 정상
- 수정량: 소폭
```

---

## 19. 실패 기록 원칙

실패한 run도 매우 중요한 자산이다.

### 실패 로그에 꼭 남길 것
- 무엇이 실패였는가
- 왜 수정이 아니라 재실행이 필요했는가
- 입력/프롬프트/모델 중 어디 원인이 더 큰가
- 같은 실패를 막기 위한 다음 조치

### 나쁜 기록 예
```text
결과가 별로였음
```

### 좋은 기록 예
```text
비교 구조가 무너져 OpenAI 설명만 길게 생성됨.
입력 기사 균형도 약했고, 프롬프트의 비교 축 지시도 부족했음.
다음 run에서는 입력 세트 재구성 + 비교 항목 고정 지시 추가 필요.
```

---

## 20. 수동 수정 기록 원칙

자동 생성 후 사람이 수정한 내용도 가능한 범위에서 남긴다.

### 기록할 내용
- 수정했는지 여부
- 어떤 부분을 수정했는지
- 왜 수정했는지
- 수정량이 적었는지 많았는지

### 수정 수준 예시
- `None`
- `Light`
- `Moderate`
- `Heavy`

### 예시
```text
Manual Edit Level: Light
- 제목 표현 완화
- 결론 2문장 수정
- 표 셀 문구 압축
```

---

## 21. 재실행 기록 원칙

재실행은 단순 반복이 아니라 **실험 결과의 연장선**으로 기록해야 한다.

### 기록 항목
- 이전 run_id
- 재실행 사유
- 바뀐 조건
- 개선 여부

### 예시
```md
### Rerun Info
- Previous Run: RUN_20250704_001
- Reason: conclusion too strong / comparison imbalance
- Changed Condition: prompt_compare_v2 used
- Improvement: better conclusion tone, still slight intro generalization
```

---

## 22. 승인 및 게시 기록 원칙

최종적으로 게시까지 연결되는 run은 별도로 표시해두는 것이 좋다.

### 기록 항목
- 게시 승인 여부
- 승인 날짜
- 게시 후보 파일명
- 최종 수정 반영 여부

### 예시
```text
Approved: Yes
Approved Date: 2025-07-04
Posting Candidate File: final_openai_google_001.html
```

## 23. 로그 저장 방식 권장안

실제 운영에서는 로그를 한 파일에 누적하거나, 날짜별로 분리할 수 있다.

### 방식 A: 단일 누적 문서
- 장점: 검색이 쉽다
- 단점: 길어질 수 있다

### 방식 B: 날짜별 로그 파일
- 장점: 관리가 깔끔하다
- 단점: 비교 검색이 다소 번거롭다

### 권장
초기에는 단일 누적 문서로 시작하고,  
run 수가 많아지면 월별 또는 날짜별로 분리한다.

## 24. 파일명 권장 예시

로그 파일도 규칙적으로 관리하는 것이 좋다.

### 예시
```text
execution_log_master_v1.md
execution_log_2025_07.md
execution_log_2025_07_04.md
```

### 원칙
- 날짜 또는 범위가 드러나게 한다
- 버전 관리가 가능하게 한다
- 프로젝트 전체 규칙과 맞춘다

## 25. 체크리스트 문서와의 연결

실행 로그는 체크리스트와 함께 쓸 때 가장 유용하다.

### 연결 방식
- 체크리스트에서 실패한 항목을 로그에 기록
- 반복 실패 항목을 집계
- 어떤 항목에서 자주 막히는지 확인
- 체크리스트 개정 필요 여부 판단

예:
```text
체크리스트 10.2 표현 리스크 항목 반복 실패
→ 프롬프트 결론 가이드 강화 필요
```

---

## 26. 예시 문서와의 연결

출력 품질은 `09_output_examples_v1.md`의 예시와 연결해 평가할 수 있다.

### 예시 연결 방식
- 좋은 예시와 유사한 패턴인지 메모
- 나쁜 예시 패턴이 재발했는지 메모
- 수정 전/수정 후 사례를 예시 문서로 옮길 후보 표시

### 예시 메모
```text
도입부는 Acceptable Example 수준
비교표는 Good Example에 가까움
결론은 Bad Example 경향이 일부 존재
```

---

## 27. 모델 비교 문서와의 연결

모델 비교 실험 시 실행 로그는 비교 문서의 원자료가 된다.

### 활용 방법
- 동일 입력, 동일 프롬프트 조건의 결과를 나란히 기록
- 모델별 강점/약점을 반복 관찰
- HTML 안정성, 비교 품질, 과장 표현 빈도 등을 축적

### 예시 비교 메모
```text
Model A: 구조 안정성 높음, 결론 다소 단정적
Model B: 문체 자연스러움, 비교표 축 일관성 약함
```

## 28. 로그 품질을 떨어뜨리는 나쁜 습관

아래와 같은 방식은 로그의 가치를 떨어뜨린다.

- 파일명 기록 누락
- 프롬프트 버전 미기록
- “좋음”, “별로” 같은 감상만 적기
- 실패 원인 없이 재실행만 반복
- 수정 내역 기록 생략
- 승인 여부 누락
- run 간 차이점 기록 누락

---

## 29. 좋은 로그의 조건

좋은 실행 로그는 아래 조건을 만족한다.

- 나중에 봐도 무슨 실행인지 알 수 있다
- 무엇이 달랐는지 알 수 있다
- 왜 좋았는지/왜 실패했는지 추적 가능하다
- 다음 실행에서 바로 참고할 수 있다
- 프롬프트 개선이나 모델 비교에 활용 가능하다
